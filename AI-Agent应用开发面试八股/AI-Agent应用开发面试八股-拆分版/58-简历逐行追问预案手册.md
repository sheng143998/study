# 简历逐行追问预案手册

> 目标：让简历上的每一行 AI Agent / RAG / MCP / Python 项目经历，都能经得起 3 层追问。  
> 这份文件不是教你继续美化简历，而是帮你把已经写上去的内容变成可防守的面试答案。

配合文件：

- `20-简历项目Bullet优化版.md`：写出更好的项目 bullet。
- `49-简历JD定制与版本管理手册.md`：按岗位维护不同简历版本。
- `50-个人项目素材库模板.md`：补真实证据。
- `42-项目深挖追问防守库.md`：准备连续追问。
- `54-项目指标与BadCase量化手册.md`：补指标和 bad case。
- `70-项目作品集与Demo证据包手册.md`：准备 README、Demo、API/schema、评测表和脱敏说明。

## 1. 简历逐行防守原则

简历上的每个技术动词都可能变成追问入口。

```text
负责
  -> 你具体负责什么？

设计
  -> 为什么这么设计？

优化
  -> 优化前后指标是什么？

接入
  -> 接入链路、鉴权、异常怎么处理？

构建
  -> 从 0 到 1 做了哪些模块？

参与
  -> 你参与到什么深度？
```

逐行防守的目标：

```text
每一条 bullet
  -> 能说 30 秒
  -> 能展开 2 分钟
  -> 能回答 3 个追问
  -> 能给 1 个真实证据
  -> 能承认 1 个边界
```

## 2. 简历逐行审查表

复制你的每条 bullet，按下面表格审查。

| 检查项 | 问题 | 是否通过 |
|---|---|---|
| 真实性 | 这是我亲自做的吗？ |  |
| 边界 | 哪些是我主责，哪些是团队完成？ |  |
| 细节 | 能说出数据、接口、字段、日志、配置吗？ |  |
| 指标 | 有离线或线上验证吗？ |  |
| bad case | 遇到过什么问题？ |  |
| 取舍 | 为什么选这个方案，不选别的？ |  |
| 迁移 | 能迁移成系统设计题吗？ |  |
| 风险 | 哪句话最容易被追问穿？ |  |

危险信号：

- 写了“优化”，但没有优化前后对比。
- 写了“负责”，但说不清模块边界。
- 写了“平台”，但其实只是一个脚本。
- 写了“上线”，但没有用户、流量、日志或反馈。
- 写了“Agent”，但没有状态、工具、权限、终止条件。

## 3. Bullet 拆解模板

每条 bullet 拆成 6 行：

```text
原 bullet：
我真正做的部分：
相关技术链路：
可量化证据：
可能追问：
防守回答：
```

示例：

```text
原 bullet：
负责企业知识库 RAG 检索链路优化，引入混合召回和 rerank 提升问答准确率。

我真正做的部分：
参与 query rewrite、BM25 + 向量召回、rerank 接入和 bad case 复盘。

相关技术链路：
query -> rewrite -> hybrid retrieval -> rerank -> prompt -> citation checker。

可量化证据：
离线评测集包含 X 类问题；观察 Recall@K、引用准确率和人工 bad case。

可能追问：
混合召回怎么融合？rerank 放在哪里？准确率怎么定义？

防守回答：
我先把问题拆成召回和排序两层。向量召回解决语义相似，BM25 解决专有名词和编号，融合后进入 rerank，再把 topN 片段给模型。准确率不是主观感觉，而是看正确证据是否进入 topK、引用是否支持答案，以及 bad case 是否减少。
```

## 4. RAG 类 bullet 追问预案

### 4.1 常见写法

```text
负责企业知识库 RAG 系统建设，完成文档解析、chunk 切分、向量检索、rerank 和答案生成链路。
```

面试官可能追问：

1. 文档有哪些类型？
2. chunk 怎么切？
3. embedding 模型怎么选？
4. 向量库用什么，为什么？
5. rerank 怎么接？
6. 引用溯源怎么做？
7. 召回不准怎么定位？
8. 权限怎么过滤？

30 秒防守：

```text
这条主要对应 RAG 的离线入库和在线问答链路。我负责的重点是 chunk 策略、检索召回、rerank 和引用校验。文档入库时保留 doc_id、section、page、tenant_id、permission、version 等元数据；在线查询先做权限过滤和混合召回，再 rerank，最后用带引用的 Prompt 生成答案。
```

3 层追问准备：

```text
第一层：讲完整链路。
第二层：讲 chunk、召回、rerank 的具体取舍。
第三层：讲 bad case、指标、权限和更新。
```

候选证据：

- 文档类型和数量级。
- chunk 规则。
- metadata 字段。
- topK / rerank 参数。
- 1 个召回失败 bad case。
- 1 个引用错误 bad case。

### 4.2 高危词：提升准确率

如果简历写了：

```text
提升问答准确率。
```

需要能回答：

```text
准确率怎么定义？
评测集怎么构造？
提升来自 chunk、召回、rerank 还是 prompt？
有没有牺牲延迟或成本？
```

防守回答：

```text
这里的准确率不是单一指标。我拆成检索层和生成层：检索层看正确证据是否进入 topK 和排序是否靠前；生成层看答案是否忠于证据、引用是否准确、无答案是否拒答。优化前主要问题是正确证据召回靠后，所以优先做混合召回和 rerank，而不是直接改 Prompt。
```

## 5. Agent 类 bullet 追问预案

### 5.1 常见写法

```text
设计客服 Agent 编排流程，支持意图识别、知识库检索、订单查询、工单创建和人工转接。
```

面试官可能追问：

1. 为什么用 Agent，不用固定工作流？
2. 状态怎么设计？
3. 工具 schema 怎么设计？
4. 工具调用失败怎么办？
5. 写操作如何防误调用？
6. Agent 死循环怎么办？
7. 人工接管条件是什么？

30 秒防守：

```text
这个 Agent 不是完全自由执行，而是把大模型放在意图识别、工具选择和参数补全上。高风险流程仍然用显式状态机控制。状态里维护 intent、slots、retrieved_docs、tool_calls、risk_level、approval_status 和 final_answer；写操作前做用户确认、权限校验和幂等控制。
```

候选证据：

- 工具列表。
- 一个工具 schema。
- 状态字段。
- 最大步数限制。
- 人工接管规则。
- 1 个工具失败 bad case。

### 5.2 高危词：自动处理

如果简历写了：

```text
自动处理订单查询、售后咨询和工单创建。
```

必须澄清：

```text
哪些是只读？
哪些是写操作？
哪些需要确认？
哪些必须转人工？
```

防守回答：

```text
我不会把所有动作都交给模型自动执行。订单查询是只读工具，可以在权限校验后直接调用；工单创建属于写操作，需要用户确认和幂等 key；退款、改地址等高风险动作需要人工确认或转人工。模型只负责生成调用建议和参数，最终执行由工具网关判断。
```

## 6. MCP / OpenAPI 工具平台 bullet 追问预案

### 6.1 常见写法

```text
构建 OpenAPI 转 Tool 的工具接入平台，支持 Agent 统一发现和调用企业内部 API。
```

面试官可能追问：

1. OpenAPI 怎么转 Tool？
2. operationId、parameters、requestBody 怎么处理？
3. 工具描述怎么写？
4. MCP 和 OpenAPI 什么关系？
5. 权限和审计怎么做？
6. 怎么防止模型滥用工具？

30 秒防守：

```text
OpenAPI 主要描述 HTTP API，我做的是把已有 API 转成模型可理解的 Tool schema。转换时会用 operationId 生成工具名，把 parameters 和 requestBody 合并成输入 schema，再补充业务描述、风险等级、权限要求、错误码和幂等信息。真正执行工具前还要经过工具网关校验和审计。
```

候选证据：

- 一个 OpenAPI path 示例。
- 转换后的 tool schema 示例。
- 权限模型。
- 调用日志字段。
- 风险等级规则。

### 6.2 高危词：MCP

如果简历写了 MCP：

需要能回答：

```text
MCP server 暴露了哪些 tools/resources/prompts？
客户端怎么发现工具？
权限在哪里做？
为什么不用直接 HTTP API？
```

防守回答：

```text
我理解 MCP 的价值是标准化大模型应用接入工具和上下文，而不是替代 OpenAPI。已有业务服务仍然可以是 HTTP/RPC，MCP server 负责把它们包装成 Agent 可发现、可调用的 tools/resources。权限、审计和风险控制不能只依赖 MCP 协议本身，要落在工具网关和业务服务层。
```

## 7. Python 后端 bullet 追问预案

### 7.1 常见写法

```text
基于 FastAPI 构建大模型应用后端，支持异步模型调用、SSE 流式响应、限流、日志和异常处理。
```

面试官可能追问：

1. 为什么用 FastAPI？
2. async/await 适合什么？
3. SSE 怎么实现？
4. 用户断连怎么办？
5. 模型超时怎么办？
6. 限流怎么做？
7. 日志记录哪些字段？

30 秒防守：

```text
大模型应用里模型 API、向量库、工具调用都偏 I/O 密集，FastAPI 的 async 能减少等待阻塞。流式输出用 SSE 返回 token 事件，提升首 token 体验。工程上还要做超时、断连取消、限流、重试、trace 日志和错误码规范，避免模型调用不稳定影响后端服务。
```

候选证据：

- SSE 伪代码。
- 限流算法。
- 超时配置。
- 日志字段。
- 一个异常处理流程。

## 8. 模型网关 / 平台 bullet 追问预案

### 8.1 常见写法

```text
参与模型网关建设，封装多模型调用、Prompt 版本管理、流式响应、限流熔断、fallback 和成本统计。
```

面试官可能追问：

1. 模型网关和普通 SDK 封装有什么区别？
2. 路由策略怎么设计？
3. Prompt 怎么灰度和回滚？
4. fallback 会不会影响答案质量？
5. 成本怎么统计？
6. 某天成本突然升高怎么排查？

30 秒防守：

```text
普通 SDK 封装只解决调用接口一致，模型网关还要做租户鉴权、配额、路由、限流、fallback、Prompt 版本、成本统计、日志审计和评测。它的核心价值是让多个业务可控地接入模型，而不是每个业务各自处理稳定性和成本问题。
```

候选证据：

- app_id / tenant_id / prompt_version / model 字段。
- 路由策略。
- fallback 规则。
- 成本统计维度。
- 灰度回滚流程。

## 9. 指标类 bullet 追问预案

### 9.1 常见写法

```text
通过优化检索和 Prompt 策略，降低 bad case 占比并提升用户满意度。
```

面试官可能追问：

1. bad case 怎么定义？
2. 用户满意度怎么采集？
3. 是哪个优化起作用？
4. 有没有 A/B？
5. 有没有副作用？

防守回答：

```text
我会把 bad case 按输入、文档、检索、生成、工具、权限几类归因。优化时尽量一次只改一个变量，比如先改 chunk 或 rerank，再用固定评测集回归。线上如果有用户反馈，可以看点赞、追问率、人工转接率；如果没有真实流量，就诚实说是离线评测或内部试点数据。
```

不要说：

```text
准确率大幅提升。
效果明显变好。
用户反馈不错。
```

除非你能说清楚数据来源。

## 10. 项目阶段怎么防守

### 10.1 Demo 阶段

可以说：

```text
这个项目目前是 Demo/原型阶段，没有真实线上流量，所以我没有写生产指标。我主要验证了技术链路，包括文档入库、检索召回、生成、引用和日志，并用小规模评测集检查效果。
```

不要说：

```text
已经上线并提升了业务效率。
```

### 10.2 内部试点

可以说：

```text
这个项目处于内部试点阶段，用户量不大，所以我更关注 bad case 类型、内部反馈和链路稳定性。我们记录 query、召回片段、答案和反馈，用于迭代检索和 Prompt。
```

### 10.3 生产上线

可以说：

```text
生产阶段我会关注业务指标和护栏指标。业务上看满意率、任务完成率、人工转接率；工程上看 P95 延迟、错误率、成本、越权调用和 fallback 比例。
```

## 11. 逐行压测问题清单

把简历每条 bullet 都问一遍：

```text
这条是你主责还是参与？
你做的第一步是什么？
最难的问题是什么？
为什么选这个方案？
有没有替代方案？
出过什么 bad case？
怎么定位的？
怎么验证优化有效？
如果流量放大 10 倍怎么办？
如果重做一次，你会改哪里？
```

如果任意一条回答不上，这条简历就要改轻一点，或者回 `50` 补证据。

## 12. 简历修改红线

应该降级的写法：

| 原写法 | 降级写法 |
|---|---|
| 负责整体架构 | 参与核心链路设计 |
| 独立完成平台建设 | 完成平台原型/核心模块 |
| 上线服务多个业务 | 支持内部试点/接入若干场景验证 |
| 准确率提升 X% | 构建评测集并优化召回/引用 bad case |
| 自动处理全流程 | 支持部分流程自动化，高风险节点人工确认 |

原则：

```text
宁可简历保守但细节扎实，不要写得很大但一追就空。
```

## 13. 最终速背

```text
每条简历 bullet 都要准备：
我做了什么
为什么这么做
具体怎么做
效果怎么验证
出错怎么兜底
边界是什么

RAG 追：
chunk / 召回 / rerank / 引用 / 权限 / 评测

Agent 追：
state / tool schema / 参数校验 / 风险确认 / 人工接管

MCP 追：
tools / resources / OpenAPI 关系 / 权限 / 审计

后端追：
async / SSE / 限流 / 超时 / 日志 / 断连

平台追：
多租户 / 路由 / Prompt 版本 / fallback / 成本 / 灰度
```

面试官不是按你心里真实经历提问，而是按你简历上的词提问。写上去的每一个词，都要能落到证据、链路、指标和边界。
