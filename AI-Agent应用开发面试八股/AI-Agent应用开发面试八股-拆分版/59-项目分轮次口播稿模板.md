# 项目分轮次口播稿模板

> 目标：同一个 AI Agent / RAG 项目，按一面、二面、交叉面、主管面、HR 面切换表达重点。  
> 面试里不是“项目讲得越全越好”，而是“这一轮面试官想确认什么，你就先证明什么”。

配合文件：

- `18-自我介绍与项目包装.md`：开场和项目基础表达。
- `24-项目答辩讲稿版.md`：5 分钟项目答辩。
- `40-大厂公司轮次作战手册.md`：公司和轮次目标。
- `55-公司轮次面试路径卡.md`：公司 × 轮次行动卡。
- `58-简历逐行追问预案手册.md`：简历 bullet 防守。

## 1. 分轮次表达总原则

同一个项目，五轮关注点不同：

| 轮次 | 面试官想确认 | 项目表达重点 |
|---|---|---|
| 一面 | 是不是你做的，基础扎不扎实 | 职责边界、技术链路、具体实现 |
| 二面 | 能否解决复杂问题 | 难点、bad case、指标、取舍 |
| 交叉面 | 能否迁移到别的场景 | 抽象能力、系统设计、通用方法 |
| 主管面 | 是否有 ownership 和业务理解 | 目标、价值、协作、复盘 |
| HR 面 | 动机、稳定性、沟通成熟度 | 经历真实性、成长、选择原因 |

一句话：

```text
一面讲“我做了什么”，二面讲“我怎么解决问题”，主管面讲“这件事为什么有价值”。
```

## 2. 一面项目口播：证明真实性

### 2.1 60 秒版本

```text
我重点讲一个 [项目名]。这个项目面向 [用户/业务场景]，主要解决 [痛点]。

我负责的是 [你的模块]，不是整个系统都由我一个人完成。我的工作主要包括三块：第一是 [模块 1]，第二是 [模块 2]，第三是 [模块 3]。

技术链路上，用户问题会先经过 [入口/鉴权/预处理]，然后进入 [RAG/Agent 编排]，再调用 [向量库/工具/模型]，最后通过 [引用/校验/流式响应] 返回。

这个项目里我最熟的是 [最熟模块]，后面如果追问，我可以从 [实现细节]、[bad case] 和 [指标] 展开。
```

### 2.2 一面不要讲太多

不要一上来讲：

- 平台宏大愿景。
- 复杂系统设计全图。
- 团队所有模块。
- 还没做的未来规划。

一面要先给面试官抓手：

```text
我负责哪块
我做了哪些技术动作
我能被追问哪些细节
```

### 2.3 高频追问接法

问：这个项目是你独立做的吗？

```text
不是完全独立。整体项目由团队协作完成，我主要负责 [模块]。比如 [具体链路] 是我设计和实现的，[另一个模块] 是和同事联调，[不属于你的模块] 我了解接口和数据流，但不是我主责。
```

问：你最熟哪一块？

```text
我最熟的是 [模块]，因为这里我从方案、实现到 bad case 复盘都参与了。比如当时遇到 [问题]，我通过 [定位方式] 找到原因，最后用 [方案] 解决。
```

## 3. 二面项目口播：证明解决问题能力

### 3.1 3 分钟版本

```text
这个项目的背景是 [业务痛点]，第一版能跑通链路，但真正难点不在 Demo，而在 [准确率/权限/延迟/工具可靠性/成本]。

我负责的核心模块是 [模块]。上线或试点过程中遇到过一个典型 bad case：[现象]。

我当时没有直接改 Prompt，而是先分层定位：第一看 [输入/数据/检索/工具/模型]，第二看 [日志/trace/指标]，第三用 [评测集/回放/灰度] 验证。

最后选择的方案是 [方案]。这个方案的取舍是 [收益]，代价是 [成本/延迟/复杂度]，所以我加了 [缓存/限流/人工确认/fallback/监控] 做兜底。

结果上，我们用 [指标] 观察效果。如果重新做，我会优先补 [下一步优化]。
```

### 3.2 二面必须讲的 4 件事

- 一个真实问题。
- 一个定位过程。
- 一个技术取舍。
- 一个验证指标。

二面不要只说：

```text
我们优化了 chunk，加了 rerank，改了 prompt。
```

要说：

```text
问题先表现为什么，日志里看到什么，最后判断是哪一层，为什么选这个方案，怎么验证。
```

### 3.3 二面收束句

```text
所以我理解这个项目的难点不是单点模型效果，而是把检索、工具、权限、日志和评测串成可迭代闭环。
```

## 4. 交叉面项目口播：证明迁移能力

### 4.1 2 分钟版本

```text
如果把这个项目抽象出来，我会把它看成一个企业级大模型应用的通用架构：入口层负责鉴权、限流和流式响应；编排层负责 RAG 或 Agent 流程；能力层包含模型、向量检索和工具调用；数据层保存文档、索引、会话和日志；治理层负责评测、审计、成本和灰度。

我原项目偏 [RAG/Agent/平台]，但这个方法可以迁移到 [另一个场景]。差异主要在 [数据源/工具风险/权限模型/指标]。比如从企业知识库迁移到智能客服，RAG 知识问答可以复用，但要额外补订单/工单工具、人工接管和高风险操作确认。
```

### 4.2 交叉面常见问题

问：如果不用你原来的框架，你怎么做？

```text
我会先保留架构思路，而不是绑定框架。核心是数据入库、检索/工具编排、模型调用、日志评测和权限治理。LangChain/LangGraph 是实现方式之一，如果不用它，也可以用 FastAPI + 自定义状态机 + 工具网关实现，只是 checkpoint 和可观测要自己补。
```

问：如果业务场景换了怎么办？

```text
我会先识别哪些能力可复用，哪些必须重做。通常模型网关、日志、评测、权限框架可复用；知识库的文档结构、工具 schema、业务指标和 bad case 分类需要按场景重做。
```

## 5. 主管面项目口播：证明业务价值和 ownership

### 5.1 3 分钟版本

```text
这个项目对业务的价值是 [效率/成本/体验/质量]。在项目开始前，原流程是 [人工/搜索/多系统切换]，主要问题是 [慢/不准/不可追踪/成本高]。

我在项目里承担的是 [角色]。除了实现 [模块]，我也参与了和 [产品/业务/算法/后端] 的对齐，主要推动了 [协作事项]。

这个项目让我印象最深的是 [困难/冲突/失败]。当时我学到的是，AI 应用不能只追求模型回答看起来聪明，还要关注业务边界、风险兜底和效果验证。

如果重新做，我会在早期就补 [评测集/日志/权限/灰度/用户反馈]，这样后面迭代会更稳。
```

### 5.2 主管面要避免

- 只讲技术细节，不讲业务价值。
- 把所有功劳说成自己的。
- 遇到失败只怪模型或数据。
- 不知道项目下一步怎么演进。

### 5.3 ownership 表达

```text
我不是只把分配给我的接口写完，而是会关注这个模块上线后能不能被定位、能不能被评估、出了问题谁能复盘。所以我会主动补日志字段、bad case 记录和评测样例。
```

## 6. HR 面项目口播：证明动机和成长

### 6.1 90 秒版本

```text
我做这个项目最大的收获是，对 AI Agent / RAG 应用有了更工程化的理解。刚开始我更多关注模型能不能答出来，后来发现真正难的是数据质量、工具权限、效果评估和线上稳定性。

这个经历也影响了我现在的求职方向。我希望继续做大模型应用开发，不只是调模型接口，而是参与从业务问题、技术架构到工程落地的完整闭环。
```

### 6.2 HR 常见追问

问：为什么想做 AI Agent 应用开发？

```text
因为它既需要大模型能力，也需要后端工程和业务理解。我比较喜欢这种能把技术直接落到业务流程里的方向，而且我之前的项目经验也让我意识到，Agent/RAG 真正有价值的部分在于可控、可评估、可迭代的工程闭环。
```

问：这个项目最大的挫折是什么？

```text
最大的挫折是第一版效果看起来能演示，但 bad case 一多就发现不够稳。后来我意识到不能只靠 Prompt 修问题，要补日志、评测集和链路分层定位。这件事让我对工程闭环的理解更深。
```

## 7. 同一项目五种说法示例

项目：企业知识库 RAG。

一面：

```text
我负责的是 RAG 在线问答链路，主要做 query 预处理、混合召回、rerank、Prompt 拼装和引用校验。文档入库会保留 doc_id、section、page、permission、version 等元数据，在线检索时先做权限过滤，再召回和重排。
```

二面：

```text
这个项目最大的难点是召回不稳定和引用不可信。我会先看正确证据是否进入 topK，再看 rerank 排序和生成忠实度。我们通过 bad case 回放发现，很多问题不是 Prompt，而是文档切分和专有名词召回，所以加了标题路径、BM25 和 rerank。
```

交叉面：

```text
这个项目可以抽象成企业级 RAG 平台：文档入库、检索编排、模型生成、权限过滤、引用校验、评测回流。如果迁移到客服场景，要额外接订单/工单工具和人工接管。
```

主管面：

```text
这个项目的价值是降低内部员工查文档的成本，并让答案有引用可追溯。我参与后最大的体会是，AI 应用不是能答就行，而是要能解释、能评估、能兜底。
```

HR 面：

```text
这个项目让我确认自己想做大模型应用开发，因为它既有模型能力，也有后端工程和业务落地。我比较享受把不确定的模型能力变成稳定产品能力的过程。
```

## 8. 轮次切换速记

```text
一面：
职责边界 + 技术链路 + 实现细节。

二面：
bad case + 定位过程 + 指标取舍。

交叉面：
抽象架构 + 迁移能力 + 不绑定框架。

主管面：
业务价值 + 协作推动 + 复盘成长。

HR 面：
求职动机 + 成长收获 + 稳定表达。
```

临场提醒：

```text
不要每轮都背同一段项目介绍。先判断这轮在看什么，再决定是讲细节、讲难点、讲抽象、讲价值，还是讲成长。
```
