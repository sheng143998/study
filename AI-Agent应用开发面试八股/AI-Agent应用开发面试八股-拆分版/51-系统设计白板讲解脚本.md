# 系统设计白板讲解脚本

> 目标：二面/三面系统设计时，能在 8-12 分钟内边画边讲清楚架构。  
> 这份文件配合 `14-系统设计图与伪代码.md`、`32-P2系统设计平台加分版.md` 使用。

## 1. 系统设计现场节奏

推荐节奏：

```text
0-1 分钟：需求澄清
1-3 分钟：画核心链路
3-6 分钟：讲关键模块
6-8 分钟：讲稳定性、权限、评测、成本
8-10 分钟：处理追问和取舍
最后 30 秒：总结
```

不要一上来就画复杂大图。先澄清：

- 用户是谁？
- 主要场景是什么？
- QPS / 数据规模大概多少？
- 是否需要权限？
- 是否需要工具调用？
- 更关注准确率、延迟、成本，还是安全？

开场句：

```text
我先按一个企业级大模型应用的思路来设计。为了避免过度设计，我先确认几个约束：用户规模、文档规模、是否多租户、是否要求引用溯源，以及是否有高风险工具调用。
```

## 2. 白板通用骨架

画图顺序：

```text
用户入口
  -> API 层
  -> 业务编排层
  -> 模型/检索/工具能力层
  -> 数据与存储层
  -> 治理与观测层
```

口播：

```text
我会把系统拆成五层：入口层负责鉴权、限流和流式响应；编排层负责 RAG 或 Agent 流程；能力层包含模型、向量检索和工具调用；数据层保存文档、索引、会话和日志；治理层负责评测、审计、成本和监控。
```

## 3. 企业知识库 RAG 白板脚本

### 3.1 题目

```text
设计一个企业内部知识库问答系统，要求支持文档上传、权限控制、引用溯源和效果评估。
```

### 3.2 澄清问题

```text
我先确认几个点：文档主要是 PDF/Word/网页还是表格？是否多部门权限隔离？答案是否必须给引用？文档更新频率是实时还是每天同步？目标是内部员工使用还是对外客服？
```

### 3.3 白板画法

```text
用户
  -> Web/IM 入口
  -> API Gateway
  -> Query Processor
  -> Retriever
  -> Reranker
  -> Prompt Builder
  -> LLM
  -> Citation Checker
  -> Answer

文档侧：
Document Upload
  -> Parser
  -> Cleaner
  -> Chunker
  -> Embedding
  -> Vector DB + Metadata Store

治理侧：
Eval Set + Bad Case + Trace + Cost + Permission
```

### 3.4 8 分钟讲解词

```text
我把这个系统分成离线入库和在线问答两条链路。

离线入库这边，文档上传后先做解析和清洗，保留标题层级、页码、来源、版本和权限 metadata。然后按文档类型切分，FAQ 可以按问答对切，制度文档按标题层级和语义段落切，表格类内容尽量保留表头和上下文。切分后做 embedding，写入向量库，同时 metadata 写入结构化存储。

在线问答这边，用户请求先经过鉴权和限流。Query Processor 会做问题改写、意图识别和权限上下文补充。Retriever 会基于用户权限做 metadata filter，再做向量召回或 hybrid search。候选文档进入 reranker，选出 top-k 证据。Prompt Builder 把证据、引用 id 和回答约束组装给模型。模型生成后，Citation Checker 检查引用是否存在，证据不足时返回无法确认。

治理上，我会建设评测集和 bad case 回流。指标包括 top-k 命中率、答案准确率、引用覆盖率、拒答率、延迟和 token 成本。线上每次请求都记录 trace_id、召回文档、模型版本、prompt 版本和用户反馈，方便后续定位问题。
```

### 3.5 高频追问

追问：权限过滤在召回前还是召回后？

```text
优先召回前过滤，避免越权文档进入候选集。召回后也可以做二次校验，作为防线。尤其企业知识库里，不应该先召回再让模型决定能不能看。
```

追问：召回不准怎么优化？

```text
先看正确文档是否进入候选集。如果没有，查解析、切分、embedding、query rewrite 和 hybrid search；如果候选里有但没进上下文，查 rerank；如果上下文有但答错，查 prompt、引用和生成约束。
```

追问：如何避免幻觉？

```text
从四层做：检索证据相关、生成必须基于证据、引用校验、证据不足拒答。高风险场景还要人工审核。
```

### 3.6 收束句

```text
这个设计的核心不是简单把文档塞给模型，而是把文档质量、权限过滤、检索排序、引用校验和评测回流做成闭环。
```

## 4. Agent 工具平台白板脚本

### 4.1 题目

```text
设计一个支持多工具调用的 AI Agent 平台，业务方可以接入不同工具，Agent 可以根据用户任务自动调用。
```

### 4.2 澄清问题

```text
我先确认工具类型：是内部 HTTP API、OpenAPI、RPC，还是 MCP Server？工具有没有高风险操作？是否需要人工确认？平台是给一个业务用，还是多个业务线接入？
```

### 4.3 白板画法

```text
用户
  -> Agent API
  -> Intent / Planner
  -> State Manager
  -> Tool Selector
  -> Tool Executor
  -> Result Summarizer

工具接入：
OpenAPI Adapter / MCP Client / Internal RPC Adapter
  -> Tool Registry
  -> Schema Validator
  -> Auth & Permission
  -> Audit Log

治理：
Max Steps / Timeout / Retry / Human Confirm / Trace / Eval
```

### 4.4 10 分钟讲解词

```text
我会把 Agent 平台拆成运行时和工具接入两部分。

运行时这边，用户请求进入 Agent API 后，先做意图识别和任务边界判断。Planner 负责决定下一步是检索、追问用户、调用工具，还是直接回答。State Manager 保存用户意图、已执行步骤、工具结果、错误信息和确认状态。Tool Selector 根据任务和权限选择候选工具，Tool Executor 负责真正执行工具，执行结果再交给模型总结。

工具接入这边，平台支持 OpenAPI、MCP 和内部 RPC。不同来源的工具都会注册到 Tool Registry，统一维护 tool name、description、JSON schema、风险等级、权限要求和版本。模型只能提出工具调用意图，执行前必须经过 Schema Validator 和权限系统。高风险工具需要 human confirm。

为了防止 Agent 不可控，我会加最大步数、超时、重复调用检测、失败重试和降级。所有工具调用记录 trace_id、user_id、tool_name、tool_version、参数摘要、权限结果、耗时和错误码，方便审计和复盘。
```

### 4.5 高频追问

追问：为什么需要 Tool Registry？

```text
因为工具来源多、版本多、权限不同。如果没有统一注册中心，Agent 很难知道工具语义、参数 schema、风险等级和版本兼容情况。
```

追问：如何防 prompt 注入诱导工具调用？

```text
模型输出不能直接执行。后端要做工具白名单、权限校验、参数校验和风险分级。高风险操作需要人工确认，敏感字段来自服务端上下文，不来自模型。
```

追问：Agent 死循环怎么办？

```text
设置最大步数、最大工具调用次数、重复 action 检测和超时。连续失败后终止并解释当前进度，必要时转人工。
```

### 4.6 收束句

```text
Agent 平台的关键不是让模型尽可能自动，而是在明确边界内让工具调用可控、可追踪、可恢复。
```

## 5. 模型网关白板脚本

### 5.1 题目

```text
设计一个公司内部模型网关，支持多个业务线统一接入不同大模型，并做限流、成本统计和降级。
```

### 5.2 澄清问题

```text
我先确认：接入的是内部模型还是外部供应商？业务线数量大概多少？是否需要多租户隔离？更关注成本、延迟、可用性还是模型效果？是否需要流式响应？
```

### 5.3 白板画法

```text
业务系统
  -> Gateway API
  -> Auth / Tenant
  -> Rate Limiter
  -> Router
  -> Provider Adapter
  -> Model Provider

旁路：
Prompt Config
Model Config
Cost Meter
Trace Log
Eval / Monitor
Fallback Policy
```

### 5.4 8 分钟讲解词

```text
模型网关的核心价值是统一接入、统一治理和统一观测。

入口层提供统一 API，业务方不直接接不同模型供应商，而是通过 Gateway API。请求进入后先做租户鉴权、配额检查和限流。Router 根据任务类型、优先级、上下文长度、成本预算和模型可用性选择模型。Provider Adapter 屏蔽不同供应商的协议差异，包括流式输出、错误码、token 统计和重试策略。

配置侧维护模型配置、prompt 配置、路由策略和 fallback 策略。成本侧记录 input token、output token、模型单价、业务线和用户维度。观测侧记录 trace_id、latency、error_code、model_name、prompt_version 和 retry 情况。

稳定性上，网关要支持超时、重试、熔断、降级和多模型 fallback。比如强模型不可用时降级到备用模型，低优先级任务可以排队或拒绝，高优先级任务保障配额。
```

### 5.5 高频追问

追问：模型路由依据是什么？

```text
按任务类型、质量要求、上下文长度、成本、延迟、可用性和租户优先级。路由策略需要通过离线评测和线上灰度验证，不是拍规则。
```

追问：如何统计成本？

```text
按业务线、租户、用户、模型、接口维度记录 token 和单价。支持预算、告警和成本看板。缓存命中和失败请求也要分开统计。
```

追问：多模型 fallback 有什么风险？

```text
不同模型输出质量和格式可能不同，所以 fallback 要配合 prompt 兼容、结构化输出校验和灰度。不能只看可用性，还要看效果回归。
```

### 5.6 收束句

```text
模型网关不是简单转发，而是把模型接入、路由、限流、成本、观测和降级统一治理。
```

## 6. 白板追问处理方法

### 6.1 面试官追问性能

回答顺序：

```text
先说瓶颈
  -> 再说优化
  -> 再说指标
```

例子：

```text
RAG 系统的主要延迟来自检索、rerank 和模型生成。检索可以用索引和缓存优化，rerank 可以控制候选数量，模型生成可以用流式输出和模型路由优化。指标上看 P50/P95 延迟、首 token 延迟和超时率。
```

### 6.2 面试官追问安全

回答顺序：

```text
鉴权
  -> 数据权限
  -> 工具权限
  -> 审计
```

例子：

```text
安全上我会分四层：入口鉴权确认用户身份；检索前用 metadata 做数据权限过滤；工具执行前做工具级权限和参数校验；最后记录审计日志，支持追踪和回放。
```

### 6.3 面试官追问评测

回答顺序：

```text
离线评测
  -> 线上反馈
  -> bad case 回流
  -> 回归测试
```

例子：

```text
离线先用 golden set 评估命中率、准确率、引用覆盖率；线上收集用户反馈和 bad case；每次改 chunk、embedding、prompt 或模型后都做回归。
```

## 7. 白板禁忌

不要：

- 一上来画十几个框。
- 只讲模型，不讲数据和权限。
- 只讲功能，不讲评测和兜底。
- 被追问时临时推翻全部设计。
- 说“这个框架会自动处理”。

可以：

- 先画主链路，再补治理。
- 主动说明取舍。
- 不确定的规模先假设。
- 用“如果规模更大，可以演进为...”扩展。

## 8. 最后速记

系统设计的高分结构：

```text
需求澄清
  -> 核心链路
  -> 模块拆分
  -> 数据和状态
  -> 权限和安全
  -> 评测和观测
  -> 成本和稳定性
  -> 演进和取舍
```

一句话：

```text
白板面试不是画最复杂的图，而是让面试官相信你的系统能上线、能排查、能治理、能演进。
```
