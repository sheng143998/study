## 1. 必背开场

### 1 分钟自我介绍

```text
面试官您好，我主要关注大模型应用开发和 AI Agent/RAG 工程落地。

我做过的核心项目是一个面向企业知识库/业务流程的智能问答与 Agent 系统，主要包括文档解析、向量检索、RAG 问答、工具调用、权限控制和日志观测几个模块。

技术上我比较熟悉 Python、FastAPI、LangChain/LangGraph、向量数据库、Prompt Engineering、Tool Calling，也了解 OpenAPI、RPC、MCP 这类工具集成方式。

我比较关注的不只是 Demo 效果，而是线上稳定性，比如召回质量、幻觉控制、工具调用安全、流式响应、成本和 trace。
```

## 2. 项目 2 分钟版

```text
我做的是一个企业知识库问答/业务 Agent 系统，目的是把分散的制度文档、产品文档、历史工单和业务 API 统一成一个智能入口。

架构上分离线和在线两条链路。离线侧做文档采集、解析、清洗、切分、embedding 和索引构建，同时保留 doc_id、page、section、tenant_id、permission、version 等元数据。在线侧先做鉴权和 query rewrite，再走向量加 BM25 混合召回，召回后 rerank，最后把证据和引用拼进 Prompt，让模型基于证据回答。

Agent 部分主要处理工具调用和业务流程。查询类工具可以自动执行，比如查订单、查工单；写操作必须用户确认，并且后端会做 schema 校验、权限检查、超时、幂等和审计。

主要难点是召回不准、幻觉和工具调用风险。我们通过 badcase 集、chunk 优化、hybrid search、rerank、引用校验、工具白名单和 trace 日志做治理。
```

## 3. RAG 必背

### RAG 是什么

```text
RAG 是检索增强生成。它先从外部知识库检索相关内容，再让模型基于这些内容生成答案。它适合私有知识、频繁更新知识和需要引用溯源的场景。
```

### 完整链路

```text
离线：文档采集 -> 解析 -> 清洗 -> 切分 -> embedding -> 建索引 -> 存元数据。
在线：query rewrite -> 召回 -> metadata filter -> rerank -> 上下文构造 -> LLM 生成 -> 引用校验。
```

### 召回不准

```text
我会按链路排查：文档解析是否丢内容，chunk 是否合理，embedding 是否适合领域，query 是否需要改写，top_k 是否合适，是否需要 hybrid search 和 rerank，metadata filter 是否过严或过松。
```

### 幻觉治理

```text
RAG 只能降低幻觉，不能消灭幻觉。要从召回质量、rerank、Prompt 约束、无依据拒答、引用校验和 groundedness 检测一起治理。
```

### 权限过滤

```text
权限元数据要在入库时写入，例如 tenant_id、department、acl。检索时做 metadata filter，避免无权限文档进入候选集。生成后再过滤是不够的，因为模型可能已经看到敏感内容。
```

## 4. Agent 必背

### Agent 是什么

```text
Agent 是以目标为导向的大模型应用系统，能进行规划、调用工具、读取外部知识、维护状态，并根据执行结果继续决策。
```

### Agent 循环

```text
目标输入 -> 规划 -> 选择工具/动作 -> 执行 -> 观察结果 -> 更新状态 -> 判断继续或结束。
```

### Agent 不稳定原因

```text
模型输出有随机性，工具描述可能不清，多步误差会累积，上下文可能漂移，工具可能失败，终止条件不明确，权限如果只靠 Prompt 也不安全。
```

### 防死循环

```text
最大步数、超时、token budget、step_count、error_count、重复工具调用检测、条件边终止、fallback 和人工介入。
```

## 5. Tool Calling 必背

### 流程

```text
模型读取工具 schema -> 判断是否需要工具 -> 输出 tool_name 和 arguments -> 应用层校验参数 -> 鉴权 -> 执行工具 -> 返回 observation -> 模型继续或输出最终答案。
```

### 安全

```text
模型只负责提出调用意图，真正执行必须由后端控制。要做 schema 校验、工具白名单、用户权限、超时、幂等、审计，高风险操作必须人工确认。
```

### 非幂等操作

```text
下单、退款、删除、发邮件这类操作不能随便自动重试。必须有 idempotency_key，并确认上一次调用状态，避免重复执行。
```

## 6. LangChain / LangGraph 必背

### LangChain

```text
LangChain 是 LLM 应用组件库，封装模型调用、Prompt、Retriever、VectorStore、Tool、Agent、OutputParser、Callback 和 Runnable。
```

### LangGraph

```text
LangGraph 是有状态 Agent 工作流框架，用 State、Node、Edge 和 Conditional Edge 显式表达流程，适合复杂、多步骤、需要 checkpoint 和 human-in-the-loop 的生产 Agent。
```

### 区别

```text
LangChain Agent 更适合简单工具调用循环；LangGraph 更适合复杂流程，因为状态、分支、循环、恢复和人工确认都更明确。
```

## 7. MCP / OpenAPI / RPC 必背

```text
OpenAPI 描述 HTTP API，RPC 是远程过程调用抽象，MCP 是 AI 应用连接工具、资源和 Prompt 的标准协议。

MCP 不是 OpenAPI 的替代品。MCP server 内部可以包装 OpenAPI、RPC、数据库、文件系统或 SaaS 工具，再以统一方式暴露给 Agent。
```

## 8. 微调必背

```text
缺知识优先 RAG，行为模式不稳定考虑 Prompt 或微调。

RAG 适合私有知识、实时知识和引用溯源；微调适合稳定任务模式、输出格式、领域风格和话术。

微调不能很好解决频繁变化的知识，也不能完全解决幻觉。
```

## 9. Python / 后端必背

### GIL

```text
GIL 是 CPython 的全局解释器锁，同一进程里通常只有一个线程执行 Python 字节码。CPU 密集型多线程收益有限，IO 密集型仍可以通过线程或 asyncio 提升吞吐。
```

### asyncio

```text
asyncio 适合 LLM API、向量库、数据库、外部 HTTP 工具这类 IO 密集场景。CPU 密集任务要用进程池、任务队列或独立服务。
```

### SSE

```text
SSE 适合模型 token 流式输出，服务端通过 text/event-stream 持续推送 chunk。要处理断连、超时、异常和日志。
```

## 10. 系统设计万能模板

```text
1. 明确业务目标和用户。
2. 画整体架构。
3. 讲离线数据链路。
4. 讲在线请求链路。
5. 讲状态、权限、安全。
6. 讲评估指标。
7. 讲延迟、成本、稳定性。
8. 讲 badcase 闭环和迭代。
```

万能收束句：

```text
这个系统的核心不是把大模型接进来，而是围绕大模型的不确定性做工程治理：数据要可追溯，工具要可控，状态要可恢复，答案要可评估，风险操作要可审计。
```

## 11. 反问

优先问：

1. 团队现在的大模型应用更偏 RAG、Agent，还是模型平台？
2. 当前线上最大的难点是效果、成本、延迟，还是安全合规？
3. 团队是否有离线评测集和 badcase 闭环？
4. Agent 工具调用是否已经接入权限和审计？
5. 这个岗位更偏业务应用落地，还是基础平台建设？
