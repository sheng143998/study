# 面试官评分 Rubric 与回答自检表

> 目标：把“我感觉答得还行”变成可量化自检。  
> 这份文件适合配合 `16-模拟面试套卷.md`、`24-项目答辩讲稿版.md`、`35-面试后复盘与资料更新指南.md` 使用。

## 1. 总体评分模型

AI Agent 应用开发面试里，面试官通常不是只看你会不会背概念，而是在看 5 类信号：

| 维度 | 面试官在看什么 | 高分表现 | 低分表现 |
|---|---|---|---|
| 基础理解 | 概念、流程、原理是否清楚 | 能讲清定义、流程、边界和适用场景 | 名词堆砌、概念混淆 |
| 项目真实性 | 是否真的做过 | 能说清数据、接口、异常、指标和细节 | 只讲“我们用了某框架” |
| 工程闭环 | 能否上线和治理 | 有评估、监控、兜底、权限、成本 | 只停留在 Demo |
| 问题定位 | 遇到坏 case 怎么分析 | 能拆环节、找证据、做实验 | 直接说“调 prompt” |
| 沟通表达 | 是否清晰、稳定、有结构 | 先结论后展开，能主动收束 | 跑题、越讲越散 |

一句话：

```text
面试不是证明你见过多少名词，而是证明你能把不确定的大模型能力变成可控的工程系统。
```

## 1.1 1-5 分与 A/B/C 换算

为了和 `69`、`77`、`66`、`80` 保持一致，模拟面评分统一这样换算：

| raw_score | grade | display | close_level | 含义 | 强制动作 |
|---|---|---|---|---|---|
| 5 | A | A | 可关闭 | 强通过 | 可进入上场包 |
| 4 | A- | A | 可关闭但记录补强点 | 可通过但不稳 | 记录一个补强点 |
| 3 | B | B | 未关闭 | 边缘 | 必须绑定修复文件和复测题 |
| 3 且复测连续两次满足通过标准 | B+ | B | 可关闭 | 稳定边缘通过 | 记录复测证据后可关闭 |
| 2 | C | C | 未关闭 | 危险 | 必须生成弱点修复卡，暂停扩展新资料 |
| 1 | C- | C | 未关闭 | 不通过 | 回专题文件重练，不进入上场包 |

低分强制动作：

```text
B/C 项 -> 写入 `80` 弱点修复卡 -> 登记 `77` 总账本 -> 生成复测题 -> 复测通过后才能关闭
```

说明：`display` 只用于看板压缩展示，`grade` 用于记录细分状态。`B+` 不是新的 raw_score，而是“3 分项经过复测后连续两次满足通过标准，仍未达到 A，但允许关闭”的状态。

## 2. 5 分制 Rubric

### 2.1 5 分：强通过

特征：

- 回答结构清楚。
- 概念准确。
- 能结合项目细节。
- 有指标和权衡。
- 能主动讲风险和兜底。
- 被追问两层仍然稳定。

示例：

```text
RAG 召回不准我会先分层定位，不会直接改 prompt。第一步看文档解析和 chunk 是否丢信息；第二步看 query 和 chunk 的语义是否匹配；第三步看向量召回、关键词召回和 metadata filter 的命中情况；第四步看 rerank 后证据是否进入上下文。我们项目里用 top-k 命中率、答案准确率、引用覆盖率和人工 bad case 复盘来验证，最后把失败样本回流到评测集。
```

### 2.2 4 分：可通过

特征：

- 主流程清楚。
- 能说出常见优化。
- 项目结合较弱但不空。
- 指标或兜底有一部分。

风险：

- 遇到资深面试官深挖时可能不够。
- 系统设计和主管面需要补业务价值。

### 2.3 3 分：边缘

特征：

- 知道概念，但回答偏散。
- 能背流程，但讲不出真实问题。
- 只能说通用方案，没有指标。

典型表现：

```text
召回不准可以优化 chunk，换 embedding，加 rerank，然后改 prompt。
```

问题：

- 这句话不是错，但太像清单。
- 没有定位顺序。
- 没有项目证据。
- 没有评估指标。

### 2.4 2 分：危险

特征：

- 概念不稳。
- 混淆 RAG、Agent、微调、Prompt。
- 问项目细节答不上。
- 没有工程治理意识。

常见危险回答：

```text
Agent 就是让大模型自动调用工具。
```

为什么危险：

- 没讲状态、规划、观察、反馈。
- 没讲工具 schema 和权限。
- 没讲终止条件和失败恢复。
- 容易被判断为只做过 Demo。

### 2.5 1 分：不通过

特征：

- 明显背诵痕迹。
- 追问一次就断。
- 项目细节和简历不一致。
- 不能解释关键技术选择。

典型信号：

- “这个不是我负责的。”
- “框架自动处理了。”
- “没做过评估。”
- “没有遇到什么问题。”
- “具体参数不太记得。”

如果真实没做过，也不要硬编。更好的表达是：

```text
这个点我没有在线上完整落地过，但我会按这样的思路处理：先明确风险边界，再拆链路定位，最后用离线评测和小流量灰度验证。
```

## 3. 回答结构自检

每个技术题最好包含 5 个层次：

```text
定义
  -> 流程
  -> 难点
  -> 优化
  -> 评估/兜底
```

每个项目题最好包含 6 个层次：

```text
业务背景
  -> 我的职责
  -> 技术方案
  -> 难点和取舍
  -> 指标结果
  -> 复盘改进
```

每个系统设计题最好包含 7 个层次：

```text
需求澄清
  -> 核心模块
  -> 数据流
  -> 存储和接口
  -> 稳定性
  -> 安全和权限
  -> 评估和演进
```

| 4 | 能讲流程和常见优化，有部分指标 |
| 3 | 只会 chunk、embedding、rerank 清单 |

| 分数 | 表现 |

| 4 | 能针对高并发、低延迟、权限、成本等约束给出主要优化点 |

| 2 | 面试官加一个约束就推翻原设计，回答变散 |
| 1 | 只会背基础架构，无法处理多租户、私有化、强审计等生产约束 |

高分关键词：

- constraint mapping。

- metadata filter。
- timeout / retry / fallback。
- model routing。
- semantic cache。
- human-in-the-loop。
- audit log。
- SLO / SLA。
- rollback。

自检问题：

- 我有没有先复述“新增约束”是什么？
- 我有没有说清楚这个约束影响接入层、检索层、工具层、模型层还是治理层？
- 我有没有给出 2-3 个具体模块调整，而不是只说“优化一下”？
- 我有没有给出质量、延迟、成本、稳定性、安全中的至少 2 类指标？
- 我有没有说明失败、超时、权限失败或低置信度时怎么兜底？

## 5. 项目真实性自检

如果你说自己做过一个项目，至少要能回答下面问题。

### 5.1 基础细节

- 数据来源是什么？
- 数据规模多大？
- 用户是谁？
- 日调用量大概多少？
- 主要接口有哪些？
- 技术栈为什么这么选？
- 你负责哪部分？

### 5.2 RAG 项目细节

- 文档怎么解析？
- chunk 大小怎么定？
- embedding 模型怎么选？
- 向量库怎么选？
- top-k 设置多少？
- 是否有 metadata filter？
- rerank 是否使用？
- 引用如何生成？
- 无答案怎么识别？
- 评测集怎么构造？

### 5.3 Agent 项目细节

- Agent 的任务边界是什么？
- 状态里存什么？
- 工具有多少个？
- 工具 schema 谁维护？
- 哪些工具需要人工确认？
- 最大执行步数是多少？
- 失败后怎么重试？
- 日志如何追踪？
- 成功率怎么定义？
- 成本怎么控制？

### 5.4 后端项目细节

- 用同步还是异步？
- 流式响应怎么做？
- 模型超时怎么办？
- 用户断连怎么办？
- 限流怎么做？
- 缓存怎么设计？
- 日志字段有哪些？
- 如何排查线上慢请求？
- 如何部署？
- 如何回滚？

如果这些问题答不上，先回去补 `18`、`20`、`24`。

## 7. 回答升级公式

### 7.1 从 3 分升到 4 分

把“清单式回答”升级成“定位式回答”。

3 分：

```text
RAG 效果不好可以优化 chunk、embedding、rerank 和 prompt。
```

4 分：

```text
我会先判断问题发生在哪个环节。如果是文档解析丢信息，先修解析；如果是召回没有命中，优化 chunk、embedding 或 hybrid search；如果证据进了上下文但答案不准，再优化 prompt 和引用校验。
```

### 7.2 从 4 分升到 5 分

把“定位式回答”升级成“工程闭环回答”。

5 分：

```text
我会用 bad case 和评测集分层定位解析、切分、召回、排序、生成、引用哪个环节出问题。每次只改一个变量，用 top-k 命中率、答案准确率、引用覆盖率、延迟和成本对比。上线后保留无答案识别、人工反馈和版本回滚，把失败样本回流到评测集。
```

## 8. 面试官危险信号

如果面试官开始这样追问，说明你的回答不够具体：

- “能不能举个你项目里的例子？”
- “这个指标具体怎么算？”
- “这个是你负责的吗？”
- “如果线上出问题怎么办？”
- “为什么不用另一个方案？”
- “这个数据量有多大？”
- “有没有 bad case？”
- “有没有做过评估？”

应对方式：

```text
先承认刚才讲得偏抽象
  -> 补一个项目例子
  -> 给出数据或指标
  -> 说明当时的取舍
  -> 最后收束到结果
```

示例：

```text
刚才我讲得有点偏方案，我补一个项目里的例子。我们当时遇到的问题是制度类文档召回命中但答案没有引用依据，后来定位到 chunk 太长导致证据边界不清。我们改成按标题层级和语义段落切分，并在生成阶段强制绑定 source id，之后引用覆盖率和人工验收通过率都有明显提升。
```

## 9. 回答长度控制

| 场景 | 建议长度 | 结构 |
|---|---:|---|
| 一面快问 | 30-60 秒 | 结论 + 2-3 点 |
| 技术深挖 | 2-3 分钟 | 流程 + 难点 + 项目例子 |
| 系统设计 | 8-12 分钟 | 需求 + 架构 + 治理 + 演进 |
| 主管面项目 | 3-5 分钟 | 背景 + 角色 + 结果 + 复盘 |
| HR 面 | 1-2 分钟 | 真实、稳定、正向 |

如果面试官不断打断，说明要更短：

```text
先给结论。这个问题我会从三个层面处理：召回、生成、评估。第一...
```

如果面试官沉默听你讲，说明可以展开：

```text
我展开讲一个项目里的 case...
```

## 10. 最后检查清单

一次回答结束前，快速自问：

- [ ] 我有没有先给结论？
- [ ] 我有没有讲流程？
- [ ] 我有没有讲项目例子？
- [ ] 我有没有讲指标？
- [ ] 我有没有讲取舍？
- [ ] 我有没有讲风险和兜底？
- [ ] 我有没有自然收束？

最短高分句式：

```text
这个问题我会先拆链路定位，再针对瓶颈优化，最后用指标和线上兜底验证，而不是只调 prompt 或换模型。
```

最后一句：

```text
高分回答的本质，是让面试官相信你真的经历过问题、解决过问题，并且知道下一次怎么更系统地解决。
```
