# 标准回答三件套：30 秒版、2 分钟版、项目版

> 用法：先背 30 秒版，保证一面快问快答不空；再练 2 分钟版，应对技术深挖；最后把项目版替换成自己的真实经历。

## 1. 什么是 AI Agent

### 30 秒版

AI Agent 是一个以目标为导向的大模型应用系统。它不只是回答文本，而是能基于用户目标进行规划、调用工具、读取外部知识、维护状态，并根据执行结果继续决策。核心组成一般包括 LLM、Tools、State/Memory、Planner、Executor 和 Guardrails。

### 2 分钟版

普通 Chatbot 通常是用户问、模型答，流程比较线性。Agent 更强调“目标驱动”和“多步执行”：模型先理解目标，再判断是否需要检索知识或调用工具，拿到观察结果后更新状态，继续下一步，直到完成任务或触发终止条件。

生产里的 Agent 不能完全放任模型自由发挥。通常要加工具白名单、参数校验、最大步数、超时、权限、审计、人工确认和 trace。复杂场景会用 LangGraph 这类图工作流，把状态、节点、分支和循环显式化。

### 项目版

在我的项目里，Agent 不是单纯聊天入口，而是一个任务编排层。比如客服场景中，我会把它拆成意图识别、知识库检索、订单查询、结果生成、人工确认和工单创建几个节点。查询类工具可以自动执行，写操作必须二次确认。这样既保留了 Agent 的灵活性，也能控制风险。

## 2. LangChain 是什么

### 30 秒版

LangChain 是一个大模型应用开发框架，封装了模型调用、Prompt、Retriever、VectorStore、Tool、Agent、OutputParser、Callback 和 Runnable 等组件，常用于快速搭建 RAG、工具调用和 Agent 应用。

### 2 分钟版

LangChain 的价值在于把 LLM 应用里的常见模块标准化。例如 RAG 里需要 document loader、text splitter、embedding、vector store、retriever、prompt、model 和 parser；Agent 里需要 tool schema、模型决策、工具执行和中间结果回填。LangChain 提供统一抽象，可以快速集成不同模型、向量库和工具。

但生产中不能盲目依赖框架。简单链路可以用 LCEL/Runnable 组合，复杂 Agent 更适合 LangGraph 或自定义状态机，因为状态、分支、恢复、人工确认和观测会更明确。

### 项目版

我会把 LangChain 当作组件库而不是黑盒。比如 RAG 链路里用它封装 retriever、prompt 和 parser；工具调用里用 tool schema 管理参数；但复杂流程会拆成显式节点，避免所有逻辑藏在一个 AgentExecutor 循环里。

## 3. LangGraph 和 LangChain Agent 的区别

### 30 秒版

LangChain Agent 更像封装好的工具调用循环，适合简单 Agent；LangGraph 把流程表达成有状态图，节点、边、条件分支、checkpoint 和人工介入都更明确，更适合复杂生产 Agent。

### 2 分钟版

AgentExecutor 的特点是使用方便，但循环、终止条件和状态流转相对隐式。复杂业务里经常需要多阶段流程、异常处理、人工审批、失败恢复和可观测性，这时隐式循环会难维护。

LangGraph 的核心是 State、Node、Edge 和 Conditional Edge。每个节点负责一个明确步骤，比如检索、调用工具、校验、生成、人工确认；状态在节点间传递；条件边根据状态决定下一步。配合 checkpointer 可以恢复长任务，也方便调试回放。

### 项目版

如果是“查天气、查订单”这种简单工具调用，我可以用 LangChain Agent 快速实现。如果是客服工单、数据分析、代码修改这类多步骤任务，我会优先用 LangGraph，把流程拆成 router、retrieve、tool_call、validate、human_review、finalize 等节点，便于控制和排查。

## 4. 什么是 RAG

### 30 秒版

RAG 是检索增强生成。它先从外部知识库召回与问题相关的内容，再把这些内容放进 Prompt，让大模型基于证据回答。RAG 适合接入私有知识、更新频繁的知识和需要引用溯源的场景。

### 2 分钟版

RAG 分离线和在线两条链路。离线侧做文档解析、清洗、切分、embedding、入库和索引；在线侧做 query rewrite、向量/BM25/混合召回、metadata filter、rerank、上下文拼接、答案生成和引用校验。

RAG 不是把文档塞给模型那么简单。效果主要受文档质量、chunk 策略、embedding 模型、召回策略、rerank、上下文构造和 Prompt 约束影响。线上还要关注权限、延迟、成本、更新一致性和评估指标。

### 项目版

在知识库问答项目中，我会把 RAG 做成两层：离线索引构建和在线检索生成。离线保留 doc_id、chunk_id、page、section、tenant_id、permission 等元数据；在线先做问题改写和混合召回，再用 reranker 重排，最后要求模型基于证据回答并输出引用。

## 5. RAG 召回不准怎么办

### 30 秒版

我会按链路排查：数据解析是否正确、chunk 是否合理、embedding 是否适合领域、query 是否需要改写、top_k 是否合适、是否需要混合检索和 rerank、metadata filter 是否过严，以及评测集是否覆盖真实问题。

### 2 分钟版

召回不准不能只调 top_k。首先看数据侧，PDF、表格、标题层级和元数据有没有丢；然后看切分，小 chunk 可能缺上下文，大 chunk 可能噪声大；再看 query，用户问题可能省略上下文，需要 rewrite 或多查询扩展。

检索策略上，向量检索适合语义相似，BM25 适合关键词、编号、错误码和专有名词，所以企业知识库常用 hybrid search。粗召回后再用 reranker 提升排序。最后用 Recall@K、MRR、NDCG 和人工标注集做闭环评估。

### 项目版

我会先从线上 badcase 建评测集，把问题、期望文档和实际召回记录下来。然后逐项调整 chunk、embedding、hybrid 权重、rerank 和过滤条件。比如制度文档里章节结构很重要，我会采用 parent-child chunk，小 chunk 用来召回，大段落或父章节用来生成。

## 6. RAG 为什么还会幻觉

### 30 秒版

RAG 只是给模型补充上下文，不保证模型一定正确使用。召回错误、上下文噪声、问题超范围、Prompt 约束不足、引用校验缺失都会导致幻觉。

### 2 分钟版

幻觉可能来自两个阶段：检索阶段没有拿到正确证据，或生成阶段没有忠实使用证据。检索问题要通过 hybrid search、rerank、query rewrite 和评测集优化；生成问题要在 Prompt 中要求基于证据回答、无证据说不知道、输出引用，并做 groundedness/citation 检查。

高风险业务不能只靠模型自觉。需要规则校验、人工审核、答案置信度、拒答策略和线上反馈闭环。

### 项目版

在项目里我会把“无依据回答”当成核心指标。回答时必须附引用，引用 chunk 要能回溯到文档页码或章节。如果检索分数低、rerank 低或者上下文没有直接证据，就让模型拒答或转人工，而不是硬编答案。

## 7. Prompt Engineering 是什么

### 30 秒版

Prompt Engineering 是通过设计系统指令、任务说明、上下文、示例、输出格式和约束来控制模型行为。它成本低、迭代快，但只是软约束，不能替代权限和安全机制。

### 2 分钟版

一个好的 Prompt 一般包含角色、任务、输入上下文、边界条件、输出格式和示例。RAG 场景要明确“只能基于资料回答”；工具调用场景要明确每个工具的使用条件；结构化输出场景要配合 schema 和解析校验。

Prompt 的局限也很明显：容易受注入攻击影响，对复杂状态管理无能为力，也不能保证安全。因此生产中要结合 structured output、tool schema、权限系统和后处理校验。

### 项目版

我会把 Prompt 版本化管理，每次变更记录版本和效果指标。比如知识库问答中，Prompt 会要求基于证据回答、无依据拒答、输出引用；同时后端会校验引用是否来自本次召回，避免模型编造来源。

## 8. Tool Calling 是什么

### 30 秒版

Tool Calling 是让模型根据用户意图选择外部工具，并生成结构化参数；应用层负责校验、鉴权和执行工具，再把结果返回给模型。模型负责决策，真正执行必须由系统控制。

### 2 分钟版

工具调用的关键是 schema 和治理。schema 要包括工具名、描述、参数类型、必填字段和返回结构。工具描述要清楚说明适用场景，避免多个工具语义重叠。

执行前要做参数校验、权限检查、限流、超时和审计。对写操作、删除、发邮件、下单这类高风险动作，还要加人工确认、幂等 key 和回滚策略。

### 项目版

比如订单客服 Agent 里，查询订单可以自动调用，但修改地址或提交退款必须先让用户确认。模型输出参数后，后端会用 Pydantic/schema 校验，再检查用户是否有订单权限，最后执行工具并记录 tool_call trace。

## 9. 微调和 RAG 怎么选

### 30 秒版

如果问题是模型缺少外部知识，尤其知识频繁更新，优先 RAG；如果问题是模型输出风格、格式、任务模式不稳定，并且有高质量样本，可以考虑微调。

### 2 分钟版

RAG 不改变模型参数，适合私有知识库、实时知识和需要引用溯源的场景。微调会改变模型行为分布，适合稳定任务，比如分类、抽取、客服话术、格式遵循和领域风格。

两者可以结合：RAG 提供最新知识，微调让模型更会使用上下文、更稳定输出业务格式，或者微调 embedding/reranker 提升检索质量。但不能指望微调记住频繁变化的数据库。

### 项目版

如果公司制度每周更新，我不会用微调记知识，而是用 RAG 做增量索引。如果客服回复总是不符合固定话术，我会先用 Prompt 和 few-shot，仍不稳定再用高质量对话样本做 SFT 或 LoRA。

## 10. MCP 是什么

### 30 秒版

MCP 是 Model Context Protocol，是 AI 应用连接外部工具、资源和 Prompt 的标准协议。它让不同 AI 客户端能用统一方式发现和调用 MCP server 暴露的能力。

### 2 分钟版

MCP 的基本角色包括 Host、Client 和 Server。Server 可以暴露 tools、resources、prompts 等能力，Client 负责和 Server 通信，Host 是承载 AI 应用的环境。MCP 使用 JSON-RPC 风格消息，常见传输包括 stdio 和 Streamable HTTP。

MCP 不是 OpenAPI 的替代品。OpenAPI 描述 HTTP API，RPC 是远程调用抽象，MCP 是面向 AI 应用的上下文/工具连接协议。一个 MCP server 内部可以包装 OpenAPI、RPC、数据库、文件系统或 SaaS。

### 项目版

如果我要做企业内部工具平台，我会把常用系统，比如工单、知识库、代码仓库、数据库查询，包装成 MCP server。Agent 客户端通过 MCP 发现工具，但实际执行仍要经过公司鉴权、权限过滤、审计和用户确认。

## 11. Python asyncio 适合什么场景

### 30 秒版

asyncio 适合 IO 密集型并发，比如调用模型 API、向量库、数据库和外部 HTTP 服务。它通过 await 在等待 IO 时让出事件循环，提高并发吞吐，但不适合 CPU 密集计算。

### 2 分钟版

LLM 应用大量时间花在网络 IO 上，因此 async HTTP client、连接池、超时、并发限制和流式响应很重要。CPU 密集任务，比如大规模文档解析、本地 embedding、rerank 推理，不能直接放在事件循环里，否则会阻塞其他请求。

对于 CPU 密集任务，可以用进程池、任务队列、独立推理服务或 GPU batch。对于阻塞 SDK，可以用线程池包一层，避免阻塞 async 服务。

### 项目版

在 FastAPI 服务里，我会把模型调用、检索、rerank 服务调用写成 async，并设置超时和并发信号量。文档入库这种重任务则走后台队列，避免影响在线问答接口。

## 12. OpenAPI、RPC、MCP 的关系

### 30 秒版

OpenAPI 描述 HTTP API，RPC 是远程过程调用抽象，MCP 是 AI 应用连接工具、资源和 Prompt 的协议。MCP 可以把 OpenAPI、RPC、数据库或文件系统包装成模型可用的工具服务。

### 2 分钟版

OpenAPI 的核心是 paths、methods、parameters、requestBody、responses 和 schemas，适合描述 RESTful API，也能生成 SDK 或工具 schema。RPC 更像调用远程函数，gRPC/Thrift/JSON-RPC 常用于内部服务。MCP 则站在 AI 应用视角，定义工具发现、资源读取、Prompt 获取和工具调用。

因此三者不是互斥关系，而是不同层次：OpenAPI/RPC 描述或承载业务接口，MCP 把这些能力统一暴露给 Agent。

### 项目版

如果公司已有大量 OpenAPI，我不会直接全部丢给模型，而是筛选安全的接口，改写工具描述，简化 schema，加鉴权和审计，再包装成 MCP server 或 LangChain tools 供 Agent 调用。
