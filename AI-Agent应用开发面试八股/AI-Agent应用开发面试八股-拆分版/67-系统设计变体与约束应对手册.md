# 67-系统设计变体与约束应对手册

> 目标：当面试官在系统设计题里追加“多租户、权限、低延迟、高并发、私有化、成本限制、强一致、强审计”等约束时，能从原架构平稳切换到约束版架构，而不是重新画一套图。

适用场景：

- 二面/三面系统设计题：企业知识库、智能客服 Agent、数据分析 Agent、工具平台、模型网关。
- 项目深挖：面试官问“如果 QPS 提升 10 倍怎么办”“如果必须私有化怎么办”“如果不能泄露权限怎么办”。
- 主管面：考察技术判断、风险意识、成本意识和上线治理。

和其他文件的关系：

- `14-系统设计图与伪代码.md`：准备基础架构。
- `32-P2系统设计平台加分版.md`：准备平台化能力。
- `51-系统设计白板讲解脚本.md`：练 8-12 分钟完整讲解。
- `60-技术选型与取舍防守手册.md`：解释为什么这么选。
- 本文件：处理“同一道系统设计题被追加约束”的临场变体。

## 1. 通用答题框架

系统设计题被加约束时，不要立刻重画架构。先把原架构稳住，然后说明约束影响哪几层。

通用框架：

```text
原始目标
  -> 新增约束
  -> 影响链路
  -> 模块调整
  -> 指标验证
  -> 降级兜底
```

现场话术：

> 我先不完全推翻原架构，而是在原来的接入层、检索层、工具层、模型层和治理层里，找出这个约束影响最大的地方，然后逐层调整。

> 这个约束本质上优先影响三件事：数据边界、调用链路和失败兜底。我会先保证正确性，再考虑延迟和成本。

答题顺序：

1. 复述原题：我理解原目标是解决什么业务问题。
2. 识别约束：现在新增的核心约束是什么。
3. 判断影响层：是影响数据、检索、工具、模型、权限、观测，还是部署。
4. 给出调整：每层只说最关键的 1-2 个动作。
5. 给出指标：怎么判断调整有效。
6. 给出兜底：异常、超时、低置信度、权限失败时怎么处理。

## 2. 约束到架构层的映射

| 面试官追加约束 | 优先影响层 | 答题关键词 |
|---|---|---|
| QPS 提升 10 倍 | 接入层、检索层、模型层 | 缓存、限流、队列、异步、横向扩展、降级 |
| 延迟必须 2 秒内 | 检索层、rerank、模型层 | topK 控制、并行调用、小模型、缓存、流式输出 |
| 成本降低 50% | 模型层、上下文层、缓存层 | 模型路由、prompt 压缩、语义缓存、批处理、限额 |
| 必须权限隔离 | 数据层、检索层、工具层 | tenant_id、metadata filter、RBAC、ABAC、审计日志 |
| 必须私有化部署 | 部署层、模型层、向量库 | 本地模型、内网工具、离线镜像、数据不出域 |
| 结果不能出错 | 决策层、工具层、人工审核 | 强规则、人工确认、拒答、回滚、审计 |
| 文档实时更新 | 数据管道、索引层 | 增量索引、版本号、CDC、队列、重建任务 |
| 引用必须可信 | 检索层、生成层、评测层 | citation、片段 ID、出处校验、无引用不回答 |
| 工具经常失败 | Tool 层、Agent 状态机 | timeout、retry、fallback、幂等、人工接管 |
| 多业务接入 | 平台层、协议层 | OpenAPI、MCP、工具注册、schema 校验、权限分级 |
| 合规要求强 | 治理层、日志层 | 脱敏、审计、留痕、数据分级、审批 |

速背句：

> 系统设计变体不要只说“加缓存、加限流”。要说清楚约束影响哪条链路、改哪个模块、用什么指标验证、失败时怎么兜底。

## 3. 企业知识库 RAG 题目变体

基础题：

> 设计一个企业内部知识库问答系统，支持员工提问，并返回带引用的答案。

基础架构：

```text
文档接入 -> 清洗切分 -> embedding -> 向量库/倒排索引
用户问题 -> query rewrite -> hybrid search -> rerank -> LLM answer -> citation -> 反馈评测
```

### 3.1 变体：多租户和权限隔离

面试官问法：

- 如果不同部门只能看到自己的文档怎么办？
- 如果同一个知识库服务多个客户，怎么做隔离？
- 如果用户没有权限但检索到了相关内容怎么办？

回答重点：

1. 文档入库时打上 `tenant_id`、`department_id`、`doc_acl`、`security_level` 等 metadata。
2. 检索时先做用户身份解析，再把权限条件下推到 hybrid search 和向量检索。
3. rerank 和生成阶段不能重新放大越权片段，只允许使用权限过滤后的候选。
4. citation 阶段校验引用文档权限，发现无权限片段直接剔除或拒答。
5. 日志里记录 user、tenant、query、命中文档、权限过滤结果，用于审计。

示例话术：

> 多租户 RAG 的关键不是只在应用层判断权限，而是把权限下推到检索阶段。否则模型即使最后不展示原文，也可能在答案里泄露被召回的内容。

常见扣分点：

- 只说“后端判断权限”，没有说明向量检索如何过滤。
- 权限只作用在文档列表页，不作用在问答召回。
- 没有审计日志，出问题后无法追踪越权链路。

### 3.2 变体：文档实时更新

面试官问法：

- 文档更新后，多久能被问答系统感知？
- 如果旧索引和新索引同时存在，怎么避免答案引用旧内容？
- 大文件重建索引很慢怎么办？

回答重点：

1. 文档接入走事件驱动：上传、修改、删除触发消息队列。
2. 切分结果带 `doc_version` 和 `chunk_version`。
3. 增量更新优先，只重算变更 chunk 的 embedding。
4. 删除文档时做软删除和索引 tombstone，避免旧 chunk 被召回。
5. 查询时优先取最新版本，引用时展示版本和更新时间。

示例话术：

> 实时更新的难点不是重新 embedding，而是版本一致性。我要保证检索、rerank、引用展示看到的是同一个版本视图。

### 3.3 变体：引用强可信

面试官问法：

- 如何保证答案一定有出处？
- 如果模型编了一个引用怎么办？
- 如果召回片段相关但不能支撑结论怎么办？

回答重点：

1. 生成 prompt 要约束“只基于给定片段回答”。
2. 每个 chunk 带 doc_id、chunk_id、页码、段落号。
3. 生成后做 citation verifier，检查答案中的关键断言是否能被引用片段覆盖。
4. 低覆盖率时降级为“没有足够资料支撑”，不强行回答。
5. 评测集里单独维护 citation accuracy、faithfulness、answer relevance。

短答模板：

> 我会把引用作为答案质量的一等指标，而不是 UI 装饰。没有可验证引用的结论，要么删掉，要么改成不确定表达。

### 3.4 变体：低延迟

面试官问法：

- 用户要求 2 秒内返回首字怎么办？
- rerank 很慢怎么办？
- 多路检索会不会拖慢？

回答重点：

1. query rewrite、向量检索、关键词检索尽量并行。
2. topK 分层：召回多一点，rerank 少一点，最终给模型更少上下文。
3. 热门问题做语义缓存和答案缓存。
4. 首字延迟用流式输出优化，完整答案质量用后台校验补充。
5. 超时策略：超过阈值跳过 rerank 或降级到关键词检索。

示例话术：

> 低延迟不是简单删掉 rerank，而是把链路拆成可并行、可超时、可降级的几个阶段。

### 3.5 变体：成本受限

面试官问法：

- 如果调用大模型成本太高怎么办？
- 如果每天有大量重复问题怎么办？
- 如何让成本降低一半？

回答重点：

1. Query 分类：简单 FAQ 用小模型或模板，复杂问题才用大模型。
2. 语义缓存：相似问题复用答案，但要校验文档版本。
3. 上下文压缩：控制 chunk 数量和长度，减少 token。
4. 模型路由：按问题难度、用户等级、业务风险选择模型。
5. 成本看板：按 tenant、业务线、模型、功能统计 token 和费用。

速背句：

> 成本优化要从流量分层、缓存复用、上下文压缩、模型路由和配额治理一起做，不能只说换便宜模型。

### 3.6 变体：表格、PDF、OCR 多格式

面试官问法：

- PDF 表格问答怎么做？
- 扫描件合同怎么处理？
- 文档结构复杂，普通切分会丢上下文怎么办？

回答重点：

1. 按格式选择解析器：PDF、Office、HTML、图片 OCR 分开处理。
2. 保留版面结构：标题层级、表格行列、页码、图注。
3. 表格问答可以结构化入库，复杂计算交给 SQL/Pandas 工具。
4. OCR 结果带置信度，低置信度片段不能直接作为强证据。
5. 评测集单独覆盖表格、跨页、扫描件、公式和图片说明。

## 4. 客服 / 业务流程 Agent 题目变体

基础题：

> 设计一个智能客服 Agent，能回答问题、查询订单、办理退款，并在复杂场景转人工。

基础架构：

```text
用户消息 -> 意图识别 -> 状态管理 -> RAG/业务工具 -> 风险判断 -> 回复/执行 -> 人工接管 -> 日志评测
```

### 4.1 变体：高风险写操作

面试官问法：

- Agent 能不能直接退款？
- 如果模型误调用取消订单接口怎么办？
- 写操作如何防止越权和误操作？

回答重点：

1. 工具按风险分级：只读、低风险写、高风险写。
2. 高风险写操作必须二次确认，必要时人工审批。
3. Tool schema 明确必填字段、权限范围和幂等键。
4. 执行前做规则校验，不把业务规则完全交给模型判断。
5. 执行后记录审计日志，支持回滚或补偿。

标准回答：

> 我不会让模型直接拥有无限制写权限。模型负责理解意图和生成候选动作，真正执行前要经过权限、规则、确认和审计。

### 4.2 变体：人工接管

面试官问法：

- 什么情况下转人工？
- 转人工时上下文怎么传？
- 人工接管后 Agent 还能继续参与吗？

回答重点：

1. 转人工触发条件：低置信度、高风险、用户情绪强烈、多次失败、投诉、合规场景。
2. 接管包包括用户问题、历史对话、已查证据、已调用工具、失败原因、建议处理方向。
3. 接管后 Agent 可作为坐席辅助，但不直接回复用户。
4. 转人工指标包括转人工率、一次解决率、平均处理时长、用户满意度。

### 4.3 变体：工具失败或超时

面试官问法：

- 订单接口超时怎么办？
- 工具返回脏数据怎么办？
- Agent 一直重试会不会造成事故？

回答重点：

1. 每个工具配置 timeout、retry、熔断、fallback。
2. 写操作必须幂等，避免重复退款、重复取消。
3. 工具失败要进入状态机的失败分支，不让模型自由发挥。
4. 用户侧回复要透明：查询失败、稍后重试、转人工。
5. 监控工具成功率、P95 延迟、错误码分布。

### 4.4 变体：多轮上下文污染

面试官问法：

- 用户上一轮说的内容会不会影响下一轮？
- Prompt injection 怎么防？
- 多轮对话里如何确认当前任务？

回答重点：

1. 对话状态结构化：当前任务、槽位、用户身份、可用工具、风险级别。
2. 历史消息不全部塞进 prompt，先摘要和筛选。
3. 工具调用前重新确认关键槽位和当前意图。
4. 对用户输入中的指令进行分层，不能覆盖系统策略和工具权限。
5. 对高风险操作做显式确认：“你是否确认取消订单 X？”

### 4.5 变体：高并发客服高峰

面试官问法：

- 大促期间咨询量暴涨怎么办？
- 模型服务被打满怎么办？
- 如何保证核心用户体验？

回答重点：

1. 接入层限流和排队，区分普通咨询和高价值/高风险咨询。
2. FAQ、物流查询等高频问题走缓存或规则引擎。
3. 模型网关做配额、降级、fallback。
4. 工具层做连接池、熔断、读写隔离。
5. 用户体验上给出排队提示、预计等待时间和转人工入口。

### 4.6 变体：实时语音 / 多模态 Agent

面试官问法：

- 如果客服 Agent 从文字聊天变成实时语音，架构怎么改？
- 如何处理用户打断、ASR 错误和低延迟？
- 语音里触发高风险工具时怎么确认？

基础链路：

```text
Audio In -> VAD/ASR -> Turn State -> Realtime LLM
  -> Tool Policy / Tool Gateway
  -> TTS / UI Response
  -> Trace / Eval / Human Handoff
```

回答重点：

1. 接入层支持流式音频、VAD、ASR partial/final transcript。
2. 状态层按 `turn_id` 维护当前轮次、打断状态、已确认动作和未完成工具。
3. 低延迟优先优化首响：ASR 流式、模型流式、工具预取、小模型路由。
4. 用户 barge-in 时取消当前 TTS，冻结未确认工具动作，重新进入当前 turn。
5. ASR 低置信度、噪声大、多模态证据冲突时先澄清或转人工。
6. 高风险动作必须二次确认，确认文本要回显关键参数。
7. trace 记录 partial/final、confidence、barge-in、tool_action、approval_id、latency。

示例话术：

> 实时语音 Agent 的难点不是把文字 Agent 接上 ASR，而是低延迟、打断恢复和安全确认。语音转写有不确定性，所以高风险动作不能只凭一次识别结果执行，必须结合置信度、参数回显和二次确认。

评测指标：

| 指标 | 含义 |
|---|---|
| First Response Latency | 首响延迟 |
| Barge-in Recovery Rate | 打断后恢复成功率 |
| ASR Clarification Rate | 低置信度澄清率 |
| Unsafe Action Block Rate | 高风险动作拦截率 |
| Turn Trace Completeness | turn_id、转写、工具、确认是否完整 |

### 4.7 变体：长任务 Agent 作业系统

面试官问法：

- Agent 要跑 10 分钟生成报告，不能一直占着 HTTP 请求怎么办？
- 用户中途取消任务怎么办？
- 任务失败后怎么从中间恢复，而不是从头重跑？

基础链路：

```text
Submit Job -> Job Store -> Queue -> Worker / Agent Runtime
  -> Checkpoint Store -> Event Stream / Status API
  -> Cancel / Resume / Human Approval
  -> Trace / Cost / Eval
```

回答重点：

1. HTTP 请求只负责提交 job，返回 `job_id`，执行放到后台 worker。
2. job 表记录 `tenant_id、status、current_step、checkpoint_id、cost_budget、deadline、cancel_requested、error_code`。
3. 每个关键节点写 checkpoint，失败后按 checkpoint 恢复。
4. 用户取消不是直接 kill；先标记 `cancel_requested`，当前 step 判断能否安全停止。
5. 高风险写操作进入 `waiting_approval`，确认前不执行。
6. 状态查询走 API，进度推送可用 SSE/WebSocket。
7. 成本和超时用 budget/deadline 控制，超限进入 failed 或人工接管。

状态机：

```text
pending -> running -> waiting_approval -> running
running -> succeeded
running -> failed
running -> cancel_pending -> cancelled
failed -> pending/resume
```

示例话术：

> 长任务 Agent 不能靠一次请求硬跑。我会把它做成作业系统：提交时生成 job_id，后台 worker 按状态机执行，每步写 checkpoint，用户可以查询进度或取消。取消时要根据当前 step 判断是否能安全停止；如果已经进入外部写操作，要走补偿或人工接管。

## 5. MCP / OpenAPI 工具平台题目变体

基础题：

> 设计一个工具接入平台，让 Agent 可以调用企业内部多个业务系统。

基础架构：

```text
工具注册 -> schema 校验 -> 权限审批 -> 工具网关 -> Agent 调用 -> 执行审计 -> 版本治理
```

### 5.1 变体：多业务工具接入

面试官问法：

- 有几十个业务系统都要接入，怎么管理？
- 每个系统接口风格不同怎么办？
- 工具太多，模型怎么选对工具？

回答重点：

1. 接入层支持 OpenAPI、RPC wrapper、MCP server、SDK adapter。
2. 工具统一抽象为 name、description、input_schema、output_schema、auth、risk_level。
3. 工具描述要可检索、可分组、可灰度。
4. 对相似工具做命名规范和示例约束，减少工具选择混淆。
5. 工具选择前可先做 tool retrieval，不把所有工具一次性塞给模型。

### 5.2 变体：工具版本兼容

面试官问法：

- 工具参数变了怎么办？
- 老 prompt 还在调用旧工具怎么办？
- 业务接口升级会不会影响 Agent？

回答重点：

1. 工具 schema 做版本号，旧版本保留一段时间。
2. Prompt、Agent 配置和工具版本绑定，灰度升级。
3. 对破坏性变更做兼容适配层，而不是直接替换。
4. 工具调用日志按版本统计成功率和错误率。
5. 下线工具前做影响分析，找出仍在调用的 Agent。

### 5.3 变体：权限和风险分级

面试官问法：

- 怎么防止 Agent 调用不该调用的工具？
- 不同用户能用的工具不同怎么办？
- 高风险工具怎么审批？

回答重点：

1. 工具按读、写、资金、隐私、外发等风险维度分级。
2. 用户身份、租户、角色、业务场景共同决定工具可见性。
3. 工具调用前做 auth check，调用后做审计。
4. 高风险工具必须 confirmation 或 human-in-the-loop。
5. 返回结果做脱敏，避免工具输出敏感字段给模型。

### 5.4 变体：Tool schema 质量差

面试官问法：

- OpenAPI 文档不规范怎么办？
- 字段描述很差，模型经常传错参数怎么办？
- 工具返回值太复杂怎么办？

回答重点：

1. 接入时做 schema lint，检查字段类型、必填项、枚举、描述。
2. 给关键工具补 examples 和反例。
3. 对复杂返回值做 output adapter，只返回模型需要的字段。
4. 工具调用失败要把错误转成模型可理解的结构化错误。
5. 用离线用例集评估 tool selection accuracy 和 parameter accuracy。

### 5.5 变体：MCP vs SDK / OpenAPI 接入

面试官问法：

- 为什么要用 MCP，不直接调 OpenAPI？
- MCP 和 OpenAPI 是什么关系？
- 什么场景没必要上 MCP？

回答重点：

1. OpenAPI 更偏 API 描述规范，解决接口文档和调用契约。
2. SDK 更适合单应用内深度集成，开发体验好但跨工具治理弱。
3. MCP 更偏模型应用与外部上下文/工具的连接协议，适合统一暴露工具、资源和上下文。
4. 企业内部如果只有少量固定接口，OpenAPI wrapper 可能够用。
5. 多工具、多客户端、多 Agent、多权限治理时，MCP 的统一接入和发现能力更有价值。

短答：

> MCP 不是替代 OpenAPI，而是可以把 OpenAPI、数据库、文件、内部系统等能力，以更适合模型应用消费的方式暴露出来。

## 6. 模型网关题目变体

基础题：

> 设计一个模型网关，支持多模型接入、路由、鉴权、限流、成本统计和灰度。

基础架构：

```text
业务方 -> 模型网关 -> 鉴权/限流 -> 路由策略 -> 模型供应商/私有模型
                      -> 日志/成本/评测/灰度/fallback
```

### 6.1 变体：多模型路由

面试官问法：

- 怎么决定用哪个模型？
- 不同业务要不同模型怎么办？
- 模型效果和成本怎么平衡？

回答重点：

1. 路由条件：业务线、任务类型、输入长度、风险等级、成本预算、SLA。
2. 简单任务用小模型，复杂推理用强模型。
3. 高风险任务优先稳定和可审计，低风险任务优先成本。
4. 路由策略配置化，支持灰度和回滚。
5. 评测集持续比较不同模型效果。

### 6.2 变体：SLA 和高可用

面试官问法：

- 某个模型供应商挂了怎么办？
- 怎么保证线上稳定性？
- 模型超时如何处理？

回答重点：

1. 多供应商或多区域部署，避免单点。
2. 网关层统一 timeout、retry、circuit breaker。
3. fallback 模型要提前评测，不是临时乱切。
4. 关键业务有降级答案或人工处理方案。
5. 监控 P50/P95/P99、错误率、限流率、fallback 率。

### 6.3 变体：Prompt / Model 灰度

面试官问法：

- 新 prompt 怎么上线？
- 换模型怎么评估风险？
- 如何回滚？

回答重点：

1. prompt、模型、参数、工具版本作为配置版本管理。
2. 离线评测先过基础集、bad case 集、业务核心集。
3. 小流量灰度，按业务、租户或用户分桶。
4. 对比指标包括准确率、拒答率、幻觉率、延迟、成本、投诉。
5. 异常时一键回滚到上一稳定版本。

### 6.4 变体：敏感数据和私有化

面试官问法：

- 用户数据能不能发到外部模型？
- 私有化客户怎么部署？
- 日志里能不能存 prompt？

回答重点：

1. 数据分级：普通、内部、敏感、强敏感。
2. 敏感数据进入模型前做脱敏或走私有模型。
3. 私有化部署考虑模型、向量库、日志、对象存储、权限系统都在客户内网。
4. 日志可存摘要、hash、脱敏文本，避免明文长期保存。
5. 合规场景保留审计链路和数据删除机制。

## 7. 约束速查表

| 约束 | 第一反应 | 架构调整 | 指标 |
|---|---|---|---|
| QPS 提升 10 倍 | 先保护核心链路 | 限流、缓存、异步队列、水平扩展、读写隔离 | QPS、P95、错误率、降级率 |
| 延迟 2 秒内 | 先降低首字延迟 | 并行检索、减少 rerank、流式输出、小模型路由 | TTFT、P95、命中率 |
| 成本降低 50% | 先流量分层 | 缓存、小模型、上下文压缩、配额、批处理 | 单次成本、token、缓存命中率 |
| 权限隔离 | 先下推权限 | metadata filter、RBAC、租户隔离、审计 | 越权率、权限过滤命中 |
| 不能出错 | 先提高决策门槛 | 规则校验、人工确认、拒答、回滚 | 误操作率、人工确认率 |
| 私有化 | 先明确数据边界 | 本地模型、内网部署、离线依赖、可观测自建 | 数据出域次数、部署成功率 |
| 文档实时更新 | 先保证版本一致 | 增量索引、版本号、软删除、重建队列 | 索引延迟、旧版本召回率 |
| 引用可信 | 先证据约束 | citation verifier、无引用拒答、片段 ID | 引用准确率、faithfulness |
| 工具失败 | 先状态机收敛 | timeout、retry、熔断、fallback、幂等 | 工具成功率、重试率、补偿率 |
| 多业务接入 | 先统一契约 | 工具注册、schema lint、权限分级、版本治理 | 接入周期、调用成功率 |

## 8. 面试现场常用话术

### 8.1 面试官突然加 QPS

> 如果 QPS 提升 10 倍，我会先判断瓶颈是在检索、模型还是业务工具。RAG 场景通常模型调用和 rerank 比较重，所以我会先做语义缓存、topK 控制、并行检索和模型路由；接入层再做限流和排队，避免把下游模型和向量库打穿。

### 8.2 面试官突然加权限

> 权限隔离我会从数据入库开始做，而不是只在答案展示层做。文档 chunk 带 tenant 和 ACL，检索时权限条件下推，生成和引用阶段只使用授权片段，最后用日志审计整个链路。

### 8.3 面试官突然加低成本

> 成本约束下我会先做流量分层：简单问题走缓存、小模型或规则，复杂问题再走强模型；同时压缩上下文、控制 topK，并按租户和业务线做成本看板和配额。

### 8.4 面试官突然加“不能错”

> 如果业务要求不能错，我不会把系统设计成完全自动执行，而是把模型放在建议和信息抽取的位置。真正的高风险动作要经过规则校验、用户确认或人工审批，执行后保留审计和回滚能力。

### 8.5 面试官突然加私有化

> 私有化首先要明确数据不能出客户域，所以模型、向量库、对象存储、日志和权限系统都要能内网部署。外部模型可以作为可选能力，但默认链路要支持本地模型和离线依赖。

### 8.6 面试官质疑“你这个太复杂”

> 如果是 MVP，我会先保留最小闭环：接入、检索、生成、引用和日志。权限、评测、灰度、成本看板可以按风险逐步增强。但如果是企业生产环境，权限和审计不能后补太晚，否则后面改造成本很高。

## 10. 实时语音 / 多模态 Agent 白板卡

这张卡用于二面系统设计主答；`4.6` 是客服题追加实时语音约束时的变体回答。

题目：

> 设计一个实时语音 Agent，支持语音输入、低延迟回复、用户打断、工具调用和高风险动作确认。

白板主图：

```text
Audio Gateway
  -> VAD / Streaming ASR
  -> Turn State Store
  -> Realtime Model / Policy
  -> Tool Gateway / Action Guard
  -> TTS / UI Response
  -> Trace / Eval / Safety / Human Handoff
```

分层讲法：

| 层 | 设计重点 |
|---|---|
| Audio Gateway | 接收音频流、会话鉴权、限流、设备状态 |
| VAD / ASR | partial/final transcript、confidence、噪声处理 |
| Turn State | turn_id、barge-in、pending_action、approval_status |
| Realtime Model | 流式推理、小模型路由、上下文压缩 |
| Tool Gateway | 工具权限、风险分级、确认、幂等、审计 |
| TTS / UI | 流式播报、可取消、参数回显 |
| Governance | trace、eval gate、安全样本、人工接管 |

追问防守：

```text
实时语音不是普通 SSE。它多了音频 turn、ASR 置信度、TTS cancellation 和 barge-in。我的核心设计是把每一轮交互结构化到 turn state，高风险动作必须确认，低置信度先澄清，所有事件进入 trace，后续能按 turn_id 回放和评测。
```

## 11. 练习题

### 11.1 企业知识库

题目：

> 设计一个企业知识库问答系统，现在要求多租户隔离、2 秒内返回首字、答案必须带引用。

回答要点：

1. 多租户：metadata filter、tenant_id、ACL、引用权限校验。
2. 低延迟：并行 hybrid search、topK 控制、流式输出、语义缓存。
3. 强引用：chunk_id、页码、citation verifier、无证据拒答。
4. 指标：TTFT、引用准确率、越权率、缓存命中率。

### 11.2 客服 Agent

题目：

> 设计一个客服 Agent，现在要求能处理退款，但不能出现误退款，并且大促期间并发很高。

回答要点：

1. 退款工具高风险分级，必须二次确认或人工审批。
2. 幂等键、规则校验、审计日志、补偿机制。
3. 大促高并发：FAQ 缓存、限流排队、模型路由、工具熔断。
4. 指标：误退款率、人工确认率、P95、工具成功率。

### 11.3 工具平台

题目：

> 设计一个企业 Agent 工具平台，现在要接入几十个业务系统，并支持权限治理和版本升级。

回答要点：

1. 工具统一注册：OpenAPI、MCP、RPC adapter。
2. schema lint、examples、output adapter。
3. 工具权限按用户、租户、角色、风险等级控制。
4. 工具版本与 Agent/prompt 配置绑定，支持灰度和回滚。
5. 指标：工具选择准确率、参数准确率、调用成功率、版本错误率。

### 11.4 模型网关

题目：

> 设计一个模型网关，现在要求降低 50% 成本，同时保证核心业务 SLA。

回答要点：

1. 任务分层和模型路由：简单任务小模型，复杂任务强模型。
2. 语义缓存、上下文压缩、token 配额。
3. 多供应商 fallback，提前评测 fallback 质量。
4. 成本看板按业务线、租户、模型拆分。
5. 指标：单次成本、P95、fallback 率、核心任务成功率。

## 12. 常见失分回答

### 12.1 只会横向扩展

失分回答：

> QPS 高就加机器。

更好回答：

> 我会先定位瓶颈。如果瓶颈在模型调用，加机器不一定解决，需要缓存、路由、限流和降级。如果瓶颈在向量库，要看索引、filter、分片和 topK。如果瓶颈在工具接口，要做熔断、队列和读写隔离。

### 12.2 只会说加缓存

失分回答：

> 延迟高就加缓存。

更好回答：

> 缓存能解决高频重复问题，但不能覆盖长尾问题。我会同时做并行检索、控制候选数量、流式输出和超时降级。

### 12.3 把权限放在最后

失分回答：

> 答案返回前检查一下用户有没有权限。

更好回答：

> 权限要从文档入库、检索过滤、生成上下文、引用展示到日志审计全链路生效。只在最后检查，模型可能已经看到越权内容。

### 12.4 把模型当成业务规则引擎

失分回答：

> 让模型判断能不能退款。

更好回答：

> 模型可以理解意图和抽取信息，但退款资格、金额、时间窗口、黑名单等规则应该由确定性业务规则判断。

### 12.5 没有指标

失分回答：

> 我会优化效果。

更好回答：

> 我会拆成质量、延迟、成本、稳定性和安全指标。例如 RAG 看 answer relevance、faithfulness、citation accuracy、P95、单次成本、越权率。

## 12. 最终速背

1. 系统设计变体先别推翻原架构，先识别新增约束影响哪几层。
2. 高并发看缓存、限流、异步、横向扩展、降级和瓶颈定位。
3. 低延迟看并行、topK、rerank 控制、小模型、流式和超时策略。
4. 成本看流量分层、语义缓存、上下文压缩、模型路由和配额。
5. 权限隔离要下推到检索和工具调用，不只在 UI 或答案层判断。
6. RAG 强引用要做 chunk_id、citation verifier 和无证据拒答。
7. Agent 高风险写操作要规则校验、二次确认、人工审批、幂等和审计。
8. 工具平台要管 schema、权限、版本、灰度、调用日志和工具选择准确率。
9. 模型网关要管路由、SLA、fallback、成本、prompt/model 灰度。
10. 面试回答必须落到“模块调整 + 指标验证 + 失败兜底”，否则像背概念。
