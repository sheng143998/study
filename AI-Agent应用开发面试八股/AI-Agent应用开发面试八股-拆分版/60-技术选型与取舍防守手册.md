# 技术选型与取舍防守手册

> 目标：二面/三面被问“为什么这么选”时，能讲清收益、代价、边界和验证方式。  
> 面试官真正想听的不是“我用了某技术”，而是“我知道它解决什么问题，也知道它带来什么成本”。

## 1. 技术选型回答框架

遇到“为什么选 A，不选 B”，不要直接说 A 更好。按这个结构：

```text
业务约束
  -> 候选方案
  -> 选择理由
  -> 代价和风险
  -> 兜底方案
  -> 验证指标
```

万能回答：

```text
我不会说某个方案绝对更好，主要看场景约束。这个项目更关注 [准确率/延迟/成本/安全/可维护性]，所以我选 [方案]。它的收益是 [收益]，代价是 [代价]。为了控制风险，我会加 [兜底]，最后用 [指标] 验证。
```

高分关键词：

- 不是银弹。
- 约束优先。
- 小步验证。
- 可回滚。
- 指标闭环。

## 2. RAG vs 微调

### 2.1 什么时候选 RAG

适合：

- 知识频繁更新。
- 需要引用溯源。
- 需要权限隔离。
- 企业文档、FAQ、SOP、政策制度。
- 事实知识比回答风格更重要。

回答：

```text
这个场景我优先选 RAG，因为知识更新频繁，而且答案需要引用溯源和权限隔离。把事实知识放进检索系统更容易更新和审计，模型只负责基于证据生成。微调可以提升风格和格式，但不适合作为频繁变化事实知识的主要载体。
```

### 2.2 什么时候选微调

适合：

- 固定格式输出。
- 分类、抽取、改写。
- 领域话术风格。
- 工具调用格式稳定性。
- 小模型领域适配。

回答：

```text
如果问题不是事实知识缺失，而是模型对领域表达、输出格式或任务模式不稳定，我会考虑 SFT/LoRA。比如固定字段抽取、客服话术风格、工具调用参数格式，这些更适合微调。但事实知识仍然可以通过 RAG 保持可更新和可追溯。
```

### 2.3 取舍表

| 维度 | RAG | 微调 |
|---|---|---|
| 知识更新 | 快，更新索引即可 | 慢，需要重新训练/适配 |
| 引用溯源 | 强 | 弱 |
| 权限隔离 | 可通过 metadata 控制 | 难 |
| 风格对齐 | 中等 | 强 |
| 固定任务 | 可做但不一定稳定 | 强 |
| 成本 | 检索 + 推理成本 | 训练 + 推理成本 |
| 风险 | 检索噪声、上下文过长 | 记忆不可靠、遗忘、安全评估 |

## 3. 向量召回 vs BM25 vs 混合召回

### 3.1 什么时候只用向量召回

适合：

- 用户表达和文档表达差异大。
- 问题偏语义理解。
- 文档没有太多专有编号。

风险：

- 错误码、订单号、接口名、条款编号可能不稳定。
- embedding 模型对领域词不敏感。

### 3.2 什么时候加 BM25

适合：

- 专有名词多。
- 代码、接口、错误码、制度条款。
- 用户输入包含精确关键词。

回答：

```text
我会用混合召回而不是只用向量。向量召回解决语义相似，BM25 解决专有名词、编号、错误码和接口名。两个结果可以用 RRF 或加权融合，再进入 rerank。这样比单一路径更稳，但代价是融合和去重复杂度增加。
```

### 3.3 取舍表

| 方案 | 优点 | 缺点 | 适合 |
|---|---|---|---|
| 向量召回 | 语义匹配强 | 精确词不稳 | FAQ、自然语言问题 |
| BM25 | 精确词强、可解释 | 同义表达弱 | 条款、代码、错误码 |
| 混合召回 | 覆盖更稳 | 成本和融合复杂 | 企业知识库、客服、研发文档 |

## 4. Rerank 要不要加

### 4.1 加 rerank 的理由

适合：

- 粗召回 topK 噪声多。
- 正确片段进了候选但排序靠后。
- 对答案准确率要求高。
- 文档片段相似度高。

回答：

```text
如果正确证据能进候选但排序不稳定，我会加 rerank。粗召回负责覆盖，rerank 负责精排。它能提升上下文质量，但会增加延迟和成本，所以通常只对 topN 候选重排，并配合缓存和超时控制。
```

### 4.2 不加 rerank 的理由

适合：

- 延迟极敏感。
- 文档规模小。
- topK 已经很准。
- 只是内部低风险场景。

回答：

```text
如果文档规模小、召回质量已经够，或者业务更看重低延迟，我不会第一版就上 rerank。可以先通过评测看 Recall@K 和答案质量，如果发现正确证据排序靠后，再接 rerank。
```

## 5. LangChain vs LangGraph vs 自研工作流

### 5.1 LangChain

适合：

- 线性 RAG。
- 简单 chain。
- 快速集成模型、Prompt、Retriever、Tool。

不适合：

- 多分支复杂状态。
- 长流程恢复。
- 人工接管复杂。

### 5.2 LangGraph

适合：

- 多步 Agent。
- 状态显式管理。
- 条件分支。
- checkpoint。
- human-in-the-loop。
- 失败回放。

回答：

```text
如果只是线性 RAG，我用 LangChain 或普通代码就够；如果是多步 Agent，有状态、分支、工具失败和人工接管，我会选 LangGraph。它的价值是把状态和流程显式化，方便 checkpoint、回放和观测。代价是抽象复杂度更高，不适合所有简单场景。
```

### 5.3 自研工作流

适合：

- 流程强确定。
- 企业已有工作流引擎。
- 对可控性和审计要求极高。
- 不希望引入框架依赖。

回答：

```text
高风险业务我不一定会用自由 Agent，而是用显式工作流或状态机。模型只负责意图识别、参数补全和文本生成，真正的业务流转由工作流控制。这样牺牲一些灵活性，但安全性、可测性和审计更好。
```

## 6. Agent vs 固定工作流

| 维度 | Agent | 固定工作流 |
|---|---|---|
| 灵活性 | 高 | 低 |
| 可控性 | 较弱 | 强 |
| 适应复杂表达 | 强 | 弱 |
| 审计和测试 | 较难 | 较容易 |
| 高风险操作 | 需要强约束 | 更适合 |
| 开发速度 | Demo 快，生产治理复杂 | 初期慢，稳定性强 |

回答：

```text
我会把 Agent 和工作流结合，而不是二选一。用户意图理解、工具选择、参数补全可以用 Agent；高风险业务动作、状态流转和审批用固定工作流。这样既保留大模型的灵活性，又能保证关键流程可控。
```

## 7. MCP vs OpenAPI vs SDK

### 7.1 OpenAPI

解决：

- HTTP API 怎么描述。
- 路径、方法、参数、requestBody、response。

### 7.2 SDK

解决：

- 业务代码怎么方便调用能力。
- 封装鉴权、重试、错误处理。

### 7.3 MCP

解决：

- 大模型应用如何统一发现和调用 tools/resources/prompts。
- 多客户端/Agent 如何复用工具上下文。

回答：

```text
OpenAPI、SDK、MCP 不是替代关系。OpenAPI 描述已有 HTTP API；SDK 方便普通业务代码调用；MCP 面向大模型应用，把工具、资源和 Prompt 以统一协议暴露给 Agent。企业里常见做法是已有服务用 HTTP/RPC 暴露，再由工具平台包装成 Tool，最后通过 MCP 或 SDK 给 Agent 使用。
```

风险：

- MCP 不自动解决权限。
- OpenAPI 描述不等于模型能稳定调用。
- SDK 易绑定语言和工程环境。

## 8. Tool Calling vs 直接生成 JSON

### 8.1 Tool Calling

适合：

- 模型需要选择工具。
- 多工具场景。
- 需要应用层执行函数。
- 需要工具调用 trace。

### 8.2 直接结构化 JSON

适合：

- 分类、抽取、信息整理。
- 不需要调用外部系统。
- 输出结构固定。

回答：

```text
如果只是让模型按 schema 输出分类或抽取结果，Structured Output/JSON 就够；如果需要模型选择工具并生成调用参数，再由应用层执行外部动作，就用 Tool Calling。两者都依赖 schema，但 Tool Calling 更强调工具选择、执行、权限和审计。
```

## 9. SSE vs WebSocket

### 9.1 SSE

适合：

- LLM token streaming。
- 服务端单向推送。
- 实现简单。
- 浏览器支持 EventSource。

### 9.2 WebSocket

适合：

- 双向实时交互。
- 协同编辑。
- 语音/实时控制。
- 客户端需要频繁发送中断或控制消息。

回答：

```text
普通大模型文本生成我优先用 SSE，因为主要是服务端把 token 流式推给客户端，实现和运维都简单。如果需要双向实时控制，比如语音对话、协同编辑、客户端频繁中断和控制，就更适合 WebSocket。
```

风险：

- SSE 改善首 token 体验，不减少生成成本。
- 断连要取消下游模型调用或停止消费。
- WebSocket 状态管理和扩缩容更复杂。

## 10. 向量库选型

### 10.1 pgvector

适合：

- 数据量中小。
- 已经使用 PostgreSQL。
- 希望向量和业务数据一起管理。
- 简化部署。

### 10.2 Milvus / Qdrant / Weaviate

适合：

- 向量规模大。
- 检索性能要求高。
- 需要更丰富索引和过滤能力。
- 多集合、多租户、专用向量服务。

### 10.3 FAISS

适合：

- 本地实验。
- 离线检索。
- 自己管理索引和服务。

回答：

```text
向量库选型先看规模、过滤、运维和业务耦合。如果是中小规模、已有 PostgreSQL，pgvector 足够且部署简单；如果向量规模大、检索 QPS 高、需要专用索引和多租户管理，可以选 Milvus/Qdrant/Weaviate；如果只是本地实验或离线评测，FAISS 更轻。
```

## 11. 大模型 API vs 私有化模型

| 维度 | 外部 API | 私有化模型 |
|---|---|---|
| 接入速度 | 快 | 慢 |
| 模型效果 | 通常强 | 取决于模型和部署 |
| 数据合规 | 需评估 | 更可控 |
| 成本 | 按量付费 | 机器和运维成本 |
| 弹性 | 供应商承担 | 自己承担 |
| 可定制 | 有限制 | 更强 |

回答：

```text
如果是快速验证或通用能力，我会优先用成熟模型 API；如果涉及敏感数据、私有化交付、低延迟内网调用或成本可控性要求高，就考虑私有化模型。实际项目也可以混合：敏感任务走私有模型，复杂推理或低风险任务走外部强模型。
```

## 12. Prompt 优化 vs 评测平台

### 12.1 什么时候先改 Prompt

适合：

- 输出格式不稳定。
- 角色边界不清。
- 少量 bad case。
- 任务规则简单。

### 12.2 什么时候先建评测

适合：

- bad case 反复出现。
- 多业务共用。
- Prompt/模型频繁迭代。
- 需要灰度和回归。

回答：

```text
早期可以先用 Prompt 快速验证，但一旦进入多业务或准生产阶段，就应该补评测。否则每次改 Prompt 都不知道是整体变好还是只修了一个 case。评测平台的价值是让 Prompt、模型、检索策略变化都能回归和灰度。
```

## 13. 缓存要不要加

适合加：

- 热点 FAQ。
- embedding 结果。
- rerank 结果。
- 模型答案可复用且低风险。

不适合直接缓存：

- 权限敏感答案。
- 个性化答案。
- 文档频繁更新。
- 高风险工具结果。

回答：

```text
缓存能降延迟和成本，但 RAG/Agent 场景要注意权限和更新。embedding、检索候选、rerank 结果比较适合缓存；最终答案如果涉及权限、实时数据或个性化，就要谨慎。缓存 key 里要包含 tenant、permission、doc_version、prompt_version 等信息。
```

## 14. 成本 vs 准确率 vs 延迟

典型冲突：

| 优化动作 | 准确率 | 延迟 | 成本 |
|---|---|---|---|
| 增大 topK | 可能提升 | 变慢 | 增加 |
| 加 rerank | 通常提升 | 变慢 | 增加 |
| 多查询改写 | 提升召回 | 变慢 | 增加 |
| 用强模型 | 提升生成 | 变慢/不稳定 | 增加 |
| 缓存 | 不一定 | 变快 | 降低 |
| 小模型路由 | 可能下降 | 变快 | 降低 |

回答：

```text
这三个指标通常要一起看，不能只追求准确率。比如 topK 增大和 rerank 可能提升效果，但会增加延迟和 token 成本。我会先设护栏指标，比如 P95 延迟和单次成本上限，再在这个范围内优化 Recall@K、引用准确率和用户满意度。
```

## 15. 最终速背

```text
RAG vs 微调：
事实知识、引用、权限选 RAG；格式、风格、固定任务可微调。

向量 vs BM25：
语义问题靠向量；专有词、编号、错误码靠 BM25；企业知识库多用混合召回。

rerank：
候选有但排序差就加；延迟敏感或规模小可以先不上。

LangChain vs LangGraph：
线性链路用 LangChain；有状态、多分支、checkpoint 用 LangGraph。

Agent vs 工作流：
灵活理解用 Agent；高风险执行用工作流；生产常常结合。

MCP vs OpenAPI：
OpenAPI 描述 HTTP API；MCP 面向模型应用接入工具和上下文。

SSE vs WebSocket：
单向 token streaming 用 SSE；双向实时控制用 WebSocket。

向量库：
中小规模 pgvector；大规模专用向量服务 Milvus/Qdrant/Weaviate；实验 FAISS。

选型万能句：
看约束，不讲银弹；讲收益，也讲代价；给兜底，再给指标。
```
