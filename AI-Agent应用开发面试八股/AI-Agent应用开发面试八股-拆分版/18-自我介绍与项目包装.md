# 自我介绍与项目包装

> 用法：把模板里的项目细节替换成你自己的经历。面试时不要照读，要练到能自然讲出来。

## 1. 1 分钟自我介绍

### 模板

```text
面试官您好，我主要关注大模型应用开发和 AI Agent/RAG 工程落地。

我做过的核心项目是一个面向企业知识库/业务流程的智能问答与 Agent 系统，主要包括文档解析、向量检索、RAG 问答、工具调用、权限控制和日志观测几个模块。

技术上我比较熟悉 Python、FastAPI、LangChain/LangGraph、向量数据库、Prompt Engineering、Tool Calling，也了解 OpenAPI、RPC、MCP 这类工具集成方式。

我比较关注的不只是 Demo 效果，而是线上稳定性，比如召回质量、幻觉控制、工具调用安全、流式响应、成本和 trace。希望这次能结合岗位需求进一步交流。
```

### 适合场景

- 一面开场。
- 面试官时间紧。
- 简历项目不多但方向明确。

## 2. 3 分钟自我介绍

### 模板

```text
面试官您好，我的技术方向主要是大模型应用开发，重点是 RAG、AI Agent 和后端工程落地。

我最核心的项目是一个企业知识库问答/业务 Agent 系统。业务背景是内部文档、制度、工单和业务系统比较分散，人工查询效率低，所以我们希望用大模型做统一入口。

架构上分两条链路。离线侧做文档采集、解析、清洗、切分、embedding 和向量索引，同时保留 doc_id、page、section、tenant_id、permission 等元数据。在线侧先做用户鉴权和 query rewrite，再进行向量和关键词混合召回，召回后 rerank，最后把证据和引用拼进 Prompt 让模型回答。

在 Agent 部分，我把工具调用和普通问答区分开。查询类工具可以自动执行，例如订单查询、工单查询；写操作或高风险操作必须二次确认，并且工具层会做参数校验、权限检查、超时、幂等和审计。

这个项目里我主要负责 RAG 检索链路、Prompt 和工具调用治理，以及部分 FastAPI 接口和流式输出。遇到的主要难点是召回不准、上下文噪声、模型幻觉和工具调用不稳定。我们通过 hybrid search、rerank、引用校验、badcase 评测集和 trace 日志逐步优化。

我对这个方向的理解是，大模型应用的难点不只是调模型，而是把模型的不确定性纳入工程系统管理，让数据可追溯、工具可控、状态可恢复、效果可评估。
```

### 适合场景

- 技术一面/二面。
- 简历中有完整 AI 项目。
- 面试官让“详细介绍一下自己”。

## 3. 5 分钟项目介绍

### 结构

```text
业务背景 30 秒
系统架构 1 分钟
核心链路 1.5 分钟
难点与优化 1.5 分钟
结果与复盘 30 秒
```

### 模板

```text
这个项目的背景是，公司内部有大量制度文档、产品文档、历史工单和业务数据，员工或客服在处理问题时需要跨系统查询，效率比较低，也容易查错。因此我们做了一个基于 RAG 和工具调用的智能助手。

整体架构分为入口层、RAG 检索层、Agent 编排层、工具调用层和观测评估层。入口层负责鉴权、限流和会话管理；RAG 层负责知识库问答；Agent 层负责意图识别和流程编排；工具层对接订单、工单、数据库或内部 API；观测层记录 prompt、召回文档、tool call、token、延迟和用户反馈。

离线数据链路是：文档采集后做解析和清洗，然后按标题、段落和 token 递归切分，保留页码、章节、权限、版本等元数据，再生成 embedding 写入向量库，同时建立关键词索引。在线链路是：用户问题进来后先做 query rewrite 和权限过滤，然后向量召回加 BM25 混合检索，候选结果经过 reranker 排序，最后构造带引用的上下文给模型生成答案。

Agent 部分没有完全放任模型自由行动，而是做了受控流程。比如普通知识咨询走 RAG，订单状态查询走只读工具，退款或修改信息这类写操作必须先生成待确认动作，用户确认后才执行。所有工具调用都经过 schema 校验、用户权限检查、超时处理和审计记录。

项目中最大的难点有三个。第一是召回不准，我们通过 badcase 标注、调整 chunk、混合检索和 rerank 优化。第二是幻觉，我们要求答案必须基于上下文并附引用，引用会做后处理校验。第三是工具调用风险，我们把高风险工具加了人工确认和幂等 key，避免重复执行。

如果重新设计，我会进一步把 Prompt、模型、工具和检索策略都版本化，接入更系统的离线评测和 A/B 实验，并用 LangGraph 这类图工作流把状态和恢复机制做得更清晰。
```

## 4. 项目难点表达模板

### 召回不准

```text
当时遇到的问题是用户问制度细节时，系统有时召回的是同主题但不同版本或不同部门的文档，导致答案张冠李戴。

我先从 trace 中抽取 badcase，把 query、期望文档、实际召回文档和 rerank 分数记录下来。排查后发现主要有两个原因：一是 chunk 按固定长度切分破坏了章节语义，二是权限和版本元数据没有充分参与过滤。

后来我们改成按标题层级递归切分，并保留 parent-child 关系；检索时加入 tenant_id、department、version 等 metadata filter；同时引入 BM25 + vector 混合召回和 rerank。

优化后，至少在标注 badcase 集上，正确文档进入 top5 的比例明显提升，线上用户反馈里“答非所问”的情况也减少了。
```

### 幻觉

```text
幻觉问题主要表现为检索结果没有明确依据时，模型仍然会给出看似合理的答案。

我把这个问题拆成两层：第一是检索层有没有拿到证据，第二是生成层有没有忠实使用证据。检索层通过 hybrid search 和 rerank 提升相关性；生成层在 Prompt 中要求无依据就回答不知道，并强制输出引用。

后处理会校验答案中的引用编号是否来自本次召回文档，如果引用不存在或上下文没有直接证据，就触发重试或拒答。
```

### 工具调用风险

```text
工具调用风险主要在于模型可能选错工具、参数错误，或者重复执行写操作。

我的处理思路是把模型的职责限制在“提出调用意图和参数”，真正执行由后端控制。执行前做 schema 校验、权限检查、风险等级判断；查询工具可以自动执行，写操作必须用户确认。

对非幂等操作，我们会带 idempotency_key，并记录 tool_call trace，避免重复提交。工具失败时会把业务错误转成 observation，让模型解释或转人工，而不是直接暴露异常。
```

### 延迟和成本

```text
延迟主要来自 query rewrite、召回、rerank 和模型生成。我的优化思路是先做 trace，定位每一步耗时，再分别处理。

比如高频问题和 embedding 可以缓存；召回和部分工具调用可以并行；rerank 控制候选数量；简单问题走小模型，复杂问题再路由到大模型；前端使用 SSE 流式输出改善体感延迟。

成本上主要控制上下文长度、减少无效工具调用、缓存热点问题，并对不同租户设置 token quota。
```

### 不好的回答

```text
我参与了整个项目，前后端都做了一些。
```

问题：

- 太泛。
- 听不出贡献。
- 面试官无法继续追。

### 好的回答

```text
我主要负责三块：第一是 RAG 检索链路，包括文档切分、embedding 入库、向量召回和 rerank；第二是 Prompt 和输出校验，包括引用约束和 JSON 解析；第三是工具调用治理，包括 tool schema、参数校验、权限检查和 trace 日志。

其中我投入最多的是召回优化，因为最初系统经常答非所问。我通过 badcase 集把问题拆成 chunk、query、召回和排序几类，再逐项优化。
```

## 6. 面试官追问“你项目有什么指标”

### 可以准备的指标

如果有真实指标：

- 文档量。
- chunk 数。
- 日活/调用量。
- 平均延迟。
- Recall@K。
- 引用准确率。
- 用户满意度。
- 人工转接率。
- token 成本。

如果没有真实线上指标：

```text
这个项目没有大规模上线，所以我没有夸大线上指标。我们主要做了离线评测和 Demo 反馈。离线评测上，我构造了一批典型问题和期望文档，用 Recall@K 看检索效果，用人工评分看答案是否基于证据。后续如果上线，我会补充用户反馈、无答案率、平均延迟、token 成本和 badcase 闭环。
```

## 7. 面试官追问“为什么不用传统搜索”

回答：

```text
传统搜索适合关键词匹配，但用户很多问题是自然语言表达，可能和文档里的术语不一致。RAG 的价值是用 embedding 做语义召回，再让模型基于证据组织答案。

不过我不会完全抛弃传统搜索。企业知识库里有大量专有名词、编号、错误码和制度条款，BM25 反而很有效。所以我更倾向 hybrid search，而不是只用向量检索。
```

## 8. 面试官追问“为什么不用微调”

回答：

```text
这个项目的核心问题是模型缺少企业内部知识，而且知识更新比较频繁。微调不适合记这些变化快的知识，也不方便引用溯源，所以优先用 RAG。

微调更适合稳定的输出风格、格式或任务模式。如果后续发现模型总是不按客服话术或固定格式回答，可以在有高质量样本后考虑 SFT/LoRA，但知识本身仍然通过 RAG 接入。
```

## 9. 面试官追问“为什么用 LangGraph”

回答：

```text
如果只是一次性问答或简单工具调用，LangChain AgentExecutor 就够了。但我们的流程有意图路由、RAG、工具调用、人工确认、失败处理和最终生成，状态和分支比较多。

LangGraph 能把流程显式表达成节点和边，每个节点职责清楚，状态在节点之间传递。它还支持 checkpoint 和 interrupt，适合长任务恢复和 human-in-the-loop。
```

## 10. 反问问题

可以问：

1. 团队现在的大模型应用主要是 RAG、Agent，还是模型平台方向？
2. 目前线上最大的难点是效果、成本、延迟，还是安全合规？
3. 团队是否有自己的评测集和 badcase 闭环？
4. Agent 工具调用是否已经接入了权限和审计系统？
5. 这个岗位更偏业务应用落地，还是基础平台建设？

避免问：

- 加班多不多。
- 技术栈是不是很简单。
- 有没有人带。
- 我进去主要做什么小需求。
