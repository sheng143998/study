# P2 系统设计：平台加分版

> 用法：适合三面、主管面、平台岗、云厂商和大厂中台方向。  
> 覆盖 `27-P0P1P2题库扩容版.md` 中 P2 系统设计题的 187-195：模型网关、Prompt 管理、Agent 评测、RAG badcase、成本看板、工具审计、灰度、fallback、跨租户隔离。

## 1. 平台题通用答题框架

遇到平台类系统设计题，按这个顺序答：

```text
1. 目标：这个平台解决什么问题。
2. 用户：谁会用，业务方、算法、后端、运营还是安全团队。
3. 核心模块：入口、配置、执行、存储、观测、权限。
4. 数据流：请求怎么进来，结果怎么出去，中间记录什么。
5. 版本化：模型、Prompt、工具、检索策略怎么管理。
6. 安全：租户、权限、密钥、审计、脱敏。
7. 评估：指标、badcase、A/B、回归集。
8. 稳定性：限流、降级、fallback、回滚。
```

万能收束：

```text
平台的价值不是把一次调用封装起来，而是把模型、Prompt、工具、数据、评估和成本都纳入统一治理。
```

## 2. 如何做模型网关

### 目标

统一接入多个模型供应商和多种模型能力，屏蔽不同 API 差异，提供路由、限流、鉴权、观测、降级和成本统计。

### 架构

```text
业务应用
  -> Model Gateway API
     -> 鉴权 / 租户 / 配额
     -> 模型路由
     -> Provider Adapter
     -> 超时 / 重试 / 熔断
     -> 统一响应格式
     -> token / cost / latency trace
  -> OpenAI / Anthropic / Gemini / 本地模型 / embedding / rerank
```

### 核心模块

- Provider Adapter：适配不同模型 API。
- Capability Registry：记录模型支持 chat、stream、tool calling、embedding、rerank、vision。
- Routing Engine：按任务、成本、延迟、上下文长度、风险等级路由。
- Quota Manager：按租户、用户、模型限流和计费。
- Fallback Manager：模型失败时切备用模型。
- Observability：记录 token、延迟、错误率、成本。

### 面试回答

```text
我会把模型网关设计成业务层和模型供应商之间的抽象层。业务只调用统一接口，比如 chat、stream_chat、embed、rerank 和 tool_call，不直接依赖某个供应商格式。

网关内部通过 adapter 屏蔽不同模型的请求、响应、错误码和流式格式差异。路由层根据任务类型、上下文长度、是否需要 tool calling、成本预算和模型健康状态选择模型。

同时网关负责租户鉴权、限流、token 成本统计、超时、重试、熔断和 fallback。这样新增模型时只需要增加 adapter 和配置，不需要改业务链路。
```

### 高频追问

Q：如何做多模型 fallback？

A：先判断失败类型。超时、5xx、限流可以切备用模型；参数错误不该 fallback。fallback 模型要能力兼容，比如 tool calling 格式、上下文长度和输出结构。fallback 后要在 trace 中记录，方便评估质量差异。

Q：如何避免 fallback 后答案风格变化？

A：统一 Prompt 模板和输出 schema，记录模型差异，关键任务做 A/B 和人工评估。不能假设所有模型能力等价。

## 3. 如何做 Prompt 管理平台

### 目标

让 Prompt 像代码一样可管理、可测试、可灰度、可回滚。

### 架构

```text
Prompt Console
  -> Prompt Registry
     -> name / version / scenario / owner
     -> template / variables / output schema
     -> model config / tools config
     -> eval result / changelog
  -> Runtime SDK
     -> 拉取 prompt
     -> 渲染变量
     -> 记录 prompt_version
  -> Eval / A-B / Trace
```

### 核心能力

- Prompt 模板管理。
- 变量 schema。
- 版本和 changelog。
- Prompt diff。
- 输出 schema 绑定。
- 离线评测。
- 灰度发布。
- 快速回滚。
- trace 复现。

### 面试回答

```text
Prompt 管理平台的核心是版本化和评估。每个 Prompt 都应该有 name、version、适用场景、变量 schema、输出 schema、绑定模型、工具配置、owner 和 changelog。

运行时业务系统通过 SDK 拉取指定版本 Prompt，渲染变量后调用模型，并在 trace 中记录 prompt_version。这样线上 badcase 可以复现，Prompt 改动也能灰度和回滚。

上线前要跑离线评测集，比较答案质量、格式正确率、拒答率、引用准确率、token 成本和延迟。Prompt 不是写完就上线，而是配置、评测、灰度、观测的闭环。
```

### 高频追问

Q：Prompt 改动怎么评估？

A：用固定评测集回归，包括高频、长尾、无答案、权限、格式和安全样本。比较新旧版本的质量、成本和风险指标。

Q：Prompt 为什么不能只存在代码里？

A：不方便运营调整、A/B、回滚和 trace 复现。平台化后更适合多业务复用。

## 4. 如何做 Agent 评测平台

### 目标

评估 Agent 是否真的完成任务，而不是只看最终回答好不好看。

### 评测维度

| 维度 | 指标 |
|---|---|
| 任务结果 | task success rate、completion rate |
| 过程质量 | tool selection accuracy、step count、loop rate |
| 安全 | permission violation、high-risk action confirmation |
| 稳定性 | failure recovery rate、timeout rate |
| 成本 | token cost、tool call count、latency |
| 体验 | user satisfaction、manual handoff rate |

### 架构

```text
Eval Dataset
  -> 任务描述 / 初始状态 / 可用工具 / 期望结果 / 禁止行为
  -> Agent Runner
  -> Trace Collector
  -> Judge
     -> 规则评估
     -> LLM-as-judge
     -> 人工抽检
  -> Report
```

### 面试回答

```text
Agent 评测不能只看最终答案，而要看过程。比如客服 Agent 最终说“已处理”不够，还要看是否调用了正确工具、有没有越权、有没有重复调用写工具、步骤是否过多、失败后是否正确恢复。

我会构建任务级评测集，每条样本包含用户目标、初始环境、可用工具、期望结果和禁止行为。运行 Agent 后收集完整 trace，再用规则、LLM-as-judge 和人工抽检评估。

核心指标包括任务成功率、工具调用准确率、平均步骤数、循环率、人工介入率、延迟、成本和安全违规率。
```

### 高频追问

Q：怎么评估工具调用正确性？

A：看工具选择是否符合意图、参数是否正确、调用顺序是否合理、是否遵守权限和确认流程。

Q：LLM-as-judge 能不能完全替代人工？

A：不能。它适合规模化初筛，但要有人工校准集和抽检，尤其是高风险业务。

## 5. 如何做 RAG badcase 平台

### 目标

把线上问答问题沉淀成可分析、可复现、可回归的 badcase 闭环。

### badcase 分类

- 文档解析错误。
- chunk 切分错误。
- 没召回。
- 排序错误。
- 权限过滤错误。
- 上下文噪声。
- 生成幻觉。
- 引用错误。
- 拒答错误。
- 文档过期。

### 架构

```text
线上 Trace
  -> Badcase 标注
     -> query / expected docs / actual docs / answer / feedback
  -> 分类归因
  -> 策略实验
     -> chunk / embedding / hybrid / rerank / prompt
  -> 回归评测
  -> 上线灰度
```

### 面试回答

```text
RAG badcase 平台的核心是把一次错误回答拆解成可定位的问题。每条 badcase 要记录 query、用户上下文、召回 top_k、rerank 分数、最终上下文、模型答案、引用、用户反馈和期望文档。

然后按错误类型归因：如果正确文档完全没进候选，是召回问题；如果进了候选但排名低，是排序问题；如果文档在上下文里但答案错了，是生成或 Prompt 问题。

平台还要支持策略实验，比如调整 chunk、embedding、hybrid 权重、rerank 模型或 Prompt，并在固定 badcase 集上做回归。
```

### 高频追问

Q：badcase 如何变成评测集？

A：把真实问题清洗后标注 golden docs、答案要点和引用来源，加入回归集。每次策略变更都跑一遍，避免修一个坏一个。

## 6. 如何做大模型应用成本看板

### 目标

让 token、模型调用、工具调用和基础设施成本可观测、可归因、可优化。

### 指标

- input token。
- output token。
- model name。
- request count。
- average cost。
- cost by tenant/user/app。
- cache hit rate。
- tool call count。
- rerank/embedding cost。
- cost per successful task。

### 架构

```text
Model Gateway / Agent Trace / RAG Service
  -> Cost Collector
  -> Pricing Table
  -> Aggregation
     -> by tenant / app / model / prompt version / tool
  -> Dashboard
  -> Budget Alert / Quota
```

### 面试回答

```text
成本看板要能回答三个问题：钱花在哪里，哪个业务花的，花得值不值。

所以每次模型调用都要记录模型名、输入输出 token、单价、request_id、tenant_id、app_id、prompt_version 和任务结果。Agent 还要记录每个任务的总步骤数和工具调用次数。

看板上按租户、应用、模型、Prompt 版本和任务类型聚合成本，同时结合成功率和用户反馈计算 cost per successful task。超过预算时触发限流、降级或告警。
```

### 高频追问

Q：怎么降低成本？

A：模型路由、上下文压缩、缓存、减少 top_k、减少无效工具调用、小模型处理简单任务、设置 token budget。

## 7. 如何做工具调用审计系统

### 目标

让每一次工具调用都可追溯、可检查、可回放，尤其是高风险写操作。

### 需要记录

- request_id。
- session_id。
- user_id / tenant_id。
- tool_name。
- tool_version。
- arguments 摘要。
- permission result。
- risk_level。
- confirmation result。
- idempotency_key。
- start/end time。
- status/error_code。
- result 摘要。

### 面试回答

```text
工具调用审计系统的核心是记录模型为什么调用、调用了什么、谁授权、执行结果是什么。

模型生成 tool call 后，后端先做参数校验和权限校验。审计日志要记录 tool_name、参数摘要、用户、租户、权限结果、风险等级、确认状态、幂等 key、执行状态和错误码。

对退款、删除、发邮件、改配置这类高风险工具，必须能回放当时的用户请求、模型输出、确认动作和工具响应。日志要脱敏，并按租户隔离。
```

### 高频追问

Q：审计日志能不能记录完整参数？

A：要看敏感性。可以记录参数摘要和脱敏字段，敏感字段加密或不落日志。审计可追溯和隐私合规要平衡。

## 8. 如何设计 AI 应用灰度发布

### 灰度对象

- 模型版本。
- Prompt 版本。
- RAG 检索策略。
- embedding/rerank 模型。
- tool schema。
- Agent workflow。
- MCP server 版本。

### 面试回答

```text
AI 应用灰度不只是发布代码，还包括模型、Prompt、检索策略、工具 schema 和 Agent 工作流。

我会按租户、用户白名单或流量比例灰度，灰度期间监控答案质量、拒答率、幻觉率、引用准确率、工具失败率、延迟、成本和用户反馈。

每个版本都要能回滚。trace 中记录 model_version、prompt_version、retrieval_version 和 tool_version，确保 badcase 可复现。
```

### 高频追问

Q：Prompt 灰度失败怎么回滚？

A：Prompt registry 保留旧版本，运行时按配置切回旧 prompt_version。已产生的 trace 保留新旧版本对比。

### 8.1 LLMOps 发布变更单模板

面试官追问“你怎么证明灰度和回滚真的能落地”时，用变更单回答，而不是只说“支持灰度”。

```markdown
# LLMOps Change Record

- change_id:
- owner:
- change_type: prompt / model / retrieval / tool_schema / workflow / mcp_server
- target_app:
- target_tenants:
- prompt_version_before:
- prompt_version_after:
- model_version_before:
- model_version_after:
- retrieval_version_before:
- retrieval_version_after:
- tool_schema_version_before:
- tool_schema_version_after:
- eval_dataset_version:
- eval_gate_result:
- gray_strategy: whitelist / tenant / percentage
- gray_ratio:
- start_time:
- rollback_version:
- rollback_trigger:
- monitoring_metrics:
  - task_success_rate:
  - faithfulness:
  - unsafe_action_rate:
  - p95_latency:
  - token_cost:
- approval:
- postmortem_link:
```

60 秒回答：

```text
AI 应用发布变更不只发代码，还可能改 prompt、模型、检索策略、工具 schema 或 Agent workflow。每次变更我会记录 change_id、影响租户、版本前后对比、eval gate 结果、灰度比例、监控指标和回滚版本。线上 trace 绑定 change_id，bad case 出现后能知道是哪次变更引入，并一键回滚到上一稳定版本。
```

### 8.2 LLMOps 回滚单模板

回滚不是 fallback。fallback 是运行时模型或工具降级；rollback 是把已经发布的配置或版本退回上一稳定状态。

```markdown
# LLMOps Rollback Record

- rollback_id:
- related_change_id:
- owner:
- trigger:
  - eval_gate_failed:
  - unsafe_action_spike:
  - p95_latency_spike:
  - cost_spike:
  - user_complaint:
- affected_tenants:
- affected_versions:
  - prompt_version:
  - model_version:
  - retrieval_version:
  - tool_schema_version:
  - workflow_version:
  - mcp_server_version:
- rollback_to:
  - prompt_version:
  - model_version:
  - retrieval_version:
  - tool_schema_version:
  - workflow_version:
- action:
  - config_revert:
  - traffic_shift:
  - cache_invalidate:
  - eval_rerun:
- validation:
  - eval_gate_result:
  - key_metrics_after:
  - sample_trace_ids:
- postmortem_owner:
- follow_up_fix:
```

60 秒回答：

```text
回滚单关注触发条件、影响范围、回退动作和验证结果。比如 prompt_v12 灰度后 unsafe_action_rate 升高，我会用 rollback_id 关联 change_id，列出受影响租户和版本，配置回退到 prompt_v11，必要时清缓存并重跑 eval gate。回滚后用关键指标和 sample trace 验证恢复，再把根因进入 postmortem 和后续修复。
```

## 9. 如何设计多模型 fallback

### fallback 类型

- 同供应商不同模型。
- 不同供应商模型。
- 大模型降小模型。
- 跳过非关键步骤。
- 转人工。

### 面试回答

```text
多模型 fallback 要先做能力兼容判断。比如主模型支持 tool calling，备用模型也要支持类似结构化输出，否则业务链路可能断。

触发条件包括超时、限流、5xx、模型健康度下降和成本策略。fallback 时要统一错误码和响应格式，并在 trace 中记录 fallback_from、fallback_to 和原因。

但不是所有错误都该 fallback。参数错误、权限错误、用户输入不完整，应直接返回可解释错误或澄清，而不是换模型。
```

### 高频追问

Q：fallback 会不会影响答案质量？

A：会，所以要做 A/B 和质量监控。关键任务 fallback 后可增加校验或人工兜底。

## 10. 如何设计跨租户数据隔离

### 隔离层次

- 身份和权限。
- 文档和向量索引。
- 工具白名单。
- Prompt 配置。
- 模型配额。
- 缓存。
- 日志和 trace。
- 评测数据。

### 面试回答

```text
跨租户隔离要让 tenant_id 贯穿全链路。文档入库时 chunk 带 tenant_id，检索时强制 metadata filter；强隔离场景可以按租户建 collection 或索引。

工具层按租户加载工具白名单和密钥，模型调用按租户做 quota 和成本统计。缓存 key 必须包含 tenant_id 和权限版本，日志和 trace 按租户隔离并脱敏。

最重要的是不要只在生成后过滤，因为模型一旦看到无权限上下文，就已经产生泄漏风险。
```

### 高频追问

Q：metadata filter 足够安全吗？

A：取决于风险等级和向量库能力。高安全场景建议 collection 级隔离或物理隔离，metadata filter 作为应用层控制还要配合审计。

## 11. 平台题加分表达

面试官问平台题时，最好主动补一句：

```text
我会把这个平台设计成可配置、可观测、可评估、可回滚的系统。因为大模型能力变化快，如果没有版本、评测和 trace，后续问题很难定位。
```

不要只说：

```text
用一个数据库存配置，再调模型。
```

更好的收束：

```text
平台化的核心是治理复杂度：多模型、多 Prompt、多工具、多租户、多版本都要有统一管理和闭环评估。
```
