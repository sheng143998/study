# 项目答辩讲稿版

> 用法：适合二面、三面、主管面、项目答辩式深挖。目标不是背长稿，而是练到能在 5 分钟内把业务、架构、难点、结果讲完整。

## 1. 5 分钟项目主讲稿

### 适用项目

企业知识库问答、智能客服 Agent、内部业务助手、数据分析 Agent、工具调用平台等。

### 主讲稿

```text
我介绍一下我做过的一个大模型应用项目。这个项目的背景是，公司内部有大量制度文档、产品文档、历史工单和业务 API，信息分散在不同系统里，业务人员或客服处理问题时需要反复搜索和切换系统，效率比较低，也容易出现查错规则或漏查信息的情况。

所以我们做了一个基于 RAG 和工具调用的智能助手，希望把“查知识”和“查业务状态”统一到一个自然语言入口里。它既能回答制度、产品、流程类问题，也能在权限允许的情况下调用订单、工单等内部工具。

整体架构我会分成五层：入口层、知识检索层、Agent 编排层、工具调用层和观测评估层。

入口层主要负责用户鉴权、租户识别、限流、会话管理和 SSE 流式返回。这里不会直接把用户请求丢给模型，而是先明确用户身份和权限边界。

知识检索层是 RAG 的核心。离线侧我们做文档采集、解析、清洗、结构化切分、embedding 入库，同时保留 doc_id、page、section、tenant_id、permission、version 等元数据。在线侧用户问题进来后，会先做 query rewrite，然后进行向量检索和 BM25 混合召回，召回结果再经过 reranker 排序，最后构造带引用信息的上下文给模型生成答案。

Agent 编排层主要负责意图路由和状态管理。比如用户只是问制度，就走 RAG；如果问订单状态，就走只读工具；如果涉及退款、修改地址、创建工单这类写操作，就进入确认节点。我们不会让模型自由执行高风险动作，而是把流程拆成明确节点。

工具调用层把内部 API 封装成 Tool，每个工具都有 name、description、参数 schema、返回 schema、风险等级和权限要求。模型只生成工具名和参数，真正执行前后端会做 schema 校验、用户鉴权、超时控制、幂等处理和审计记录。

观测评估层会记录 request_id、prompt 版本、模型名、召回文档、rerank 分数、tool call、token 成本、延迟和最终答案。线上 badcase 会按召回错误、排序错误、上下文噪声、幻觉、工具失败等类别复盘。

这个项目里最大的难点有三个。第一是 RAG 召回不准。我们最开始只用向量检索，遇到制度编号、错误码、产品名这类问题时效果不稳定。后来改成 hybrid search，并用 reranker 提升排序，同时按标题层级优化 chunk。

第二是模型幻觉。RAG 只能降低幻觉，不保证完全正确。所以我们在 Prompt 里要求基于证据回答、无依据拒答，并在后处理里校验引用编号是否来自本次召回上下文。

第三是工具调用安全。查询类工具可以自动执行，但写操作必须用户确认，并且带 idempotency_key，避免超时重试导致重复提交。所有工具调用都会进入审计日志。

如果重新设计，我会进一步把 Prompt、模型、工具和检索策略都版本化，配套更完整的离线评测和 A/B 实验；复杂 Agent 流程会优先用 LangGraph，把状态、分支、checkpoint 和 human-in-the-loop 做得更显式。
```

## 2. 2 分钟压缩版

```text
这个项目是一个企业知识库问答和业务 Agent 系统，目标是把分散的文档和业务 API 统一成自然语言入口。

架构上分成 RAG 检索和 Agent 工具调用两部分。RAG 离线侧做文档解析、清洗、结构化切分、embedding 入库和元数据管理；在线侧做 query rewrite、混合召回、rerank、上下文构造和引用式答案生成。

Agent 部分主要做意图路由和工具调用。知识类问题走 RAG，查询类问题走只读工具，写操作进入用户确认节点。工具执行前会做参数 schema 校验、权限检查、超时、幂等和审计。

项目难点主要是召回不准、幻觉和工具调用风险。我们通过 hybrid search、rerank、引用校验、无依据拒答、工具白名单和 trace 日志来治理。

我对这个项目的理解是，大模型应用不是简单调模型，而是要围绕模型的不确定性做工程治理，让数据可追溯、工具可控、状态可恢复、效果可评估。
```

## 3. 架构图讲解词

配合 `14-系统设计图与伪代码.md` 里的企业知识库 RAG 架构图，可以这样讲：

```text
这张图左边是离线数据链路，右边是在线查询链路。

离线侧从业务文档源开始，包括 PDF、Word、Wiki、数据库和工单。文档进来后先做解析和清洗，处理 OCR、表格、页眉页脚、重复内容等问题。然后进入结构化切分，我们不会只按固定长度切，而是优先按标题、段落、语义边界切，同时保留 parent-child 关系。

切分后，一路生成 embedding 写入向量数据库，一路抽取元数据，比如 doc_id、page、section、tenant_id、permission、version。这些元数据后面会用于权限过滤、引用溯源和增量更新。同时我们也会建立 BM25 索引，用来补足向量检索对关键词、编号、错误码不敏感的问题。

在线侧用户问题进来后，入口层先做鉴权、限流和租户识别。然后做 query rewrite，把多轮上下文里的省略问题补全。检索时会同时走向量召回和关键词召回，并且强制带 metadata filter，避免无权限文档进入候选集。

候选文档经过 reranker 排序后，进入上下文构造模块。这里会去重、合并相邻 chunk、控制 token 长度，并保留引用编号。最后模型基于这些证据生成答案，后处理会做引用校验、敏感信息过滤和格式检查。

最右边是 trace 和评测闭环。每次请求都会记录召回、排序、Prompt、模型输出和用户反馈，用于 badcase 分析和策略迭代。
```

## 4. 难点答辩：召回不准

### 面试官问

你说做了 RAG，那召回不准的时候怎么定位？

### 回答

```text
我会先把问题拆成三类：没召回、召回了但排序靠后、召回正确但生成没用证据。

第一步是从 trace 里抽 badcase，记录用户 query、期望文档、实际召回 top_k、rerank 分数、最终答案和用户反馈。没有这个评测集，就很难判断优化是否有效。

如果是没召回，我先查数据侧：文档解析有没有丢内容，chunk 是否切碎语义，元数据是否缺失，embedding 模型是否适合中文和业务术语。

如果是排序问题，我会看是否需要 hybrid search 和 rerank。向量检索对语义问题好，但对错误码、编号、产品名不一定稳，所以 BM25 很有价值。粗召回后再用 reranker 排序。

如果召回正确但生成没用证据，就要改上下文构造和 Prompt，例如减少噪声 chunk、把关键证据放前面、要求基于证据回答并输出引用。
```

## 5. 难点答辩：权限和数据安全

### 面试官问

如果用户没有权限，但向量库召回了敏感文档怎么办？

### 回答

```text
这个问题不能靠生成后过滤解决，因为模型一旦看到敏感上下文，就已经泄漏了。

我的设计是在入库时就把 tenant_id、department、role、acl、version 等权限元数据写到 chunk 上。在线检索时，根据用户身份构造 metadata filter，并在向量检索和关键词检索阶段都强制带上过滤条件。

缓存也要隔离，cache key 不能只用 query，还要包含 tenant_id、权限版本、prompt 版本和模型版本。日志里敏感内容要脱敏，trace 也要按租户隔离。

如果向量库本身的过滤能力不够，就要在业务层做更严格的租户级 collection 隔离，宁可牺牲一些索引复用，也不能冒数据串租风险。
```

## 6. 难点答辩：工具调用安全

### 面试官问

如果模型重复调用退款接口怎么办？

### 回答

```text
退款这种非幂等写操作不能让模型直接自动执行。模型只负责生成意图和参数，真正执行由后端工具层控制。

执行前必须做用户确认、订单归属校验和权限检查。执行时带 idempotency_key，服务端用这个 key 保证重复请求不会造成重复退款。

如果调用超时，不能直接重试。要先查退款状态：如果成功就返回成功，如果处理中就等待或转人工，如果明确失败才根据规则重新发起。

同时记录 tool_call trace，包括 request_id、user_id、订单号、参数摘要、幂等 key、执行状态和错误码，便于审计。
```

## 7. 难点答辩：延迟和成本

### 面试官问

如果线上延迟太高，你怎么优化？

### 回答

```text
我会先用 trace 拆每一步耗时，而不是凭感觉优化。一般链路里可能慢的点包括 query rewrite、向量检索、BM25、rerank、工具调用和模型生成。

优化可以分几层：

第一是减少不必要步骤。简单问题不一定需要完整 RAG 或大模型，可以走缓存、小模型或规则。

第二是并行化。向量检索和 BM25 可以并行，多个只读工具也可以并行。

第三是控制上下文。减少 top_k，rerank 后只保留高质量 chunk，合并去重，压缩历史对话。

第四是缓存。热点 query、embedding、检索结果和部分模型答案可以缓存，但缓存 key 必须包含租户和权限版本。

第五是流式输出。即使总耗时不变，SSE 可以降低用户体感延迟。

成本上还要做模型路由，简单任务用小模型，复杂任务再用大模型，并设置 token budget 和租户 quota。
```

## 8. 主管面视角：为什么这个项目有价值

### 回答

```text
我认为这个项目的价值不只是把聊天框接到文档上，而是把分散知识和业务操作统一成一个可治理的入口。

对业务侧，它降低了查资料和跨系统操作的成本；对客服或运营，能提升处理效率并减少规则查错；对技术侧，它沉淀了 RAG、工具调用、权限、评估和 trace 这些通用能力，后续可以复用到更多场景。

但我也不会夸大 Agent 的能力。生产环境里，高风险动作仍然要受控，知识回答要可引用，工具调用要可审计，效果要能评估。只有这样，大模型应用才不是 Demo，而是能真正进入业务流程的系统。
```

## 9. 如果项目没有真实上线，怎么说

```text
这个项目目前没有大规模线上用户，所以我不会夸大 DAU 或 QPS。

我们完成的是端到端原型和离线验证，覆盖文档入库、向量检索、Rerank、Prompt 生成、引用校验、工具调用和 trace 记录。

为了评估效果，我构建了一批典型问题和期望文档，主要看 Recall@K、答案相关性、引用准确性和人工评分。

如果要推进上线，我认为下一步最重要的是补齐权限系统、灰度发布、badcase 闭环、成本监控和人工兜底机制。
```

## 10. 如果被问“你的贡献到底是什么”

```text
我主要负责三块。

第一是 RAG 检索链路，包括文档切分、embedding 入库、向量检索、BM25 混合召回、rerank 和上下文构造。

第二是生成和校验，包括 Prompt 设计、引用约束、无依据拒答和输出格式检查。

第三是工具调用治理，包括 tool schema、参数校验、权限检查、超时、幂等和 trace 日志。

其中投入最多的是召回优化和工具调用安全。因为这两个点直接影响系统能不能从 Demo 走向生产。
```

## 11. 项目答辩防守清单

面试前确认自己能答：

- 业务为什么需要大模型，而不是传统搜索或规则。
- 系统整体架构图能否 2 分钟讲清楚。
- 离线数据链路能否讲清楚。
- 在线查询链路能否讲清楚。
- chunk 策略为什么这么选。
- 向量检索、BM25、rerank 分别解决什么问题。
- 权限过滤如何保证不泄漏。
- 工具调用如何防误调用和重复执行。
- 延迟和成本怎么优化。
- 项目指标如何评估。
- 没上线时如何诚实表达验证结果。
- 如果重构，先改什么。

## 12. 结尾收束句

```text
我对这个项目最大的收获是，大模型应用真正难的不是调通模型，而是把模型接入一个可控的工程系统。RAG 要能追溯，Agent 要能恢复，工具要能审计，效果要能评估，风险要能兜底。
```
