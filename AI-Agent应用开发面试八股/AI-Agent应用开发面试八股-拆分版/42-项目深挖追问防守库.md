# 项目深挖追问防守库

> 目标：面试官沿着简历项目连续追问时，能防守到第三层。  
> 这份文件补的是“项目细节防守”，适合配合 `18`、`20`、`24`、`41` 使用。

## 1. 项目深挖的底层逻辑

面试官深挖项目时，通常在验证 5 件事：

| 验证点 | 面试官心里的问题 | 你要证明 |
|---|---|---|
| 真实性 | 这个项目是不是你真做的？ | 能讲数据、接口、参数、异常、指标 |
| 复杂度 | 这个项目有没有技术含量？ | 不是简单调 API，有工程难点 |
| 贡献度 | 你具体负责什么？ | 你做了核心设计或关键优化 |
| 闭环性 | 这个东西有没有上线和评估？ | 有指标、bad case、兜底和复盘 |
| 迁移性 | 换个场景你还能做吗？ | 能抽象方法，而不是只背项目 |

防守的基本句式：

```text
这个点我们当时确实遇到过。
我先说当时的业务约束，再说我们怎么定位，最后说为什么选这个方案。
```

不要用下面这些句子：

- “框架自动做的。”
- “这个不是我负责。”
- “我们没有特别优化。”
- “就是调了一下 prompt。”
- “具体参数不记得了。”

更稳的替代说法：

```text
这个模块不是我独立负责全部实现，但我参与了方案设计和联调。我能讲清楚它在整体链路里的作用，以及我们当时遇到的主要问题。
```

## 2. 通用项目追问链

### 2.1 你这个项目解决了什么问题？

30 秒回答：

```text
这个项目解决的是业务人员在大量内部文档和系统工具之间查找、理解和执行成本高的问题。我们用 RAG 做知识检索和答案生成，用工具调用处理可执行动作，再通过权限、日志、评测和人工兜底保证上线可控。
```

二层追问：为什么不用传统搜索？

```text
传统搜索适合关键词匹配和文档列表返回，但业务用户更需要直接答案、引用依据和多轮澄清。我们不是完全替代搜索，而是保留关键词/向量混合召回，再用大模型做理解、总结和格式化输出。
```

三层追问：如果传统搜索也能满足呢？

```text
如果场景只是精确查文档，传统搜索更稳更便宜。但我们项目里的问题包含自然语言提问、跨文档总结和工具执行，所以采用 RAG/Agent。选型上不是为了用大模型，而是看任务是否需要语义理解、生成和上下文协同。
```

### 2.2 你负责什么？

30 秒回答：

```text
我主要负责 RAG/Agent 后端链路，包括文档入库后的检索策略、Tool schema 设计、模型调用封装、流式响应、日志 trace 和部分评测脚本。项目里我不是只写接口，而是参与了方案选型、bad case 定位和上线后的优化。
```

二层追问：哪些是你亲自实现的？

```text
我亲自实现的是检索服务封装、rerank 前后的上下文组装、工具参数校验、SSE 流式接口和调用日志。文档解析和前端页面由其他同学负责，但我参与了字段约定和联调。
```

三层追问：怎么证明是你做的？

```text
我可以讲几个实现细节。比如检索接口返回的不只是 chunk 文本，还包括 doc_id、section_path、score、source_url 和 permission_tag，后续生成引用、权限过滤和 bad case 复盘都依赖这些字段。
```

### 2.3 项目最大的难点是什么？

30 秒回答：

```text
最大的难点不是把模型接上，而是让结果稳定可控。具体包括召回不稳定、答案可能幻觉、工具调用有风险、延迟和成本不可控。我们把链路拆成检索、生成、工具、评估和治理几个层面逐步优化。
```

二层追问：最难的一个 bad case 是什么？

```text
有一类制度类问题，用户问的是最新政策，但召回到了旧版本文档。表面看是模型答错，实际是知识库版本和 metadata 过滤没做好。后来我们给文档加 version、effective_date 和 department 字段，召回时先做权限和版本过滤，再进向量排序。
```

三层追问：这个问题怎么避免复发？

```text
我们把它沉淀成评测集里的固定 case，每次索引更新、切分策略调整或 embedding 模型切换后都会回归。同时在答案里展示引用来源和日期，让用户能发现旧文档风险。
```

## 3. RAG 项目深挖防守

### 3.1 文档怎么处理？

标准回答：

```text
文档处理分为解析、清洗、结构化、切分和入库。解析阶段保留标题层级、表格、页码和来源；清洗阶段去掉页眉页脚、重复目录和无效字符；切分时优先按标题层级和语义段落，再控制 chunk 长度和 overlap；入库时保存 metadata，方便权限过滤、引用溯源和版本管理。
```

二层追问：PDF 表格怎么办？

```text
表格不适合直接按普通段落切。我们会尽量把表头、行列含义和上下文一起保留，转成 markdown 或结构化文本。如果表格特别关键，会单独做表格索引或保留原始坐标，避免检索到一行却丢失列含义。
```

三层追问：解析错了怎么发现？

```text
一方面做入库抽样检查，看 chunk 是否有乱码、断句和表格错位；另一方面在 bad case 复盘时，如果召回 chunk 本身质量差，就把问题归到解析层，而不是误判成 embedding 或 prompt 问题。
```

### 3.2 chunk 大小怎么定？

标准回答：

```text
chunk 大小不是固定拍脑袋，要看文档结构、问题粒度和模型上下文。制度类文档通常按标题层级和语义段落切，保留一定 overlap；FAQ 类可以按问答对切；长报告类需要章节摘要和细粒度 chunk 结合。最终用召回命中率、答案准确率和上下文冗余来评估。
```

二层追问：chunk 太大太小分别有什么问题？

```text
太大会引入无关信息，影响 rerank 和生成，成本也高；太小会丢上下文，模型拿到证据但理解不了条件和例外。所以通常会在语义完整和检索精度之间折中。
```

三层追问：你们最后怎么选？

```text
我们先按默认长度做 baseline，然后抽取高频问题构造评测集，对比不同 chunk 策略的 top-k 命中率、引用覆盖率和人工验收结果。最后不是只选一个固定长度，而是对 FAQ、制度、操作手册采用不同切分策略。
```

### 3.3 召回不准怎么定位？

标准回答：

```text
我会先判断是 query 表达问题、文档切分问题、embedding 语义匹配问题、metadata 过滤问题，还是 top-k/rerank 问题。定位时看正确文档是否在候选集里：如果 top-k 前完全没有，优先查召回；如果候选里有但没进上下文，查 rerank；如果上下文有但答案错，查生成和引用约束。
```

二层追问：如果用户问题很短怎么办？

```text
短 query 信息不足时，可以做 query rewrite 或多查询扩展，把用户问题补成更明确的检索表达。但要控制扩展范围，避免引入错误意图。对业务系统也可以结合用户角色、当前页面和历史对话补充上下文。
```

三层追问：怎么证明优化有效？

```text
用固定评测集对比优化前后的 top-k hit rate、MRR、答案准确率、引用覆盖率、平均延迟和 token 成本。不能只拿几个成功 case 证明，要看整体收益和坏 case 是否减少。
```

### 3.4 幻觉怎么处理？

标准回答：

```text
幻觉治理不能只靠 prompt。我们从检索证据、生成约束、引用校验和无答案识别四层处理：召回阶段尽量保证证据相关；生成阶段要求答案基于上下文；输出阶段检查引用是否存在；证据不足时明确回答无法确定。
```

二层追问：模型还是编怎么办？

```text
可以把生成结果和引用片段做一致性校验，比如要求每个关键结论都能映射到 source_id。如果映射不到，就降级成“根据已检索资料无法确认”。高风险场景还需要人工审核。
```

三层追问：会不会降低回答率？

```text
会，所以要区分场景。企业制度、法律、财务这类高风险场景宁愿降低回答率，也要保证可信；开放问答可以适当放宽。指标上要同时看准确率、拒答率和用户满意度。
```

## 4. Agent 项目深挖防守

### 4.1 Agent 的任务边界是什么？

标准回答：

```text
我们的 Agent 不是什么都自动做，而是限定在明确业务流程内，比如查询信息、生成草稿、调用低风险工具、提交前人工确认。模型负责理解意图和选择下一步，真正执行由后端工具完成，并且有权限、参数校验和审计。
```

二层追问：哪些事情不让 Agent 做？

```text
高风险、不可逆、涉及资金或权限变更的操作不能直接自动执行，至少需要人工确认。还有一些规则明确、无需模型判断的流程，我们用确定性代码处理，不让 Agent 增加不确定性。
```

三层追问：怎么防止越权？

```text
工具执行前会基于用户身份、租户、角色和工具权限做校验。模型只能提出调用意图和参数，不能绕过后端鉴权。日志里记录 user_id、tool_name、args_hash、trace_id 和执行结果，方便审计。
```

### 4.2 为什么用 LangGraph？

标准回答：

```text
因为这个任务是多步骤、有状态、可能失败恢复的流程。LangGraph 可以把意图识别、检索、工具选择、参数补全、执行确认、结果总结拆成节点，通过 state 在节点间传递信息，并用条件边控制流程。
```

二层追问：不用 LangGraph 怎么做？

```text
简单任务可以用普通 chain 或后端状态机。我们选择 LangGraph 是因为需要 checkpoint、可观测、条件分支和人工介入。如果只是单轮 RAG，用 LangGraph 反而可能过重。
```

三层追问：state 里放什么？

```text
state 里放用户意图、会话摘要、检索结果、候选工具、已执行步骤、工具返回、错误信息、确认状态和最终答案。不会把所有原始对话无限塞进去，会做摘要和字段化，避免上下文膨胀。
```

### 4.3 Agent 死循环怎么办？

标准回答：

```text
死循环通常是目标不清、工具返回不符合预期、模型反复修正失败导致的。我们会设置最大步数、最大工具调用次数、重复动作检测和超时；连续失败后降级为人工处理或返回需要补充信息。
```

二层追问：怎么检测重复动作？

```text
可以记录最近几步的 action、tool_name 和关键参数 hash。如果多次调用同一工具、参数变化很小且结果没有新增信息，就判断为无效循环，触发终止或人工介入。
```

三层追问：终止后用户体验怎么办？

```text
不要只说失败，而是给出当前已完成步骤、失败原因和下一步建议。比如“我已经查到 A 和 B，但调用 C 工具时缺少订单号，请补充后继续”。这样即使终止也能保持可解释。
```

### 4.4 工具调用失败怎么办？

标准回答：

```text
先区分失败类型：参数错误、权限不足、外部 API 超时、业务状态不满足、工具内部异常。参数错误可以让模型补参或追问用户；权限不足直接拒绝；超时可以重试或降级；业务状态不满足要解释原因；系统异常要记录 trace 并兜底。
```

二层追问：重试怎么设计？

```text
只对幂等且可能瞬时恢复的错误重试，比如网络超时。重试要限制次数并使用退避策略。对创建、支付、提交这类可能产生副作用的操作，必须用幂等 key 或人工确认，不能盲目重试。
```

三层追问：模型怎么知道失败原因？

```text
工具返回要标准化，包含 error_code、message、retryable、user_action_required 等字段。不要把原始异常直接丢给模型，而是转成模型和用户都能理解的结构化错误。
```

## 5. MCP / 工具平台项目深挖防守

### 5.1 OpenAPI 怎么转 Tool？

标准回答：

```text
OpenAPI 转 Tool 的核心是把接口描述、参数 schema、认证方式和错误响应转成模型可理解、后端可执行的工具定义。不是所有接口都适合作为工具，需要筛选低风险、语义清晰、参数可校验的能力。
```

二层追问：接口太复杂怎么办？

```text
复杂接口不能原样暴露给模型。可以做适配层，把多个底层参数封装成业务语义更清晰的 tool，比如把 start_time、end_time、department_id 封装成“查询某部门某时间段报表”。模型面对业务工具，后端再映射到底层 API。
```

三层追问：schema 更新怎么办？

```text
需要版本管理。工具 schema 变更时保留旧版本一段时间，新增字段尽量向后兼容；破坏性变更要灰度，并在调用日志里记录 tool_version，方便排查。
```

### 5.2 MCP 的价值是什么？

标准回答：

```text
MCP 的价值是把模型客户端和外部工具、资源、提示词之间的集成标准化。相比每个应用自己写插件协议，MCP Server 可以统一暴露 tools、resources 和 prompts，让不同客户端以一致方式接入。
```

二层追问：MCP 和 OpenAPI 区别？

```text
OpenAPI 描述的是 HTTP API；MCP 更像模型上下文和工具集成协议，除了 tools，还包含 resources、prompts 等面向模型使用的能力。实际工程里可以用 OpenAPI 生成工具，再通过 MCP Server 暴露给 Agent。
```

三层追问：MCP 有什么风险？

```text
风险主要是工具权限扩大、上下文泄露、prompt 注入诱导工具调用和服务端信任边界不清。所以 MCP Server 后面仍然要做鉴权、参数校验、审计和高风险操作确认。
```

### 5.3 工具权限怎么设计？

标准回答：

```text
工具权限至少分用户权限、租户权限、工具权限和数据权限。模型不能决定权限，只能发起调用请求。后端执行前根据用户身份和业务规则校验，敏感工具还要二次确认。
```

二层追问：如果模型构造了越权参数呢？

```text
后端不能信任模型参数。比如 user_id、tenant_id、department_id 这类敏感字段应来自服务端会话或权限系统，而不是模型生成。模型传来的参数只作为业务输入，必须经过白名单和范围校验。
```

三层追问：审计日志记什么？

```text
记录 user_id、tenant_id、session_id、trace_id、tool_name、tool_version、参数摘要、权限校验结果、执行状态、耗时、错误码和人工确认信息。敏感参数脱敏或只存 hash。
```

## 6. Python 后端项目深挖防守

### 6.1 为什么用 FastAPI？

标准回答：

```text
FastAPI 适合大模型应用后端，因为它原生支持 async、类型校验和自动 API 文档，方便做模型调用、流式响应和工具接口封装。但框架只是基础，真正要处理的是超时、限流、缓存、日志和可观测。
```

二层追问：async 一定更快吗？

```text
不一定。async 适合 I/O 密集，比如调用模型 API、向量库和外部工具。CPU 密集任务不会因为 async 变快，需要进程池、任务队列或独立服务处理。
```

三层追问：如何避免请求堆积？

```text
入口做限流和并发控制，模型调用设置超时，长任务进入队列，流式请求支持断连取消。监控队列长度、平均耗时、失败率和模型供应商延迟，必要时降级到轻量模型或缓存结果。
```

### 6.2 SSE 流式响应怎么做？

标准回答：

```text
SSE 适合服务端向客户端持续推送 token 或阶段性结果。后端通常用 async generator 包装模型流式输出，逐段 yield 给客户端，同时处理异常、心跳、断连和最终状态记录。
```

二层追问：用户断开怎么办？

```text
需要检测客户端断连并取消后续任务，避免模型调用继续消耗资源。如果底层模型 API 不支持取消，也要停止向客户端写入，并记录这次请求为 client_cancelled。
```

三层追问：流式输出如何记录日志？

```text
不能每个 token 都打完整日志。通常记录 trace_id、首 token 延迟、总耗时、输出 token 数、结束状态和错误码。必要时对完整输出做采样或脱敏保存。
```

### 6.3 限流怎么做？

标准回答：

```text
限流要按用户、租户、接口、模型和工具维度设计。常见算法有固定窗口、滑动窗口、令牌桶和漏桶。大模型应用还要考虑 token 成本，所以不只按请求数限流，也可以按 token 预算限流。
```

二层追问：令牌桶和漏桶区别？

```text
令牌桶允许一定突发，只要桶里有令牌就能请求；漏桶更强调平滑输出，固定速率处理。用户交互类应用通常需要允许短时突发，后台任务更适合平滑限速。
```

三层追问：限流后怎么返回？

```text
返回明确错误码和重试建议，比如 retry_after。对重要业务可以排队或降级，对普通请求直接拒绝。日志里记录限流维度和当前配额，方便运营和排查。
```

## 7. 微调 / 模型优化项目深挖防守

### 7.1 为什么不只用 RAG？

标准回答：

```text
RAG 适合补充外部知识和保持知识更新，但如果问题是输出格式、语气风格、领域指令遵循或特定任务模式不稳定，微调会更合适。我们会先做 RAG/Prompt baseline，再判断是否需要 SFT 或 LoRA。
```

二层追问：怎么判断需要微调？

```text
如果模型明明拿到了正确上下文，但长期不能按业务格式、规则或风格输出，且 prompt 复杂到难维护，就可以考虑微调。如果问题是知识缺失或数据频繁更新，优先 RAG。
```

三层追问：微调后怎么评估？

```text
用固定测试集对比 baseline，看准确率、格式遵循、拒答、幻觉、人工偏好和成本延迟。还要看通用能力有没有下降，避免只在训练分布上变好。
```

### 7.2 数据怎么构造？

标准回答：

```text
数据构造先来自真实业务 case、人工标注和日志清洗，再做去重、脱敏、质量筛选和格式统一。指令要覆盖正常问题、边界问题、拒答问题和多轮上下文，不能只放成功样本。
```

二层追问：数据少怎么办？

```text
数据少时先不要急着微调，可以用 prompt、RAG、规则和 few-shot 做 baseline。确实要微调时，优先保证高质量和覆盖度，可以从 bad case 反向构造样本，而不是盲目扩大量。
```

三层追问：如何防止过拟合？

```text
划分训练/验证/测试集，控制训练轮次和学习率，监控验证集表现。测试集要包含未见过的问题和负样本，同时保留通用能力评估，避免模型只记住模板。
```

## 8. 平台 / 模型网关项目深挖防守

### 8.1 模型网关解决什么问题？

标准回答：

```text
模型网关解决的是多业务、多模型接入时的统一鉴权、路由、限流、日志、成本和降级问题。没有网关时，每个业务自己接模型，权限、成本和观测都很分散。
```

二层追问：路由策略怎么设计？

```text
可以按业务场景、模型能力、成本、延迟、上下文长度和可用性路由。简单任务走便宜模型，复杂任务走强模型；供应商异常时自动切换；高优先级租户有更高配额。
```

三层追问：如何避免路由错误影响效果？

```text
先离线评测不同模型在各类任务上的表现，再灰度上线。路由策略要有可解释配置和回滚机制，并持续观察准确率、失败率、延迟和成本。
```

### 8.2 Prompt 平台有什么价值？

标准回答：

```text
Prompt 平台的价值是把 prompt 从代码里抽出来，支持版本管理、变量模板、审批、灰度、回滚和效果评测。这样业务调整 prompt 不需要频繁发版，也能追踪某次效果变化来自哪个版本。
```

二层追问：怎么评测 prompt？

```text
每个 prompt 版本绑定固定评测集，比较格式正确率、答案准确率、拒答率、幻觉率、成本和延迟。上线前离线回归，上线后小流量灰度。
```

三层追问：prompt 泄露怎么办？

```text
平台侧做权限控制和脱敏，客户端不暴露系统 prompt。日志保存时注意敏感信息脱敏。对外部输入要做 prompt 注入检测和工具调用边界控制。
```

## 9. 指标和数据防守

### 9.1 如果没有真实线上指标怎么办？

稳妥说法：

```text
这个项目没有大规模线上流量，所以我不会夸大线上指标。我们主要用了离线评测和小范围试用反馈，指标包括问题命中率、答案人工验收通过率、平均响应时间和 bad case 类型分布。
```

危险说法：

```text
效果还不错，用户反馈挺好。
```

### 9.2 指标被追问怎么算？

回答模板：

```text
我们把问题集按业务类型分层，每个问题有标准答案或人工验收标准。RAG 看 top-k 是否命中证据、答案是否正确、引用是否覆盖；Agent 看任务成功率、工具调用成功率、人工介入率、平均步骤数和成本。
```

### 9.3 数据量不大怎么办？

回答模板：

```text
数据量不大时，我会强调方法闭环而不是夸规模。比如先构造覆盖核心业务路径的小型 golden set，再通过真实使用中的 bad case 持续扩充。小数据也能做严谨的版本对比和回归测试。
```

## 10. 坏回答改写

| 面试官问题 | 危险回答 | 更好的回答 |
|---|---|---|
| 你负责什么？ | 我主要负责后端。 | 我负责模型调用和检索服务这一段，包括接口封装、上下文组装、流式响应和日志 trace。 |
| 为什么用 RAG？ | 因为 RAG 比较火。 | 因为知识更新频繁且需要引用溯源，微调不适合承载动态知识。 |
| 为什么用 Agent？ | 因为它能自动完成任务。 | 因为任务需要多步骤决策和工具执行，但我们限定了边界和人工确认。 |
| 怎么评估？ | 看回答准不准。 | 用固定问题集评估命中率、答案准确率、引用覆盖率、延迟和人工验收。 |
| 有什么难点？ | prompt 不太好调。 | 难点是坏 case 定位，要判断问题来自解析、召回、排序、生成还是工具执行。 |
| 上线了吗？ | 还没有正式上线。 | 目前是小范围试用/内部验证，所以我主要讲离线评测、试用反馈和上线前还需要补的治理能力。 |
| 数据从哪来？ | 公司文档。 | 主要来自制度文档、FAQ 和业务操作手册，入库时保留来源、部门、版本和权限 metadata。 |

## 12. 临场防守原则

### 12.1 不知道细节时

可以说：

```text
这个参数我不想现场编一个不准确的数字。我记得我们当时关注的是它对召回命中和上下文长度的影响，具体做法是用评测集对比几个候选值。面试后我可以再补具体数值。
```

不要说：

```text
应该差不多吧。
```

### 12.2 项目不是完全上线时

可以说：

```text
这个项目还没有大规模线上化，所以我会把它定义为内部验证/试点项目。已经完成的是核心链路、离线评测和小范围反馈；如果继续推进上线，还需要补权限审计、监控告警、灰度和成本预算。
```

### 12.3 不是自己负责的模块

可以说：

```text
这个模块不是我主责，但我和负责同学做过接口联调，所以我能讲清楚输入输出和它对整体链路的影响。更底层的实现细节我不会假装是我做的。
```

## 13. 练习方法

每个项目至少练 3 轮：

### 第 1 轮：讲清楚

目标：

- 2 分钟讲完整。
- 不跑题。
- 能说清自己的职责。

### 第 2 轮：抗追问

目标：

- 每个关键模块至少准备 3 层追问。
- RAG、Agent、Tool、后端至少各有一个 bad case。

### 第 3 轮：换公司表达

目标：

- 腾讯版讲业务体验。
- 阿里版讲平台治理。
- 百度版讲检索和模型效果。
- 字节版讲指标和实验。
- 华为/云厂商版讲权限、审计和交付。

## 14. 最后速记

```text
项目深挖不是背一段讲稿，而是准备证据链：

我为什么做
  -> 我负责什么
  -> 我怎么设计
  -> 我遇到什么问题
  -> 我怎么定位
  -> 我怎么验证
  -> 我怎么兜底
  -> 我如果重做会怎么改
```

一句话：

```text
能把项目讲到第三层，面试官才会相信这是你的项目。
```
