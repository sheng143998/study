## 1. 项目深挖：1-15

### 1. 用 2 分钟介绍你的 AI Agent/RAG 项目

30 秒版：

```text
我做的是一个企业知识库问答和业务 Agent 系统，目标是把分散的文档和业务 API 统一成自然语言入口。RAG 负责制度、产品、流程类知识问答，Agent 负责意图路由和工具调用，例如查询订单、创建工单等。系统重点做了文档切分、混合召回、rerank、引用校验、工具 schema、权限校验、幂等和 trace。
```

展开关键词：

- 业务背景。
- 离线 RAG 链路。
- 在线问答链路。
- Agent 工具调用。
- 权限、安全、评估。

### 2. 这个项目解决什么业务问题

30 秒版：

```text
主要解决信息分散和跨系统操作成本高的问题。业务人员或客服以前需要在文档、Wiki、工单、订单系统之间来回查，现在可以用自然语言统一提问，系统先检索知识，再在权限允许的情况下调用工具查询业务状态。
```

展开关键词：

- 查资料效率低。
- 规则容易查错。
- 多系统切换。
- 知识更新频繁。
- 需要引用溯源。

### 3. 为什么需要大模型，不用传统搜索或规则系统

30 秒版：

```text
传统搜索适合关键词匹配，规则系统适合确定性判断，但用户问题往往是自然语言、口语化、多轮上下文相关。大模型适合理解意图、总结证据和生成自然语言答案。不过我不会完全替代传统搜索和规则，而是用 RAG 结合 BM25，用规则处理权限、金额阈值、状态流转等确定性逻辑。
```

展开关键词：

- 语义理解。
- 长尾表达。
- 证据总结。
- 规则系统保留强一致判断。
- hybrid search。

### 4. 你负责哪一部分

30 秒版：

```text
我主要负责三块：第一是 RAG 检索链路，包括文档切分、embedding 入库、向量召回、BM25 混合召回、rerank 和上下文构造；第二是生成和校验，包括 Prompt、引用约束和无依据拒答；第三是工具调用治理，包括 tool schema、参数校验、权限检查、超时、幂等和 trace。
```

展开关键词：

- 不说“都参与了”。
- 明确模块边界。
- 强调自己做的难点。

30 秒版：

```text
整体分五层：入口层负责鉴权、限流和流式输出；RAG 层负责文档入库、检索、rerank 和生成；Agent 编排层负责意图路由、状态和流程控制；工具层负责内部 API 调用；观测评估层记录 trace、token、延迟、召回文档、tool call 和 badcase。
```

展开关键词：

- API gateway。
- Offline ingestion。
- Online retrieval。
- Agent workflow。
- Tool execution。
- Observability/eval。

### 6. 项目里最难的问题是什么

30 秒版：

```text
最难的是从 Demo 走向可控系统，主要体现在召回不准、模型幻觉和工具调用风险。召回问题靠 badcase、chunk 优化、hybrid search 和 rerank；幻觉靠证据约束和引用校验；工具风险靠 schema、权限、确认、幂等和审计。
```

展开关键词：

- 现象、根因、方案、效果。

30 秒版：

```text
我会先做 trace，把一次请求拆成 query rewrite、召回、rerank、prompt、模型输出、tool call 等步骤。然后从 badcase 判断问题属于没召回、排错、上下文噪声、生成没用证据，还是工具执行错误，再按模块定位。
```

展开关键词：

- trace。
- badcase。
- 分层定位。
- 评测集。

### 8. 做过哪些方案对比

30 秒版：

```text
常见对比包括纯向量检索和 hybrid search，对比不同 chunk_size，对比是否加 rerank，对比大模型和小模型路由，对比自由 Agent 和受控 workflow。每个方案都看召回质量、答案质量、延迟、成本和稳定性。
```

展开关键词：

- 不只看效果。
- 要讲 trade-off。

### 9. 项目有没有上线？没有上线怎么验证效果

30 秒版：

```text
如果没有大规模上线，我会如实说明。我们可以做端到端原型和离线验证，构建典型问题集和期望文档，评估 Recall@K、答案相关性、引用准确率和人工评分，同时记录 Demo 用户反馈和 badcase。
```

展开关键词：

- 不编指标。
- 离线评测。
- 端到端链路。
- 上线前还需权限、灰度、监控。

### 10. 如果重新设计，你会怎么改

30 秒版：

```text
我会优先补三件事：第一，把 Prompt、模型、检索策略和工具版本化，支持灰度和回滚；第二，建立更系统的离线评测和 badcase 平台；第三，用 LangGraph 或状态机把复杂 Agent 流程显式化，支持 checkpoint、human-in-the-loop 和恢复。
```

展开关键词：

- 版本管理。
- 评测闭环。
- 显式状态。
- 权限审计。

### 11. 项目中哪些地方体现工程能力

30 秒版：

```text
主要体现在可控性和可观测性：RAG 有元数据、权限过滤、引用溯源和评测；Agent 有状态、最大步数、工具 schema、幂等和人工确认；服务层有异步调用、限流、超时、降级、SSE 和 trace。
```

展开关键词：

- 工程治理。
- 不是只接 API。

30 秒版：

```text
我会先固定评测集和指标，再对比优化前后。检索看 Recall@K、MRR、NDCG；生成看答案相关性、faithfulness、引用准确率；工程看延迟、成本、失败率和用户反馈。没有指标的优化很容易只是主观感觉。
```

### 13. 项目中有没有权限、安全、审计设计

```text
有。RAG 入库时给 chunk 写 tenant_id、department、acl、version 等元数据，检索时强制 metadata filter。工具调用前做用户鉴权、参数校验和风险等级判断，高风险写操作需要确认。全链路记录 request_id、召回文档、工具参数摘要、执行状态和审计日志。
```

```text
最大技术债通常是评测体系和版本管理不够完善。很多策略改动只靠少量 badcase 判断，缺少稳定回归集；Prompt、模型、retrieval 配置和工具 schema 如果没有版本化，线上问题也很难复现和回滚。
```

## 2. RAG：16-40

### 16. RAG 是什么

30 秒版：

```text
RAG 是检索增强生成。它先从外部知识库检索相关内容，再把这些内容作为上下文交给大模型生成答案。它适合私有知识、更新频繁的知识和需要引用溯源的场景。
```

追问关键词：

- 不改变模型参数。
- 降低幻觉但不能消灭。
- 离线/在线两条链路。

### 17. RAG 的离线链路是什么

30 秒版：

```text
离线链路是文档采集、解析、清洗、切分、embedding、建索引和存元数据。元数据包括 doc_id、chunk_id、page、section、tenant_id、permission、version，用于权限、引用和更新。
```

### 18. RAG 的在线链路是什么

30 秒版：

```text
在线链路是用户问题进来后，先做鉴权和 query rewrite，然后进行向量/BM25 混合召回，带 metadata filter，召回结果经过 rerank，再构造上下文给模型生成，最后做引用校验和敏感过滤。
```

### 19. 文档怎么解析和清洗

30 秒版：

```text
解析要按文档类型处理 PDF、Word、网页、Markdown、表格和 OCR。清洗包括去页眉页脚、去噪、去重、修复乱码、保留标题层级和页码。解析质量直接决定 RAG 上限。
```

### 20. chunk 怎么切

30 秒版：

```text
优先按文档结构切，比如标题、段落、列表、代码块和表格；再用 token 长度控制。不要只按固定长度硬切。制度文档适合标题层级，FAQ 适合问答对，代码文档要保护函数和代码块边界。
```

### 21. chunk_size 和 overlap 怎么选

30 秒版：

```text
chunk_size 要平衡召回精准和上下文完整。小 chunk 精准但信息不足，大 chunk 完整但噪声和成本高。overlap 用来保留跨段语义，但过大会增加重复和索引成本。最终要靠评测集调。
```

### 22. 小 chunk 和大 chunk 各有什么问题

30 秒版：

```text
小 chunk 容易召回准，但缺上下文，模型可能无法回答完整问题。大 chunk 信息完整，但召回容易不准，噪声多，token 成本高。工程上常用 parent-child chunk，小块召回，大块生成。
```

### 23. parent-child chunk 是什么

30 秒版：

```text
parent-child chunk 是把文档切成小 chunk 用于向量召回，同时保留它所属的父段落或章节。召回命中小 chunk 后，把父 chunk 或相邻上下文提供给模型，兼顾召回精度和上下文完整性。
```

### 24. embedding 模型怎么选

30 秒版：

```text
看语言、领域、维度、成本、延迟和评测效果。中文企业知识库要优先选中文或多语言表现好的 embedding。最终不能只看榜单，要用自己的 query-doc 评测集看 Recall@K 和排序质量。
```

### 25. 向量检索和 BM25 区别是什么

30 秒版：

```text
向量检索按语义相似度，适合表达不完全一致但语义接近的问题。BM25 按关键词匹配，适合编号、错误码、产品名、函数名等精确词。企业 RAG 通常两者结合。
```

### 26. 为什么要 hybrid search

30 秒版：

```text
因为向量检索和关键词检索互补。向量擅长语义，BM25 擅长精确匹配。混合检索能提升企业知识库里专有名词、制度条款、错误码和口语化问题的整体召回稳定性。
```

### 27. rerank 为什么有效

30 秒版：

```text
向量召回是粗召回，排序不一定精准。reranker 通常同时看 query 和文档文本，能做更细粒度的相关性判断，把真正相关的文档排到前面。
```

### 28. top_k 越大越好吗

30 秒版：

```text
不是。top_k 大会提高覆盖率，但也引入更多噪声、增加 rerank 和 token 成本，甚至降低答案质量。要结合 hybrid search、rerank 和评测集选择。
```

### 29. RAG 召回不准怎么办

30 秒版：

```text
先用 badcase 建评测集，再按链路排查：文档解析是否丢内容，chunk 是否合理，embedding 是否适合领域，query 是否需要改写，top_k 是否合适，是否需要 hybrid search、rerank 和 metadata filter 调整。
```

### 30. 如何判断是没召回还是排序错误

30 秒版：

```text
看正确文档是否出现在候选集合里。如果 top50 都没有，是召回问题；如果在 top50 但不在 top5，是排序问题；如果 top5 有正确文档但答案错了，是上下文构造或生成问题。
```

### 31. 如何处理 RAG 幻觉

30 秒版：

```text
从检索和生成两层治理。检索层提高证据质量，生成层要求基于证据回答、无依据拒答、输出引用。后处理做引用校验和 groundedness 检查，高风险场景加人工审核。
```

### 32. 如何让答案带引用

30 秒版：

```text
上下文构造时给每个 chunk 编号，并保留 source、page、section。Prompt 要求答案引用编号，后处理校验引用编号是否来自本次上下文，并把编号映射回真实文档来源。
```

### 33. 引用编号合法是否等于答案正确

30 秒版：

```text
不等于。编号合法只能说明模型引用了本次提供的文档，不能证明答案内容被文档支持。还需要检查答案和引用片段的一致性，可以用规则、LLM-as-judge 或人工评估。
```

### 34. RAG 如何做权限过滤

30 秒版：

```text
入库时给 chunk 写权限元数据，如 tenant_id、department、role、acl。检索时根据用户身份构造 metadata filter，并在向量检索和关键词检索阶段都强制过滤。生成后过滤不够安全。
```

### 35. 文档热更新怎么做

30 秒版：

```text
按 doc_id 和 version 做增量更新。更稳的做法是先写入新版本 chunk，校验成功后切换 active_version，再异步删除旧版本，避免先删后写导致查询空窗。
```

### 36. 删除文档后向量库如何一致

30 秒版：

```text
通过 doc_id/chunk_id 删除对应向量和元数据，必要时先软删除标记 inactive，在线检索过滤 inactive，再异步物理删除或重建索引。还要清理关键词索引和相关缓存。
```

### 37. RAG 如何评估

30 秒版：

```text
分检索、生成和工程三层评估。检索看 Recall@K、MRR、NDCG；生成看答案相关性、faithfulness、引用准确率；工程看延迟、成本、失败率、缓存命中率和用户反馈。
```

### 38. Recall@K、MRR、NDCG 分别是什么

30 秒版：

```text
Recall@K 看正确文档是否出现在前 K 个结果里；MRR 关注第一个正确结果的排名；NDCG 考虑相关性等级和排序位置，更适合评估排序质量。
```

### 39. RAG 和微调怎么选

30 秒版：

```text
缺知识，尤其是私有和频繁更新知识，优先 RAG；输出风格、格式、任务模式不稳定，并且有高质量样本，可以考虑微调。两者可以结合，RAG 给知识，微调改善行为。
```

### 40. 为什么 RAG 不能完全消除幻觉

30 秒版：

```text
因为 RAG 只是把检索结果放进上下文，不保证检索一定正确，也不保证模型一定忠实使用证据。召回错误、上下文噪声、Prompt 约束不足和问题超范围都会导致幻觉。
```

## 3. Agent：41-55

### 41. 什么是 AI Agent

30 秒版：

```text
AI Agent 是以目标为导向的大模型应用系统，能基于任务进行规划、调用工具、读取外部知识、维护状态，并根据观察结果继续决策，直到完成任务或触发终止。
```

### 42. Agent 和 Chatbot 有什么区别

30 秒版：

```text
Chatbot 主要是对话生成，用户问、模型答；Agent 不只生成文本，还能围绕目标多步执行、调用工具、更新状态和处理反馈。Agent 更灵活，但稳定性和安全治理要求更高。
```

### 43. Agent 的核心组成有哪些

30 秒版：

```text
核心包括 LLM、Tools、State/Memory、Planner、Executor、Observer 和 Guardrails。LLM 负责理解和决策，Tools 提供外部能力，State 保存任务进度，Guardrails 控制权限、预算、终止和安全。
```

### 44. Agent 的执行循环是什么

30 秒版：

```text
典型循环是：接收目标，规划下一步，选择工具或动作，执行工具，观察结果，更新状态，判断继续还是结束。生产系统会加最大步数、超时和失败分支。
```

### 45. ReAct 是什么

30 秒版：

```text
ReAct 是 Reasoning + Acting 的模式，让模型交替进行思考、行动和观察，也就是 Thought、Action、Observation 循环。它适合工具调用推理，但生产中要限制步骤和输出。
```

### 46. Planner-Executor 是什么

30 秒版：

```text
Planner-Executor 是把复杂任务拆成计划和执行两部分。Planner 负责生成步骤，Executor 负责逐步执行工具并根据结果更新状态。它适合长任务，但要支持计划修正和失败处理。
```

### 47. Agent 为什么不稳定

30 秒版：

```text
因为模型输出有随机性，工具描述可能不清，多步误差会累积，上下文可能漂移，工具可能失败，终止条件不明确，权限如果只靠 Prompt 也不安全。
```

### 48. 如何防止 Agent 死循环

30 秒版：

```text
设置最大步数、超时、token budget、step_count、error_count、重复工具调用检测和终止条件。复杂流程用 LangGraph 或状态机显式控制循环，失败后进入 fallback 或人工节点。
```

### 49. Agent 状态应该怎么设计

30 秒版：

```text
状态只放流程控制需要的信息，比如 messages、task_id、intent、retrieved_docs、tool_results、pending_action、approval_status、step_count、error_count 和 final_answer。大对象存外部，只在状态里放引用。
```

### 50. 多轮上下文太长怎么办

30 秒版：

```text
可以做滑动窗口、历史摘要、检索式记忆和结构化状态。重要信息不要只放自然语言摘要，比如订单号、用户确认状态、工具结果要结构化存储。
```

### 51. Agent 失败后怎么恢复

30 秒版：

```text
要先区分失败类型：参数错误让模型修正，工具超时做状态查询或降级，权限错误直接拒绝，连续失败转人工。长任务可以用 checkpoint 保存状态，恢复后从中断节点继续。
```

### 52. Agent 如何评估

30 秒版：

```text
不能只看最终回答，要看任务成功率、工具选择准确率、平均步骤数、失败恢复率、人工介入率、延迟、成本和权限违规率。复杂任务还要看过程 trace。
```

### 53. 什么时候不应该用 Agent

30 秒版：

```text
如果流程固定、规则明确、风险高或对稳定性要求极强，不一定需要 Agent。能用普通 workflow 或规则系统解决的，不要为了 Agent 而 Agent。生产中优先受控流程。
```

### 54. 自由 Agent 和受控 workflow 怎么选

30 秒版：

```text
自由 Agent 灵活但不可控，适合探索性任务；受控 workflow 稳定、可测、可审计，适合生产业务。大多数企业场景会把关键路径做成 workflow，只在低风险环节给模型决策空间。
```

### 55. 多 Agent 怎么编排

30 秒版：

```text
通常用 supervisor/router 调度多个专职 Agent，比如 Researcher、Tool Executor、Reviewer、Writer。关键是定义共享状态、输入输出 schema、最大轮数、终止条件和冲突处理。
```

## 4. Tool Calling：56-70

### 56. Tool Calling 是什么

30 秒版：

```text
Tool Calling 是让模型根据用户意图选择外部工具，并生成结构化参数。模型不直接执行工具，应用层负责参数校验、权限检查、执行、异常处理和结果回填。
```

### 57. Function Calling 和 Tool Calling 有什么区别

30 秒版：

```text
Function Calling 更强调调用开发者定义的函数，Tool Calling 范围更广，可以包括 API、搜索、数据库、代码执行、MCP 工具等。工程上两者流程类似，都是模型生成结构化调用，系统执行。
```

### 58. 工具调用完整流程是什么

30 秒版：

```text
模型读取工具 schema，判断是否需要工具，输出 tool_name 和 arguments；后端校验参数、检查权限、执行工具、处理错误，再把 observation 返回给模型，模型继续推理或输出最终答案。
```

### 59. Tool schema 怎么设计

30 秒版：

```text
工具名要具体，description 要说明什么时候用和什么时候不用，参数 schema 要类型明确、required 清楚，尽量用 enum 限制取值，返回结构稳定，高风险工具标记 risk_level。
```

### 60. 工具 description 为什么重要

30 秒版：

```text
description 会影响模型是否选择这个工具。描述模糊或多个工具语义重叠，会导致错调工具。好的 description 应该写清适用场景、限制条件和不要使用的情况。
```

### 61. 模型生成的参数错了怎么办

30 秒版：

```text
后端先做 schema 校验。校验失败可以把错误作为 observation 返回给模型，让模型修正；超过重试次数就失败或转人工。不能直接信任模型参数。
```

### 62. 工具调用失败怎么办

30 秒版：

```text
按错误类型处理：参数错误让模型修正，权限错误拒绝，网络超时重试或降级，业务错误转成可理解 observation，连续失败转人工。写操作失败还要考虑幂等和状态查询。
```

### 63. 如何防止模型误调用工具

30 秒版：

```text
工具层面要有清晰 name/description/schema，运行时只暴露当前场景可用工具，执行前做权限和参数校验。流程上可以用 router 或 workflow 限制模型选择范围。
```

### 64. 如何防止越权调用工具

30 秒版：

```text
不能靠 Prompt。执行前必须在工具层根据 user_id、tenant_id、role、resource_id 做鉴权。模型即使生成了调用，也只有通过后端权限校验才会执行。
```

### 65. 高风险工具如何处理

30 秒版：

```text
高风险工具如退款、删除、发邮件、改配置，需要用户确认、权限校验、参数预览、幂等 key、审计日志和必要的人工审批。模型只能生成待确认动作。
```

### 66. 非幂等工具为什么不能简单重试

30 秒版：

```text
因为超时不代表失败，可能请求已经成功执行。简单重试可能导致重复下单、重复扣款、重复退款。必须使用 idempotency_key，并先查询上一次操作状态。
```

### 67. idempotency_key 有什么用

30 秒版：

```text
idempotency_key 用来保证同一个业务操作重复请求只执行一次。服务端根据 key 识别重复提交，返回第一次执行结果，避免网络重试或 Agent 重复调用造成副作用。
```

### 68. 工具调用日志应该记录什么

30 秒版：

```text
记录 request_id、session_id、user_id、tenant_id、tool_name、参数摘要、权限结果、开始结束时间、状态、错误码、幂等 key 和结果摘要。敏感字段要脱敏。
```

### 69. 如何把 OpenAPI 接口转成工具

30 秒版：

```text
可以解析 OpenAPI 的 path、method、parameters、requestBody 和 response schema 生成工具定义，但要筛选接口、简化 schema、补充 description、加权限和风险等级，不能把所有 API 无脑暴露给模型。
```

### 70. 工具结果返回给模型时要注意什么

30 秒版：

```text
结果要结构化、简洁、脱敏，并明确成功或失败状态。不要把异常栈、敏感字段或大量无关数据直接塞给模型。业务错误要转成模型能理解的 observation。
```
