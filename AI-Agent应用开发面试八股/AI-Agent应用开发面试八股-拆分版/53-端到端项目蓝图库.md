## 1. 近期 JD 反推的项目能力模型

公开招聘信息里，AI Agent 应用开发岗通常不只问“会不会 LangChain”，而是问你能不能把大模型能力接进业务系统。近期香港、内地和海外公开 JD 共同出现的关键词包括：

- RAG：文档解析、切分、向量化、召回、rerank、引用溯源、评测。
- Agent：任务规划、多步推理、工具调用、记忆、人机协同、多 Agent 协作。
- 工程化：Python/FastAPI、异步、SSE、缓存、限流、灰度、监控、日志。
- 治理：权限、审计、成本、质量评估、bad case 回流、Prompt 版本管理。
- 协议与集成：OpenAPI、RPC/gRPC、JSON-RPC、MCP、企业内部系统连接。
- 模型策略：Qwen/DeepSeek/Llama/GPT 等模型调用、路由、微调、量化、蒸馏。

可参考的公开趋势信号：

- 阿里云大模型应用开发相关 JD 提到 Prompt、知识库、AI Agent、Tool Calling、LLMOps、RAG 优化、MCP 生态。
- 腾讯相关岗位提到 Agent 系统设计、意图理解、对话管理、任务规划、工具调用、RAG/Plugin、LangChain/LlamaIndex。
- 海外 Agent Engineer JD 高频出现 LangGraph、MCP、RAG、memory、human-in-the-loop、evaluation、observability。

近期公开检索样例：

## 2. 选择项目蓝图的方法

如果你没有完整大模型项目，不要硬编“上线千万用户”。更稳的做法是：

```text
真实经历
  -> 找一个业务场景
  -> 叠加 RAG / Agent / Tool / 平台化能力
  -> 补齐工程指标
  -> 明确自己负责的模块
  -> 准备 bad case 和取舍
```

按岗位选蓝图：

| 目标岗位 | 首选蓝图 | 加分蓝图 | 面试表达重点 |
|---|---|---|---|
| 大模型应用开发 | 企业知识库 RAG | 客服/流程 Agent | 准确率、延迟、引用、业务闭环 |
| AI Agent 工程师 | 客服/流程 Agent | MCP/OpenAPI 工具平台 | 工具调用、状态机、失败恢复、权限 |
| RAG 工程师 | 企业知识库 RAG | 模型网关 | 召回、rerank、评测、索引更新 |
| 平台/架构方向 | 模型网关 | MCP/OpenAPI 工具平台 | 多租户、治理、成本、观测 |
| 后端转 AI | MCP/OpenAPI 工具平台 | 企业知识库 RAG | FastAPI、异步、协议、稳定性 |
| 算法偏应用 | 企业知识库 RAG | 垂直场景微调 | 数据、评测、微调与 RAG 取舍 |

## 3. 蓝图一：企业知识库 RAG

### 3.1 一句话介绍

```text
我做的是一个面向企业内部员工的知识库问答系统，把公司制度、产品文档、运维手册等非结构化资料接入 RAG 链路，支持权限隔离、引用溯源、答案评估和 bad case 回流。
```

### 3.2 业务背景

适合包装的真实背景：

- 公司内部文档多，员工查找信息慢。
- 客服/运营/销售需要快速定位标准答案。
- 产品、技术、运维文档散落在飞书、Confluence、网页、PDF、Word。
- 传统关键词搜索召回不稳定，用户问题和文档表达不一致。

不要这样讲：

```text
我就是调了 LangChain 做了一个知识库。
```

要这样讲：

```text
核心问题不是“能不能问答”，而是企业文档存在权限、更新、引用可信度和效果评估问题，所以我把项目拆成离线入库、在线检索生成、权限过滤、评测回流四条链路。
```

### 3.3 目标用户与场景

目标用户：

- 内部员工：查制度、流程、FAQ。
- 客服/售前：查产品参数、套餐规则、故障处理。
- 运维/研发：查 SOP、排障手册、接口文档。
- 管理者：看知识库命中率、bad case、热点问题。

核心场景：

- 自然语言问答。
- 多轮追问。
- 引用来源跳转。
- 文档上传和增量更新。
- 按部门/角色过滤可见文档。

### 3.4 MVP 功能

第一版只做：

- 文档上传：PDF、Word、Markdown、网页。
- 文档解析：提取正文、标题、页码、表格。
- chunk 切分：按标题、段落、token 长度混合切。
- embedding 入库：保存向量、原文、文档 ID、权限标签。
- 检索：向量召回 + BM25/关键词召回。
- rerank：交叉编码器或 LLM 轻量重排。
- 生成：带引用的 Prompt。
- 引用校验：答案必须能映射到 chunk。
- 日志：问题、召回片段、答案、用户反馈。

第二版再加：

- 多租户权限。
- 增量索引。
- 热点问题缓存。
- bad case 回流。
- 自动评测集。
- Prompt 版本管理。

### 3.5 架构模块

```text
文档源
  -> Ingestion Worker
  -> Parser
  -> Chunker
  -> Embedding Service
  -> Vector DB / BM25 Index
  -> Metadata DB

用户问题
  -> API Gateway
  -> Auth / Tenant Filter
  -> Query Rewrite
  -> Hybrid Retriever
  -> Reranker
  -> Prompt Builder
  -> LLM
  -> Citation Checker
  -> SSE Answer
  -> Feedback / Eval
```

关键存储：

- 对象存储：原始文档。
- 关系数据库：文档元数据、权限、任务状态、用户反馈。
- 向量数据库：chunk embedding、chunk metadata。
- 搜索引擎：BM25、关键词、字段过滤。
- 缓存：热点问题、embedding 缓存、rerank 缓存。

### 3.6 核心技术点

文档解析：

- PDF 要区分正文、页眉页脚、目录、表格、图片 OCR。
- 表格文档最好保留行列关系，不要简单拼成长文本。
- 文档要保留标题层级，用于 chunk 上下文补全。

chunk 策略：

```text
先按标题/章节粗切
  -> 再按 token 长度细切
  -> 保留 overlap
  -> 给每个 chunk 追加标题路径
  -> 对表格/代码/FAQ 做特殊切分
```

检索策略：

- 向量召回解决语义相近。
- BM25 解决专有名词、编号、接口名、错误码。
- metadata filter 解决部门、租户、文档类型。
- rerank 解决 topK 相关性排序。

生成策略：

- Prompt 明确只基于引用回答。
- 无依据时拒答或要求补充信息。
- 答案结构化输出：结论、依据、引用、注意事项。
- 引用与句子绑定，避免“看起来有引用但答非所问”。

### 3.7 指标体系

离线指标：

- Recall@K：正确 chunk 是否进入 topK。
- MRR/NDCG：正确证据排序是否靠前。
- Answer Faithfulness：答案是否忠于证据。
- Citation Accuracy：引用是否真的支持答案。
- Refusal Accuracy：无答案时是否拒答。

线上指标：

- 用户满意率。
- 追问率。
- 人工转接率。
- 首 token 延迟。
- RAG 生产护栏：越权召回率 = 0、citation_acl_pass_rate、p95_latency、no_answer_accuracy、index_freshness_lag。
- ACL 证据字段：tenant_id、doc_acl_version、filter_stage、citation_acl_pass。
- 总响应耗时。
- 单次问答成本。
- bad case 占比。

回答模板：

```text
我不会只看模型回答主观感觉，而是把 RAG 拆成检索质量和生成质量两层评估。检索层看 Recall@K、MRR、NDCG，生成层看忠实度、引用准确率、拒答准确率。线上再结合用户点赞、追问率和人工转接率判断是否真的解决业务问题。
```

### 3.8 常见 bad case 与修复

| bad case | 可能原因 | 修复思路 |
|---|---|---|
| 召回不到正确文档 | chunk 太粗/太细、query 表达不匹配 | query rewrite、多路召回、调整 chunk |
| 召回到了但排序靠后 | embedding 区分度不足 | rerank、领域 embedding、hard negative |
| 答案有幻觉 | Prompt 约束弱、上下文不足 | 强制引用、无依据拒答、citation checker |
| 引用不支持答案 | 生成和引用脱节 | 句子级引用、答案后校验 |
| 权限越权 | 检索前未过滤 metadata | tenant/role filter 前置 |
| 文档更新不生效 | 增量索引失败 | 索引任务状态机、版本号、重试 |
| 延迟过高 | topK 太大、rerank 太慢 | 分层召回、缓存、并行、流式输出 |


### 3.10 面试防守点

面试官问“你具体做了什么”：

```text
我主要负责在线问答链路和检索效果优化，包括 query rewrite、混合召回、rerank、Prompt 拼装、引用校验和日志评测。离线入库我也参与了 chunk 策略设计，但 OCR 和文档解析底层不是我独立完成的。
```

面试官问“为什么不用微调”：

```text
这个场景的知识更新频繁，而且要求引用溯源，优先用 RAG 更合适。微调更适合固定风格、固定任务或领域表达对齐；如果后续发现模型对公司术语理解差，可以考虑用少量 SFT 做术语和回答风格对齐，但事实知识仍然放在 RAG。
```

面试官问“怎么证明有效”：

```text
我会先构建一批标注问题，每题标正确证据 chunk 和参考答案。上线前看 Recall@K、MRR、引用准确率，上线后看满意率、追问率、人工转接率，并把 bad case 回流到切分、召回和 Prompt 版本。
```

### 3.11 公司表达侧重点

- 腾讯：强调业务场景、用户体验、权限、稳定性、成本。
- 阿里：强调平台化、链路抽象、规模化复用、业务指标。
- 百度：强调检索、排序、模型效果、评测体系。
- 字节：强调实验、数据闭环、延迟、A/B、快速迭代。
- 京东/美团：强调客服/供应链/运营场景、降本增效、SOP。

## 4. 蓝图二：客服/业务流程 Agent

### 4.1 一句话介绍

```text
我做的是一个面向客服或运营场景的业务流程 Agent，它能理解用户意图，结合知识库检索和业务工具调用，完成查询、生成、校验、提交等多步任务，并在高风险节点引入人工确认。
```

### 4.2 业务背景

典型场景：

- 客服需要同时查知识库、查订单、改工单。
- 运营需要生成活动文案、查询商品信息、提交审核。
- HR/财务/IT 运维有大量流程化问答和系统操作。
- 用户表达不标准，传统流程机器人覆盖率低。

核心问题：

```text
普通 Chatbot 只能回答问题，业务 Agent 要能在可控范围内执行动作。
```

### 4.3 MVP 功能

- 意图识别：问答、查询、创建、修改、投诉、转人工。
- RAG 问答：回答政策、SOP、FAQ。
- 工具调用：订单查询、库存查询、工单创建、邮件发送。
- 状态管理：保存任务进度、槽位、工具结果。
- 风险控制：写操作前二次确认。
- 人工接管：低置信度或高风险时转人工。
- 审计日志：记录每次模型决策、工具入参、工具结果。

### 4.4 架构模块

```text
用户
  -> Conversation API
  -> Session Store
  -> Intent Router
  -> Agent Orchestrator
       -> RAG Tool
       -> Business API Tools
       -> Validation Tool
       -> Human Handoff
  -> Response Generator
  -> Audit / Eval / Feedback
```

如果用 LangGraph，可以这样拆节点：

```text
START
  -> classify_intent
  -> retrieve_policy
  -> decide_action
  -> call_tool
  -> validate_result
  -> need_human?
  -> generate_response
  -> END
```

状态字段：

```python
class AgentState(TypedDict):
    user_id: str
    session_id: str
    messages: list[dict]
    intent: str
    slots: dict
    retrieved_docs: list[dict]
    tool_calls: list[dict]
    tool_results: list[dict]
    risk_level: str
    need_human: bool
    final_answer: str
```

### 4.5 工具设计原则

工具 schema 要小而明确：

```text
工具名：query_order
用途：根据订单号查询订单状态
输入：order_id
输出：status、pay_time、shipping_status、after_sales_status
权限：只能查询当前用户自己的订单
风险：只读，低风险
```

不要把一个工具设计成万能接口：

```text
bad：execute_sql(sql)
good：query_order(order_id)、create_ticket(type, desc)、check_refund_policy(order_id)
```

工具调用前要做：

- 参数校验。
- 权限校验。
- 幂等键。
- 超时控制。
- 重试策略。
- 风险分级。
- 审计日志。

### 4.6 Agent 编排取舍

什么时候用简单工作流：

- 流程固定。
- 工具数量少。
- 风险高，需要强控制。
- 业务规则清晰。

什么时候用 Agent：

- 用户表达复杂。
- 工具选择不固定。
- 需要多步推理和动态决策。
- 有人工兜底和审计。

标准回答：

```text
我不会所有流程都上自由 Agent。高风险、强流程的业务更适合工作流；Agent 主要放在意图理解、工具选择、参数补全和异常分支处理上。这样既能利用大模型的灵活性，又不会把核心业务控制权完全交给模型。
```

### 4.7 指标体系

- 意图识别准确率。
- 工具选择准确率。
- 工具参数正确率。
- 任务完成率。
- 人工接管率。
- 错误执行率。
- 平均处理时长。
- 用户满意率。
- 单次会话成本。

### 4.8 常见 bad case 与修复

| bad case | 原因 | 修复 |
|---|---|---|
| 选错工具 | 工具描述重叠 | 工具分组、few-shot、router |
| 参数填错 | 槽位抽取不稳 | Pydantic 校验、二次确认 |
| 重复提交 | 重试无幂等 | idempotency key、状态机 |
| 越权查询 | 用户身份未绑定 | 工具层权限校验 |
| 自作主张执行 | 风险分级缺失 | 写操作 human confirmation |
| 多轮状态丢失 | session 管理弱 | 持久化 state、checkpoint |
| 成本过高 | 每步都调用大模型 | 小模型分类、缓存、规则前置 |

### 4.9 简历 bullet

```text
设计并实现客服流程 Agent，基于意图识别、RAG 问答和业务工具调用完成订单查询、政策解释、工单创建等多步任务，引入风险分级、人工确认和审计日志，降低人工处理压力。
```

```text
使用 LangGraph 抽象客服 Agent 状态机，将意图识别、知识检索、工具调用、结果校验和人工接管拆分为可观测节点，支持失败重试、checkpoint 和 bad case 回放。
```

### 4.10 面试防守点

问“Agent 出错怎么办”：

```text
我会把错误分三类：理解错、工具错、执行错。理解错靠意图置信度和澄清问题；工具错靠 schema、参数校验和超时重试；执行错靠权限、幂等、人工确认和审计。高风险写操作一定不让模型直接无确认执行。
```

问“为什么用 LangGraph”：

```text
这个项目有多步状态和异常分支，不只是线性 chain。LangGraph 更适合把流程拆成节点和边，状态显式传递，也方便 checkpoint、回放和人工接管。简单问答我不会强行用 LangGraph。
```

## 5. 蓝图三：MCP/OpenAPI 工具平台

### 5.1 一句话介绍

```text
我做的是一个面向企业内部 Agent 的工具接入平台，把已有 OpenAPI/RPC 服务包装成可被大模型安全调用的 Tool，并通过 MCP 或统一协议暴露给不同 Agent 使用。
```

### 5.2 业务背景

很多公司不是没有系统，而是系统太多：

- CRM、工单、订单、库存、财务、数据平台都有 API。
- 每个 Agent 重复接工具，成本高。
- 工具描述、权限、审计、限流没有统一规范。
- 模型直接调用内部 API 风险大。

项目价值：

```text
把“某个 Agent 的临时工具”升级成“企业 Agent 工具底座”。
```

### 5.3 MVP 功能

- OpenAPI 导入：解析 paths、methods、schemas。
- Tool 生成：将 API 转成工具名、描述、参数 schema。
- 权限配置：按用户、租户、角色、工具分配权限。
- Mock 调试：在不上真实业务系统时测试工具。
- 调用代理：统一鉴权、限流、超时、重试、日志。
- MCP Server：向支持 MCP 的客户端/Agent 暴露工具。
- 审计面板：查看谁在什么时候调用了什么工具。

### 5.4 架构模块

```text
OpenAPI / RPC Definition
  -> Tool Registry
  -> Schema Normalizer
  -> Permission Center
  -> Tool Gateway
       -> Auth
       -> Rate Limit
       -> Param Validation
       -> API Adapter
       -> Audit Log
  -> MCP Server / SDK
  -> Agent Runtime
```

核心表：

```text
tool_definition(id, name, description, input_schema, output_schema, risk_level)
tool_version(tool_id, version, schema_hash, status)
tool_permission(tool_id, subject_type, subject_id, allow_actions)
tool_call_log(call_id, user_id, tool_id, input, output, status, latency, trace_id)
```

### 5.5 OpenAPI 转 Tool 的关键点

转换规则：

- operationId 优先作为工具名。
- summary/description 作为工具描述基础。
- parameters + requestBody 合并成 input_schema。
- response schema 转成 output_schema。
- path/query/header/body 参数要明确来源。
- 高风险接口要标记 risk_level。

工具描述要补充：

```text
这个工具什么时候用
什么时候不能用
输入字段的业务含义
输出字段怎么解释
是否只读
是否需要用户确认
```

常见坑：

- API 描述太工程化，模型看不懂业务语义。
- 同名字段在不同接口含义不同。
- response schema 缺少错误码说明。
- 写接口没有幂等键。
- 权限只在 Agent 层做，没有在工具网关做。

### 5.6 MCP 表达方式

面试中可以这样解释 MCP：

```text
OpenAPI 更像是描述 HTTP API 的规范，RPC/gRPC 更像服务间调用方式，MCP 更像是给大模型应用接上下文和工具的一套协议。我的理解是，MCP 的价值在于让 Agent 不直接散落地适配各种工具，而是通过标准化 server 暴露 tools/resources/prompts，客户端按统一方式发现和调用。
```

MCP 适合：

- IDE/本地工具接入。
- 企业内部工具统一暴露。
- 多 Agent 复用同一批工具。
- 将文件、数据库、业务系统作为上下文资源。

MCP 不等于：

- 不等于模型本身。
- 不等于 OpenAPI 替代品。
- 不等于自动解决权限问题。
- 不等于所有工具都应该开放给模型。

### 5.7 指标体系

- 工具接入耗时。
- 工具调用成功率。
- 参数校验失败率。
- 平均延迟。
- 超时率。
- 高风险调用拦截数。
- 权限拒绝数。
- 工具复用数。
- Agent 接入数。
- MCP/A2A 平台指标：tool_schema_change_fail_rate、unauthorized_tool_blocked、delegation_scope_violation、result_schema_pass_rate。

### 5.8 简历 bullet

```text
设计企业 Agent 工具接入平台，支持 OpenAPI 导入、Tool schema 生成、权限配置、调用代理和审计日志，将多个业务 API 统一暴露给 Agent 编排层复用。
```

```text
实现 MCP Server 原型，封装内部查询、工单、知识库等工具能力，支持工具发现、参数校验、权限拦截和调用链追踪，降低 Agent 接入业务系统成本。
```

### 5.9 面试防守点

问“OpenAPI、RPC、MCP 的关系”：

```text
OpenAPI 解决 HTTP API 怎么描述；RPC 解决服务之间怎么调用；MCP 解决大模型应用怎么以统一方式发现和使用工具、资源和 Prompt。它们不是互斥关系，企业里常见做法是已有业务服务通过 HTTP/RPC 暴露，再由工具平台包装成 Tool，最后通过 MCP 或 SDK 给 Agent 使用。
```

问“怎么防止工具被滥用”：

```text
我会分四层控制：工具注册时标风险等级；调用前做用户和租户权限校验；写操作要求确认和幂等；调用后记录审计日志和 trace。模型的选择只是建议，真正能不能执行必须由工具网关判断。
```

## 6. 蓝图四：模型网关/大模型应用平台

### 6.1 一句话介绍

```text
我做的是一个模型网关和大模型应用平台，为不同业务应用统一提供模型调用、Prompt 版本、流式响应、限流熔断、成本统计、评测和灰度能力。
```

### 6.2 业务背景

典型问题：

- 不同团队各自接模型，密钥、日志、成本分散。
- 模型更新频繁，切换成本高。
- Prompt 没版本管理，线上效果难回滚。
- 缺少统一评测，无法判断新模型是否更好。
- 流式响应、限流、重试、fallback 每个项目重复写。

平台价值：

```text
把“单个应用调模型”升级成“多个业务共享的大模型基础设施”。
```

### 6.3 MVP 功能

- 统一模型 API：OpenAI-compatible 或内部统一协议。
- 多模型路由：按业务、成本、延迟、能力选择模型。
- Prompt 管理：模板、变量、版本、灰度。
- 流式响应：SSE/WebSocket。
- 限流熔断：按租户、应用、模型维度。
- fallback：主模型失败切备用模型。
- 观测：token、延迟、错误码、成本、trace。
- 评测：离线评测集、线上抽样、A/B。

### 6.4 架构模块

```text
业务应用
  -> Model Gateway API
  -> Auth / Tenant / Quota
  -> Prompt Service
  -> Router
  -> Provider Adapter
       -> Qwen / DeepSeek / GPT / Claude / Local Model
  -> Stream Aggregator
  -> Logging / Metrics / Billing
  -> Eval Platform
```

核心数据：

```text
app(id, owner, quota, enabled_models)
prompt(id, app_id, template, version, status)
model_provider(id, name, endpoint, auth_type, capabilities)
model_call_log(trace_id, app_id, model, tokens, latency, cost, status)
eval_case(id, task_type, input, expected, tags)
eval_result(case_id, model, prompt_version, score, error_type)
```

### 6.5 路由策略

简单路由：

- 默认模型。
- 按应用选择模型。
- 按任务类型选择模型。
- 失败 fallback。

进阶路由：

- 短文本用低成本模型。
- 复杂推理用强模型。
- 敏感数据走私有模型。
- 高峰期按配额降级。
- 根据历史质量和延迟动态选择。

回答模板：

```text
模型路由不是单纯按价格选，而是在质量、延迟、成本和合规之间做取舍。比如客服摘要可以用低成本模型，复杂问答或代码生成走强模型，敏感数据走私有化模型，主模型超时则 fallback 到备用模型，并记录 trace 方便复盘。
```

### 6.6 Prompt 版本管理

需要能回答：

- Prompt 如何上线？
- Prompt 如何灰度？
- Prompt 如何回滚？
- Prompt 修改后怎么评测？
- 线上 bad case 怎么关联到 Prompt 版本？

推荐流程：

```text
创建 Prompt 草稿
  -> 本地调试
  -> 离线评测
  -> 小流量灰度
  -> 观察指标
  -> 全量发布
  -> bad case 回流
```

### 6.7 观测与成本

必须记录：

- app_id。
- user_id/tenant_id。
- model。
- prompt_version。
- input_tokens/output_tokens。
- latency。
- error_code。
- retry_count。
- cost。
- trace_id。

常见追问：

```text
如果某天成本突然升高，你怎么排查？
```

回答：

```text
我会按 app、tenant、model、prompt_version 四个维度拆 token 和请求量。先看是请求量上涨还是单请求 token 变长，再看是否有 Prompt 版本变更、RAG 上下文过长、重试率升高或某个业务异常循环调用。定位后可以做限流、上下文压缩、缓存、降级或回滚 Prompt。
```

### 6.8 简历 bullet

```text
参与模型网关建设，封装多模型调用、SSE 流式响应、限流熔断、fallback、token 成本统计和调用链日志，为多个业务应用提供统一大模型接入能力。
```

```text
设计 Prompt 版本与评测流程，支持 Prompt 草稿、离线评测、小流量灰度、线上指标观测和 bad case 回流，降低模型/Prompt 迭代对业务稳定性的影响。
```

### 6.9 面试防守点

问“模型网关和普通封装有什么区别”：

```text
普通封装只是把不同模型 API 包成统一调用；模型网关还要承担多租户鉴权、配额、路由、限流、fallback、成本统计、Prompt 版本、评测和审计。它更像大模型应用的基础设施，而不是一个 SDK wrapper。
```

问“怎么做灰度”：

```text
可以按 app、tenant、用户比例或请求标签灰度。灰度期间同时记录 prompt_version、model_version 和输出评分，对比错误率、延迟、满意率、成本和 bad case 类型。如果核心指标变差，就快速回滚到旧版本。
```

## 7. 四个蓝图的关系

```text
企业知识库 RAG
  -> 解决知识 grounding 和引用可信
  -> 可作为 Agent 的 RAG Tool

客服/业务流程 Agent
  -> 解决多步任务和工具执行
  -> 依赖 RAG、Tool Gateway、模型网关

MCP/OpenAPI 工具平台
  -> 解决企业工具标准化接入
  -> 给 Agent 提供安全、可审计的工具层

模型网关/大模型平台
  -> 解决模型调用、成本、评测、Prompt、灰度
  -> 给 RAG 和 Agent 提供统一模型底座
```

面试里可以把它们串成一张大图：

```text
业务应用
  -> Agent 编排层
      -> RAG 知识工具
      -> MCP/OpenAPI 业务工具
  -> 模型网关
  -> 评测/观测/审计
```

最强表达：

```text
我不是把 RAG、Agent、MCP、模型网关看成孤立技术。RAG 负责给模型可靠知识，Agent 负责任务编排，MCP/OpenAPI 工具平台负责连接企业系统，模型网关负责统一模型调用和治理。真正落地时，这四块要一起考虑权限、评测、成本和可观测性。
```
