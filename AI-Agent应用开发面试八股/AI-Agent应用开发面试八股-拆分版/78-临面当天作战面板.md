# 78-临面当天作战面板

> 目标：面试当天最后 30 分钟只看这一页，不再翻完整资料。  
> 核心原则：临面前不扩展新知识，只激活上场顺序、救场句、反问和最高风险 B/C。

适用场景：

- 面试前 30 分钟 / 10 分钟 / 3 分钟。
- 已经准备过资料，但临场开始紧张。
- 临时被通知加面，不知道最后该看什么。
- 刚做完模拟面，想快速回到上场状态。

如果你是第一次打开这份文件，只记住一句话：

```text
最后 30 分钟不再学习，只做启动、自证、救场和反问。
```

进入 78 前只按剩余时间检查：

- 2 小时用户：只需要 `80` 一页上场包，且已经按 `74` 停止继续扩展。
- 半天用户：确认 13 项口径、Top2 风险、救场和反问已摘进 `80`。
- 1 天用户：再确认 `77` Top2 弱点和 `66` 验收已完成。
- 少于 30 分钟才第一次打开：直接用本页 `0` 节写 3 分钟应急包。

如果距离面试少于 30 分钟，不再打开以上文件，只看本页 `0-4` 节和手头的 `80` 上场包。

---

## 0. 没有 80 上场包时

如果是临时通知，手头还没有 `80`，不要跳出去补完整工单。用 3 分钟在这里写一个应急包：

```markdown
# 3 分钟应急包

- 公司 / 岗位 / 轮次：
- 1 分钟开场第一句：
- 2 分钟项目第一句：
- 最高风险题：
- 1 个真实 bad case：
- 2 个反问：
  1.
  2.
```

写完立刻进入下面的最后 30 分钟流程。

---

## 1. 最后 30 分钟

只做 6 件事：

| 时间 | 动作 | 产出 |
|---|---|---|
| 0-5 分钟 | 看面试信息 | 公司、岗位、轮次、面试官类型 |
| 5-10 分钟 | 过 1 分钟自我介绍 | 开场不空 |
| 10-15 分钟 | 过 2 分钟项目入口 | 项目不散 |
| 15-20 分钟 | 看最高风险 B/C | 只补一个短板 |
| 20-25 分钟 | 复述 `80` 已选公司口径 | 只说 1 句话，不打开公司资料 |
| 25-30 分钟 | 过救场和反问 | 卡壳能接住，收尾有问题 |

绝对不要做：

- 打开新资料。
- 搜新面经。
- 背长答案。
- 临时改简历项目。
- 重写系统设计。

---

## 2. 最后 10 分钟

只念这 5 句：

```text
1. 我先讲结论，再展开链路。
2. 项目要讲背景、职责、链路、难点、指标和边界。
3. 不确定的问题先澄清，不硬编。
4. 被追问时回到工程闭环：权限、评测、观测、成本、兜底。
5. 收尾反问要贴合公司、岗位和轮次。
```

然后只确认 4 个东西：

- [ ] 自我介绍第一句。
- [ ] 项目入口第一句。
- [ ] 最高风险题的 30 秒版。
- [ ] 2 个反问。

最后 10 分钟禁止看第 `5/6/7` 节；如果还想翻答案，说明该去做呼吸和启动句了。

---

## 3. 最后 3 分钟

不要再看资料，只做呼吸和启动句。

启动句：

```text
您好，我先简单介绍一下自己。我主要关注 AI Agent / RAG / 大模型应用工程化，做过企业知识库、工具调用和相关后端治理方向的项目。
```

如果面试官让你直接讲项目：

```text
我介绍一个和岗位最相关的项目。它的目标是把分散的文档和业务工具统一成自然语言入口，我主要负责 RAG 检索、工具调用治理和后端接口这一段。
```

如果面试官先问八股：

```text
我先给一个主干答案，再结合项目讲一下落地时会遇到的坑。
```

## 4. 面试中救场面板

### 4.1 没听清

```text
我确认一下，您主要想问的是概念区别，还是在项目里怎么落地？
```

### 4.2 不会

```text
这个点我没有完整实践过，我先按我的理解说一下边界。如果要在生产里做，我会优先考虑权限、评测、观测和兜底。
```

### 4.3 回答太散

```text
我收一下，核心就是三点：第一是主链路，第二是风险控制，第三是上线后的评测和监控。
```

### 4.4 被质疑是 Demo

```text
这个项目目前确实还没有到完整生产级，所以我不会夸大。已经做的是核心链路、基础评测和日志；如果上线，我会优先补权限体系、灰度、监控、成本控制和安全评测。
```

### 4.5 被追问指标

```text
如果是 Demo 或内部验证阶段，我不会编线上指标。我会讲离线评测、人工反馈、bad case 数量、延迟和成本；如果上线，再补用户采纳率、无答案率、投诉率和人工接管率。
```

## 5. 附录：公司风格速切

本节不是最后 30 分钟通读清单。面前只允许把其中 1 句话提前摘进 `80`，最后 30 分钟只复述已选口径。

| 公司/方向 | 临场优先词 |
|---|---|
| 腾讯 | 用户体验、稳定性、反馈、人工接管、兜底 |
| 阿里/阿里云 | 平台化、多租户、权限、审计、私有化、复用 |
| 百度 | RAG、搜索、trace、评测、Data Agent、模型边界 |
| 字节 | 指标、实验、成本、延迟、灰度、回滚 |
| 美团/京东 | 订单、交易风险、高风险写操作、峰值流量 |
| ToB/云厂商 | 数据不出域、合规、部署边界、日志脱敏 |

一句话切换：

```text
如果按贵团队这类场景，我会把重点从“模型能不能答”转到“上线后是否可控”，也就是权限、评测、观测、成本和失败兜底。
```

## 6. 附录：最高风险 B/C 命中时才看 1 条

本节不是最后 30 分钟通读清单。只有 `80` 或 `77` 已经标出最高风险 B/C，且该风险正好命中下面某一条时，才允许看 1 条。

```text
规则：只看 1 条 -> 立刻口述 1 遍 -> 回到第 1/2/3 节。
```

### RAG 召回不准

```text
我会先分层定位：文档解析和切分有没有丢信息，query rewrite 是否正确，向量和 BM25 召回是否命中，rerank 后证据是否进入上下文，最后看生成是否忠实使用证据。修复时不会只调 prompt，而是用 bad case 和评测集验证每一层。
```

### Agent vs Workflow

```text
Workflow 是流程固定、状态明确的编排；Agent 更强调模型根据上下文选择下一步动作。生产里我不会让 Agent 完全自由行动，而是把工具、状态、最大步数、权限、确认和 fallback 都约束住。
```

### Tool Calling 安全

```text
工具调用不能只靠 prompt。工具层要做 schema 校验、鉴权、风险分级、超时、幂等和审计。查询类工具可以自动执行，高风险写操作必须确认或人工审批。
```

### MCP

```text
MCP 解决的是模型应用和外部工具/资源的连接协议问题，不是完整安全系统。安全还要靠 Host、Client、Server 和底层工具共同实现，包括授权、roots 边界、工具白名单、用户确认和审计。
```

### MCP vs A2A

```text
MCP 更像模型应用连接工具和资源的上下文协议，重点是工具、资源、roots、授权和审计；A2A 更强调不同 Agent 之间的任务委派、能力发现和结果交付。两者都不能替代权限治理，生产里要关注身份传递、授权范围、委派审计和最终结果验收。
```

### 代码执行 Agent 安全

```text
浏览器、终端或代码执行 Agent 的风险不只是工具调用失败，而是越权读文件、执行危险命令、泄露凭据和改坏代码。我的控制点会放在沙箱、路径 allowlist、命令白名单、网络边界、人工确认、diff 审计和可回滚快照。
```

### Computer Use / Browser Agent

```text
Browser Agent 不能让模型“看见页面就随便点”。我会把观察和动作分开：观察用 DOM、截图或 accessibility tree，但网页内容都标成不可信数据；动作只允许白名单，跨域、下载、提交表单、付款、删除和发消息必须确认；会话用临时 profile 和凭据隔离；trace 记录 URL、selector、截图摘要、动作、审批和接管结果，低置信度直接转人工。
```

### 评测进 CI/CD

```text
我会把 RAG/Agent 评测做成发布门禁：每次 prompt、工具 schema、检索配置或模型版本变化，都跑 golden set 和 bad case 回归；指标看任务成功率、faithfulness、安全通过率、延迟和成本，低于阈值就阻止发布或灰度。
```

### 上下文工程

```text
上下文不是越长越好。生产里我会区分短期对话、长期记忆和结构化状态：最近消息保留，旧历史摘要，关键控制字段如 step_count、approval_status、tool_result 单独结构化保存；工具结果先脱敏和压缩，再进模型上下文。
```

### Memory Governance

```text
长期记忆不是“用户说过什么都存”。我会先区分短期上下文、结构化状态和长期偏好；写入前检查来源、敏感级别、用户确认、tenant scope 和 TTL；读取时按任务相关性和权限过滤；用户要求删除时同步主库、向量索引和缓存，只保留脱敏审计记录。未确认事实和敏感信息不能写入长期记忆。
```

### Agent 成功率

```text
我不会只看模型回答像不像，而是先定义任务成功：是否完成用户目标、是否调用了正确工具、是否遵守权限、是否需要人工接管、是否在成本和延迟预算内。失败再按规划、检索、工具、模型生成、权限和外部系统分层归因。
```

### 长任务 Agent

```text
长任务 Agent 不能占着一次 HTTP 请求硬跑。我会把它做成 job 系统：提交返回 job_id，后台 worker 执行，状态包括 pending、running、waiting_approval、succeeded、failed、cancel_pending、cancelled；每个关键节点写 checkpoint。用户取消时先标记 cancel_requested，在安全点停止；如果已经执行外部写操作，要补偿、回滚或转人工。
```

### Agent SLO / 告警

```text
我会把线上 SLO 分成质量、稳定性、成本和安全四类：task_success_rate、tool_call_accuracy、p95_latency、timeout_rate、queue_lag、cost_per_successful_task、unsafe_action_rate。告警触发后按 tenant、model_version、prompt_version 和 tool_version 聚合，关联最近 change_id 和 trace，再决定降级、回滚、限流或人工接管。
```

### 成本降低 50%

```text
我会先看成本来源：模型 token、检索和 rerank、工具调用、重试和长上下文。优化顺序是缓存高频结果、压缩上下文、调小 topK、并行可并行步骤、按任务路由大小模型，最后才考虑牺牲效果的降级。
```

### Trace 记录什么

```text
Trace 至少记录 request_id、用户意图、召回文档、rerank 分数、工具名和参数、模型版本、token、耗时、错误码、人工接管和最终结果。这样出问题时能判断是检索没命中、工具失败、权限拒绝、模型幻觉还是外部系统超时。
```

### Data Agent

```text
Data Agent 不能让模型直接查库。我会先做 schema linking 和指标口径匹配，生成 SQL 后经过 AST 校验、只读限制、表字段白名单、行列权限、limit、超时和 cost 控制，再返回 SQL、口径、时间范围和图表解释。
```

### 实时 / 语音 / 多模态 Agent

```text
实时 Agent 的关键不是把语音转文字后丢给模型，而是低延迟、可打断、可回放和可确认。我会按 turn_id 记录 partial/final transcript、ASR 置信度、barge-in、工具动作和审批结果；高风险动作必须二次确认，ASR 低置信度或多模态证据冲突时降级成人工确认。
```

### 项目是不是你做的

```text
我可以具体讲我负责的部分：RAG 检索链路、工具调用治理和后端接口。比如接口入参、trace 字段、bad case 记录、工具风险分级和评测指标这些细节，是我准备重点展开的。
```

### 生产级 Agent 证据

```text
我不会只说“接了大模型”。我会按生产链路讲证据：输入输出 schema、工具风险分级、trace 字段、评测集、bad case 回归、延迟和成本指标，以及高风险动作的人审和回滚。这样面试官追问到稳定性、安全或上线价值时，我都有可验证的工程抓手。
```

### 框架怎么选

```text
简单链路我会优先用显式 workflow，状态清楚、好测试、好回滚；需要多步决策、工具选择和中断恢复时才引入 LangGraph 这类状态图编排。框架不是亮点，亮点是能否把状态、权限、评测、观测和失败兜底管住。
```

## 7. 反问速选

### 技术一面

```text
团队目前的 AI 应用更偏 RAG 知识库、Agent 工具调用，还是模型平台能力建设？
```

### 二面 / 系统设计

```text
如果加入团队，这个岗位更需要我优先补齐业务落地能力，还是平台工程和稳定性治理能力？
```

### 主管面

```text
团队现在衡量 AI 应用价值时，更关注用户体验、效率提升、成本控制，还是平台复用？
```

### ToB / 云厂商

```text
客户侧在落地大模型应用时，目前最大的阻力是数据安全、效果评测、系统集成，还是私有化交付？
```

## 9. 最终速背

1. 临面前不看新资料，只激活已有答案。
2. 开场讲方向，项目讲职责，追问讲闭环。
3. 不会就澄清边界，不要硬编。
4. 公司风格要切换，但不要编经历。
5. 结束后立刻复盘，把真实问题沉淀回资料库。
