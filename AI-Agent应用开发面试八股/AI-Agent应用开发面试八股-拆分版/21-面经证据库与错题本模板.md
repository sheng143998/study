# 面经证据库与错题本模板

> 用法：这份不是用来背的，而是用来持续维护。每看到一篇牛客/Boss/JD/面经，或每做一次模拟面，都按表格记录，逐步形成自己的高频题证据库。

## 1. 为什么需要证据库

公开面经最大的问题是：

- 真假混杂。
- 岗位不一定匹配。
- 时间可能过旧。
- 很多题是培训号拼接。
- 同一家公司不同部门差异很大。

所以不要把所有面经等权看待。建议按“证据强度”记录。

## 2. 面经可信度分级

| 等级 | 判断标准 | 使用方式 |
|---|---|---|
| S | 有明确公司、岗位、轮次、时间、题目链路，且问题和 JD 高度匹配 | 重点纳入押题 |
| A | 公司和岗位明确，题目具体，但缺少轮次或时间 | 作为高频参考 |
| B | 题目具体，但公司/岗位信息模糊 | 只用于补充题型 |
| C | 只有泛泛题单，没有上下文 | 低权重参考 |
| D | 明显拼接、概念错误、营销味强 | 不纳入 |

## 5. 面经处理流程

看到一篇面经后按这个流程处理：

```text
1. 记录来源、公司、岗位、时间。
2. 判断可信度 S/A/B/C/D。
3. 把题目拆成模块：RAG、Agent、Python、后端、协议、系统设计。
4. 看是否已经在题目归类表里。
5. 如果重复出现，增加频次和公司。
6. 如果是新题，补到题库或追问链。
7. 如果自己不会，加入错题本。
```

## 8. 示例：RAG 召回不准

```text
问题：
RAG 召回不准怎么办？

我当时怎么答的：
调大 top_k，换 embedding 模型。

为什么不够好：
回答太单点，没有按链路排查，也没提评测集、hybrid search、rerank、metadata filter。

标准答案骨架：
1. 先基于 badcase 建评测集，区分没召回、排错、生成没用证据。
2. 数据侧检查解析、清洗、chunk、元数据。
3. Query 侧做 rewrite、多查询或上下文补全。
4. 检索侧做 vector + BM25 hybrid search，调整 top_k 和过滤条件。
5. 排序侧加入 rerank。
6. 用 Recall@K、MRR、NDCG 和人工评估验证。

项目结合版：
在企业制度文档里，我会特别关注版本和部门权限，因为很多召回错误不是语义问题，而是同主题不同版本文档混淆。

下次 30 秒回答：
我会先用 badcase 建评测集，然后按数据解析、chunk、query rewrite、embedding、hybrid search、rerank 和 metadata filter 逐层排查，不会只调 top_k。
```

## 9. 示例：Agent 写操作重复执行

```text
问题：
如果 Agent 重复调用退款工具怎么办？

我当时怎么答的：
限制最大调用次数。

为什么不够好：
最大次数只能减少循环，不能保证非幂等写操作安全。退款可能第一次超时但实际成功，第二次重试导致重复退款。

标准答案骨架：
1. 写操作不能完全交给模型自动执行。
2. 执行前必须用户确认。
3. 工具层做权限校验。
4. 使用 idempotency_key 防重复提交。
5. 查询上一次操作状态再决定是否重试。
6. 记录审计日志，必要时人工介入。

下次 30 秒回答：
退款这类非幂等操作不能简单自动重试。模型只生成调用意图，执行前要用户确认，后端带 idempotency_key，并查询上一次状态，避免超时后重复执行。
```

## 12. 每周维护节奏

如果你准备周期比较长，建议每周维护一次：

```text
周一：收集 5 篇 JD/面经，更新证据库。
周二：把新增题目归类到题库。
周三：补 3 道标准回答。
周四：做 1 套模拟面试。
周五：整理错题本。
周末：重讲项目 3 分钟版和系统设计图。
```

## 13. 面经真假快速判断

优先相信：

- 有连续追问链。
- 问题和岗位 JD 高度匹配。
- 有明确轮次和时间。
- 题目涉及项目、工程和系统设计。
- 追问细节具体，例如“权限过滤在召回前还是召回后”。

谨慎对待：

- 只有“LangChain 八股 100 题”但无来源。
- 题目覆盖所有方向但没有岗位上下文。
- 答案明显概念错误。
- 大量堆名词，没有工程追问。
- 标题夸张，内容重复度高。
