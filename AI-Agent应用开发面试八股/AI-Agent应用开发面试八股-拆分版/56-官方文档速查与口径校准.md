# 官方文档速查与口径校准

> 目标：避免只背二手八股，把高频技术点和官方口径对齐。  
> 用法：临面前快速扫一遍“不要怎么说 / 应该怎么说”，防止在 LangGraph、MCP、Tool Calling、OpenAPI 这类概念上说偏。

注意：

- 官方文档用于校准概念边界，不代表面试只会问官方原文。
- 招聘 JD 和公开面经用于判断趋势，不用于证明某家公司一定考某道题。
- 框架 API 更新快，真正写代码前要回官方文档确认版本。

## 1. LangChain

官方入口：

- LangChain Python 文档：https://docs.langchain.com/oss/python/langchain/overview
- LangChain v0.3 Python 文档：https://python.langchain.com/docs/introduction/

面试常问：

- LangChain 解决什么问题？
- LCEL 是什么？
- Chain、Tool、Retriever、Agent 的关系？
- LangChain 和 LangGraph 区别？

不要这么说：

```text
LangChain 就是用来做 Agent 的框架。
```

应该这么说：

```text
LangChain 更像是大模型应用开发框架，提供模型调用、Prompt、Retriever、Tool、结构化输出、链式编排等能力。简单线性流程用 LangChain 就够；复杂多步状态、分支、checkpoint、人机协同时更适合 LangGraph。
```

面试防守点：

- LangChain 不等于 Agent。
- LangChain 不等于 RAG，但可以组装 RAG。
- 框架只是工程抽象，核心仍是数据、Prompt、检索、工具、评测和治理。

## 2. LangGraph

官方入口：

- LangGraph 文档：https://docs.langchain.com/oss/python/langgraph/overview
- LangGraph GitHub：https://github.com/langchain-ai/langgraph

面试常问：

- LangGraph 和 LangChain 区别？
- StateGraph 是什么？
- state 怎么设计？
- checkpoint 有什么用？
- interrupt / human-in-the-loop 怎么理解？

不要这么说：

```text
LangGraph 就是高级版 LangChain。
```

应该这么说：

```text
LangGraph 更偏有状态、多步骤、可恢复的 Agent/workflow 编排。它把流程建模成图，节点负责执行任务，边负责控制流，state 在节点间传递。相比线性 chain，它更适合多轮状态、条件分支、失败重试、checkpoint 和人工接管。
```

面试防守点：

- state 不是随便塞 messages，要包含 intent、slots、tool_calls、retrieved_docs、risk_level、final_answer 等业务状态。
- checkpoint 的价值是恢复、回放、人工介入，不只是“保存一下历史”。
- 简单 RAG 问答不一定要用 LangGraph。

## 3. Model Context Protocol

官方入口：

- MCP 官方介绍：https://modelcontextprotocol.io/docs/getting-started/intro
- MCP 规范：https://modelcontextprotocol.io/specification

面试常问：

- MCP 是什么？
- MCP 和 OpenAPI、RPC 的关系？
- tools、resources、prompts 分别是什么？
- MCP 能不能解决权限问题？
- 企业里怎么落地 MCP？

不要这么说：

```text
MCP 是一种新的 API 协议，可以替代 OpenAPI。
```

应该这么说：

```text
MCP 是面向大模型应用的上下文和工具接入协议。它让客户端可以用统一方式发现和调用 server 暴露的 tools、resources、prompts。OpenAPI 主要描述 HTTP API，RPC/gRPC 主要解决服务间调用，MCP 更关注模型应用如何接入工具和上下文。企业里可以把已有 HTTP/RPC 服务包装成工具，再通过 MCP 给 Agent 使用。
```

面试防守点：

- MCP 不自动解决权限、安全、审计。
- MCP server 暴露什么工具，需要业务侧做风险分级。
- 工具执行权限应该在工具网关/业务服务层强校验。
- MCP 更像标准化接入层，不是模型推理框架。

## 4. A2A / Agent-to-Agent

参考入口：

- IBM A2A 解释：https://www.ibm.com/think/topics/agent2agent-protocol
- Linux Foundation A2A 项目：https://www.linuxfoundation.org/press/linux-foundation-launches-the-agent2agent-protocol-project-to-enable-secure-intelligent-communication-between-ai-agents

面试常问：

- A2A 和 MCP 分别解决什么？
- 多 Agent 委派任务时怎么传递权限和责任边界？
- A2A 能不能替代工具网关和审计？

不要这么说：

```text
A2A 是新版 MCP，能解决 Agent 安全协作。
```

应该这么说：

```text
A2A 更偏 Agent-to-Agent 的任务委派、能力发现、状态同步和结果交付；MCP 更偏 Agent-to-tool/data/resource 的标准化接入。二者是互补关系，都不替代权限治理、审批、审计和结果验收。
```

面试防守点：

- A2A task contract 至少要有 caller、delegate、scope、deadline、result_schema 和 approval_id。
- 协议层只定义通信和交付边界，业务层仍要做身份传递、授权范围、幂等和审计。
- 高风险委派必须有人类确认或策略引擎确认。

## 5. 实时 / 语音 / 多模态 Agent

参考入口：

- 以官方模型/语音/实时 API 文档和目标公司 JD 为准；本文件只校准通用工程口径。

面试常问：

- 实时 Agent 的低延迟怎么做？
- 用户打断、ASR 错误和多模态证据冲突怎么办？
- 高风险工具动作怎么确认？

不要这么说：

```text
语音 Agent 就是 ASR 转文字后调用普通聊天接口。
```

应该这么说：

```text
实时 Agent 要把音频接入、VAD/ASR、turn state、实时模型、工具动作、TTS 和治理层拆开设计。关键指标包括首响延迟、打断恢复、ASR 置信度、误触发率、安全通过率和人工接管率。
```

面试防守点：

- trace 要按 turn_id 记录 partial/final transcript、confidence、barge-in、tool_action、approval 和最终结果。
- ASR 低置信度或图像/文本/语音证据冲突时先澄清，不直接执行高风险动作。
- 最后 30 分钟只在 `80/77` 标为最高风险 B/C 时看 `78` 的 30 秒口径，不通读附录。

## 6. OpenAPI

官方入口：

- OpenAPI Specification：https://spec.openapis.org/oas/latest.html
- OpenAPI Initiative：https://www.openapis.org/

面试常问：

- OpenAPI 是什么？
- OpenAPI 怎么转 Tool？
- API schema 对工具调用有什么影响？
- OpenAPI 和 JSON Schema 的关系？

不要这么说：

```text
有 OpenAPI 就能直接让模型安全调用接口。
```

应该这么说：

```text
OpenAPI 能描述 HTTP API 的路径、方法、参数、requestBody、response 和安全方案。把 OpenAPI 转 Tool 时，operationId、description、parameters、requestBody 可以生成工具名、描述和输入 schema。但要让模型稳定调用，还需要补业务语义、风险等级、权限、错误码、幂等和审计。
```

面试防守点：

- API 描述是工程语义，Tool 描述要补业务语义。
- 写操作必须有确认、权限和幂等。
- response schema 要能让 Agent 理解成功/失败。
- 不要暴露万能 `execute_sql` / `call_any_api` 之类工具。

## 7. Tool Calling / Function Calling

官方入口：

- OpenAI Function Calling：https://platform.openai.com/docs/guides/function-calling
- OpenAI Structured Outputs：https://platform.openai.com/docs/guides/structured-outputs

面试常问：

- Tool Calling 流程是什么？
- 工具 schema 怎么设计？
- 工具调用失败怎么办？
- Structured Output 和 Tool Calling 有什么区别？
- 如何防 Prompt 注入导致工具误调用？

不要这么说：

```text
Tool Calling 就是模型直接调用函数。
```

应该这么说：

```text
Tool Calling 本质上是模型根据上下文生成结构化的工具调用意图和参数，真正执行工具的是应用层。应用层要做 schema 校验、权限校验、风险分级、超时重试、幂等和审计。模型不能绕过业务权限。
```

Structured Output 口径：

```text
Structured Output 主要用于让模型按指定 schema 输出结构化结果；Tool Calling 主要用于让模型选择工具并生成调用参数。两者都依赖 schema，但用途不同。
```

## 8. FastAPI / Python 后端

官方入口：

- FastAPI 文档：https://fastapi.tiangolo.com/
- FastAPI async 文档：https://fastapi.tiangolo.com/async/
- Python asyncio 文档：https://docs.python.org/3/library/asyncio.html

面试常问：

- FastAPI 为什么适合大模型应用？
- async/await 适合什么场景？
- SSE 流式响应怎么做？
- 模型调用并发怎么控？
- GIL 对异步有什么影响？

不要这么说：

```text
用了 async 就一定更快。
```

应该这么说：

```text
async/await 适合 I/O 密集场景，比如调用模型 API、向量库、外部工具和数据库。它能减少等待期间的线程阻塞，但 CPU 密集任务不会因为 async 自动变快。大模型应用里常用 FastAPI 做 API 层、SSE 流式响应、异步工具调用、限流和超时控制。
```

面试防守点：

- 模型 API 调用是 I/O 密集，适合异步。
- embedding 批处理、PDF 解析、OCR 可能是 CPU/GPU 密集，要用 worker 或任务队列。
- SSE 可以改善首 token 体验，但不减少总 token 生成成本。
- 并发要配合限流、连接池、超时和熔断。

## 9. 向量数据库与检索

官方入口：

- Milvus 文档：https://milvus.io/docs
- Qdrant 文档：https://qdrant.tech/documentation/
- Weaviate 文档：https://weaviate.io/developers/weaviate
- pgvector GitHub：https://github.com/pgvector/pgvector
- FAISS 文档：https://faiss.ai/

面试常问：

- 向量数据库解决什么问题？
- HNSW、IVF、PQ 是什么方向的索引？
- 为什么要混合召回？
- metadata filter 怎么做权限？
- rerank 为什么重要？

不要这么说：

```text
向量数据库就是存 embedding 的数据库。
```

应该这么说：

```text
向量数据库不只是存 embedding，还要支持近似最近邻检索、metadata 过滤、集合管理、索引构建、增量更新和查询性能优化。RAG 里它解决语义召回，但对专有名词、编号、错误码不一定稳定，所以常和 BM25、关键词、rerank 组合。
```

面试防守点：

- 权限过滤尽量检索前做 metadata filter，不要召回后再删。
- topK 越大不一定越好，会增加噪声、延迟和成本。
- rerank 能提升排序质量，但也会增加延迟。
- pgvector 适合和业务数据库集成，专用向量库适合更复杂的向量检索和扩展场景。

## 10. RAG 评测

可参考入口：

- Ragas 文档：https://docs.ragas.io/
- LangSmith Evaluation：https://docs.smith.langchain.com/evaluation

面试常问：

- RAG 怎么评估？
- Recall@K 和答案准确率的关系？
- faithfulness 是什么？
- bad case 怎么回流？

不要这么说：

```text
我让模型回答几道题，看起来不错就上线。
```

应该这么说：

```text
RAG 评测要拆成检索层和生成层。检索层看正确证据是否进入 topK、排序是否靠前；生成层看答案是否忠于证据、引用是否准确、无答案时是否拒答。线上再结合用户反馈、追问率、人工转接率和 bad case 回流。
```

面试防守点：

- 没有标注集时，可以先从线上日志和业务 FAQ 构造小评测集。
- bad case 修复后要进入回归集。
- 评测不能只看平均分，还要看高风险问题和长尾问题。

## 11. 微调 / LoRA / PEFT

官方入口：

- Hugging Face PEFT：https://huggingface.co/docs/peft/index
- Transformers 文档：https://huggingface.co/docs/transformers/index

面试常问：

- 什么时候微调，什么时候 RAG？
- LoRA 的核心思想是什么？
- SFT 数据怎么构造？
- 微调后怎么评估？

不要这么说：

```text
知识库问答效果不好就微调。
```

应该这么说：

```text
如果问题是事实知识更新、引用溯源、权限隔离，优先用 RAG；如果问题是固定任务格式、领域表达、分类抽取、回答风格或工具调用格式稳定性，可以考虑 SFT/LoRA。微调不是替代 RAG，而是解决不同问题。
```

面试防守点：

- 微调不能可靠记住频繁变化的事实。
- 微调后仍然需要评测和安全验证。
- 数据质量比训练技巧更关键。
- LoRA 适合低成本适配，不代表一定比 Prompt/RAG 更好。

## 12. 官方口径一页速背

```text
LangChain：
大模型应用开发框架，适合模型、Prompt、Retriever、Tool、Chain 组合。

LangGraph：
有状态图编排，适合多步 Agent、分支、checkpoint、人机协同。

MCP：
大模型应用接入工具、资源、Prompt 的协议，不替代权限治理。

OpenAPI：
HTTP API 描述规范，可转 Tool，但要补业务语义、权限、风险和审计。

Tool Calling：
模型生成工具调用意图和参数，应用层负责真正执行、校验和审计。

FastAPI/async：
适合 I/O 密集的大模型服务，CPU/GPU 任务要用 worker/队列。

向量数据库：
支持向量检索和 metadata filter，RAG 中常配合 BM25、rerank。

RAG 评测：
检索层看 Recall/MRR/NDCG，生成层看忠实度、引用、拒答。

微调：
适合风格、格式、固定任务和领域适配；事实知识和溯源优先 RAG。
```

## 13. 临面前 5 分钟纠错

逐条检查自己有没有说错：

- 我有没有把 MCP 说成 OpenAPI 替代品？
- 我有没有把 Tool Calling 说成模型直接执行函数？
- 我有没有把 LangGraph 说成“高级 LangChain”？
- 我有没有把向量数据库说成只存 embedding？
- 我有没有把 RAG 效果评估说成“看回答准不准”？
- 我有没有把微调说成知识库问答的默认方案？
- 我有没有说 async 一定更快？
- 我有没有忽略权限、审计、成本和灰度？

只要这 8 个点不翻车，概念边界基本稳住。
