# HR / 主管面 / 行为面回答手册

> 目标：解决“技术面过了，但主管面/HR 面表达不稳”的问题。  
> 这份文件适合在终面前、主管面前、HR 面前配合 `18`、`24`、`40` 使用。

## 1. 行为面的本质

主管面和 HR 面不是闲聊，而是在判断：

| 维度 | 他们想确认什么 | 高分信号 |
|---|---|---|
| 动机 | 为什么来这个岗位 | 目标清晰，和岗位匹配 |
| 稳定性 | 会不会短期离开 | 职业规划合理，不逃避问题 |
| ownership | 是否能主动推进 | 遇到问题不甩锅，有闭环 |
| 协作 | 能否和产品、算法、后端、业务合作 | 能沟通取舍，推动共识 |
| 复盘 | 是否能从失败中学习 | 能讲事实、原因、改进 |
| 成长性 | 是否值得培养 | 有学习路径和技术判断 |

回答原则：

```text
真实
  -> 正向
  -> 有事实
  -> 有反思
  -> 和岗位相关
```

不要把 HR 面当成“随便聊”。很多候选人技术没问题，最后败在动机飘、离职原因负面、项目复盘没有 ownership。

## 2. STAR + 技术闭环模板

行为面可以用 STAR，但 AI 应用岗位最好加一个“技术闭环”。

```text
S：当时的业务背景是什么
T：我承担什么目标
A：我做了哪些动作，怎么推动
R：结果如何，有什么指标
L：复盘学到了什么，下次怎么改
```

简称：

```text
背景 -> 目标 -> 动作 -> 结果 -> 复盘
```

如果讲技术项目，可以再补：

```text
问题定位 -> 方案取舍 -> 上线兜底 -> 指标验证
```


## 4. 为什么想来我们公司？

### 腾讯版

```text
我关注腾讯主要是因为它的大模型应用场景离真实用户和业务流程很近。AI Agent 或 RAG 最难的不是 Demo，而是怎么在高频场景里保证体验、准确率、延迟和安全。我过去做项目时也比较关注用户问题、bad case 回流和线上兜底，所以希望在腾讯这样业务场景丰富的平台里继续做更真实的大模型应用落地。
```

### 阿里 / 阿里云版

```text
我比较看重阿里在云和企业服务上的平台化场景。大模型应用发展到一定阶段后，不只是单个业务接入模型，而是需要模型网关、工具平台、Prompt 管理、评测、权限和成本治理。我过去的项目里也逐渐意识到平台化能力的重要性，所以希望在这类工程体系更完整的团队里继续深入。
```

### 百度版

```text
我关注百度是因为它在搜索、知识增强和大模型能力上积累比较深。RAG 和 Agent 应用里，检索、排序、评测和模型边界非常关键。我自己也做过知识库问答和检索优化相关项目，希望能在更强的技术体系里继续提升大模型应用效果优化能力。
```

### 字节版

```text
我关注字节主要是因为它强调效率、数据指标和快速迭代。大模型应用不是一次性上线就结束，后面要靠实验、评测、bad case 回流持续优化。我比较喜欢这种用指标驱动产品和工程迭代的方式，也希望在节奏更快、场景更多的团队里提升自己的工程和业务判断。
```

### 通用版

```text
我选择这个岗位主要看三点：第一，岗位方向和我过去做的大模型应用开发比较匹配；第二，团队场景足够真实，不只是探索 Demo，而是要解决业务问题；第三，我希望下一阶段在工程化、平台化和效果评估上继续成长。
```

## 5. 为什么离职 / 为什么看机会？

安全结构：

```text
先讲正向动机
  -> 再讲发展诉求
  -> 不攻击前公司
  -> 回到目标岗位匹配
```

回答模板：

```text
我看机会主要是出于发展方向考虑。之前的经历让我对大模型应用开发有了比较明确的兴趣，尤其是 RAG、Agent 和工具调用落地。但原团队接下来更偏原有业务维护/业务支持，我希望能在更聚焦 AI 应用工程、更复杂场景和更规范平台体系里继续深入。所以这次会优先看和大模型应用落地强相关的岗位。
```

不要说：

- “公司没前途。”
- “领导不行。”
- “事情太杂。”
- “工资太低。”
- “想找个轻松点的。”

如果真实原因是薪资，也不要把薪资放第一位。可以说：

```text
薪资我会综合考虑，但这次更核心的是方向匹配和成长空间。如果岗位内容、团队方向和个人能力匹配，我相信薪酬可以在合理范围内沟通。
```


### 6.2 3-5 年规划

```text
更长期看，我希望成为 AI 应用工程和平台方向的技术骨干。一方面理解模型、RAG、Agent 的技术边界，另一方面也能理解业务目标、工程成本和团队协作，推动大模型能力在多个场景里规模化落地。
```

## 7. 你最大的优点是什么？

推荐讲和岗位相关的优点：

```text
我觉得自己比较突出的点是工程闭环意识。做大模型应用时，我不会只停在“模型能回答”，而是会继续追问：答案准不准、怎么评估、坏 case 怎么回流、工具调用是否安全、线上失败怎么兜底。

比如在之前项目里，我们遇到过召回到旧文档导致回答错误的问题。我没有直接调 prompt，而是回到文档版本 metadata、权限过滤和评测集回归上解决。这个习惯让我比较适合做需要落地和持续优化的 AI 应用开发。
```

其他可选优点：

- 学习能力强：要举具体学习和落地案例。
- 沟通协作好：要举跨团队推进案例。
- 抗压能力好：要举 deadline 或线上问题案例。
- 代码质量意识：要举重构、测试、日志、监控案例。

## 8. 你最大的缺点是什么？

原则：

- 不要说致命缺点。
- 不要伪装成优点太明显。
- 要讲改进动作。

可用回答：

```text
我之前一个问题是容易在技术方案上想得比较完整，前期会花较多时间比较不同方案。后来我意识到业务场景里需要先明确 MVP 和验证指标，所以现在会先把需求拆成必须做和可以后置两层：先用最小闭环验证价值，再逐步补治理、评测和平台化能力。
```

不要说：

- “我太追求完美。”
- “我不太会沟通。”
- “我抗压不太行。”
- “我基础还不扎实。”

## 9. 项目失败 / 效果不好怎么办？

标准回答：

```text
如果项目效果不好，我会先避免把问题简单归因给模型不行，而是拆链路定位。以 RAG 为例，要看文档解析、切分、召回、rerank、prompt、引用和评测哪个环节出问题。定位后先做小范围实验，不会直接大改。

如果最后证明这个方向收益不够，我也会把结论沉淀下来：哪些场景适合大模型，哪些更适合传统搜索或规则系统。失败项目的价值在于形成判断边界，而不是硬上线。
```

主管面加分点：

```text
我会及时和产品/业务同步预期，不会等到最后才说效果不行。大模型应用的不确定性比较强，所以前期就要定义验证指标和退出条件。
```

## 10. 和产品/业务意见冲突怎么办？

标准回答：

```text
我会先把冲突从“谁对谁错”转成“目标和约束是什么”。比如产品希望 Agent 自动执行更多操作，但技术侧担心误调用风险，我会把工具按风险分级：低风险自动执行，中风险二次确认，高风险只生成建议不执行。这样既满足体验，也保留安全边界。
```

可展开案例：

```text
之前类似场景里，业务希望知识库回答尽量多，但我们发现高风险问题如果证据不足还强答，会影响可信度。最后我们一起定义了拒答策略和人工转接机制，用准确率、拒答率和用户满意度一起评估，而不是只看回答率。
```

## 11. 和同事技术方案冲突怎么办？

标准回答：

```text
我会先明确评判标准，比如效果、成本、延迟、实现复杂度和维护成本。然后尽量用小实验或 benchmark 做决策，而不是只靠主观判断。如果时间紧，会先选风险更低、能快速验证的方案，同时保留后续演进空间。
```

AI 应用例子：

```text
比如 RAG 优化时，有人倾向直接换更强 embedding，有人倾向先加 rerank。我会建议先拿固定评测集做对比，看 top-k 命中率、答案准确率、延迟和成本。这样讨论会更聚焦。
```

## 12. 你如何学习新技术？

标准回答：

```text
我学习新技术一般分三步。第一步看官方文档和核心概念，先建立边界；第二步做一个最小可运行 Demo，验证关键能力；第三步结合项目场景补工程问题，比如异常、权限、日志、评测和成本。

比如学习 LangGraph 时，我不是只看节点和边，而是重点验证它在有状态 Agent、checkpoint、人工介入和失败恢复里的价值，然后再判断哪些业务流程适合用它。
```

## 13. 你怎么看 AI Agent 的发展？

主管面回答：

```text
我认为 AI Agent 的价值不在于完全自动化一切，而是在明确边界内提升复杂任务的执行效率。短期 Agent 更适合信息查询、流程辅助、低风险工具调用和人机协同；高风险、强一致性、不可逆操作仍然需要规则、权限和人工确认。

工程上，Agent 的核心壁垒会从“能调用工具”转向“可控、可评估、可观测、可治理”。所以我比较关注状态管理、工具权限、失败恢复、评测体系和成本控制。
```

## 14. 你怎么看 RAG、微调和 Agent 的关系？

```text
我会把它们看成不同层次的能力。RAG 解决知识接入和可追溯问题，微调解决模型行为、格式、风格和领域任务适配问题，Agent 解决多步骤任务规划和工具执行问题。

实际项目里通常不是三选一，而是组合使用：RAG 提供可信上下文，模型负责理解和生成，Agent 在需要执行动作时调用工具，微调用在 prompt 难以稳定约束的特定任务上。关键是根据业务问题选择最小够用的方案。
```

## 15. 薪资期望怎么说？

原则：

- 不要过早报死。
- 不要只说“都可以”。
- 先强调岗位匹配，再给合理区间。

回答模板：

```text
我会结合岗位职责、团队方向、整体薪酬结构和我的经验来综合考虑。目前我更看重方向匹配和成长空间。如果需要给一个预期，我希望在市场合理范围内，结合贵司职级和薪酬结构沟通。
```

如果必须给数字：

```text
结合我目前的经验和市场情况，我期望整体 package 在 X 到 Y 之间，但我不是只看数字。如果岗位内容和团队方向非常匹配，我愿意结合整体机会沟通。
```

## 16. 反问问题

### 16.1 问技术面试官

- 团队当前 AI 应用主要是 RAG、Agent，还是平台工具方向？
- 现在最核心的技术挑战是效果、成本、延迟，还是安全治理？
- 团队是否有统一的评测集、bad case 回流和模型网关？
- 这个岗位进去后前三个月最希望解决什么问题？

### 16.2 问主管

- 团队对这个岗位的短期和长期期待分别是什么？
- 业务侧如何衡量 AI 应用的价值？
- 团队更希望候选人偏业务落地、平台建设，还是模型效果优化？
- 当前团队在大模型应用落地里最大的挑战是什么？

### 16.3 问 HR

- 这个岗位的面试流程和后续时间节奏大概是怎样的？
- 团队规模和汇报关系方便介绍一下吗？
- 这个岗位对应的职级和培养路径大概是什么？
- 公司对 AI 应用方向的人才发展有什么规划？

## 17. HR 面危险问题

### 17.1 你还有其他 offer 吗？

```text
目前有一些流程在推进中，但我会优先考虑岗位方向、团队匹配度和成长空间。贵司这个岗位和我想做的大模型应用方向比较匹配，所以我也比较重视这次机会。
```

### 17.2 你能接受加班吗？

```text
我能接受项目关键阶段必要的投入，比如上线、故障处理或重要版本交付。但我也会关注效率和计划性，希望通过清晰排期、风险前置和工程化手段减少无效加班。
```

### 17.3 你为什么适合这个岗位？

```text
我觉得匹配点主要有三点。第一，我的项目经验和岗位里的 RAG/Agent/工具调用方向比较接近；第二，我比较重视工程落地，包括评测、日志、权限、成本和兜底；第三，我愿意继续在大模型应用平台化方向深入，而不是只停留在调用 API。
```

## 18. 临场表达禁忌

不要：

- 说前公司、前领导坏话。
- 把所有问题归因给别人。
- 夸大项目上线规模。
- 把 Demo 说成大规模生产。
- 对薪资和职级表现得过度焦虑。
- 问“会不会很累”“加班多不多”这种直接负向问题。

可以：

- 真实说明项目阶段。
- 强调自己做过的部分。
- 说明复盘和改进。
- 把个人诉求和岗位方向对齐。
- 用具体案例证明软技能。

## 19. 主管面最后 2 分钟总结

如果面试官让你最后补充，可以说：

```text
我最后简单总结一下。我过去的经验主要集中在大模型应用开发，尤其是 RAG、Agent 工具调用和 Python 后端落地。我比较重视工程闭环，不只是接模型，而是关注效果评估、bad case 回流、权限安全、日志追踪和线上兜底。

这次岗位和我想继续深入的方向比较匹配。如果有机会加入，我希望先快速熟悉团队业务和现有系统，短期把交付做好，中长期在 Agent/RAG 平台化和评测治理上做更多沉淀。
```

## 20. 最后速记

```text
HR 面看动机和稳定性
主管面看 ownership 和业务判断
行为面看事实和复盘
终面看你能不能从技术执行走向问题负责人
```

一句话：

```text
不要把自己包装成“会用 AI 框架的人”，要表达成“能把 AI 能力落到业务结果的人”。
```
