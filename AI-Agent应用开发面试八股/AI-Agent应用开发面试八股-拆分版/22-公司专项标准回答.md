# 公司专项标准回答

> 用法：看完 `15-公司风格与高频权重表.md` 后，用这份练“目标公司风格”的口述回答。这里不是公司官方题库，而是按公开 JD/面经常见追问方式整理的回答模板。

## 1. 腾讯专项

### 1.1 如果 Agent 调用跨境汇款工具超时，能不能自动重试

#### 30 秒回答

不能简单自动重试。跨境汇款属于高风险非幂等操作，超时不代表失败，可能已经执行成功。应该用 idempotency_key、交易状态查询、幂等接口、审计日志和人工兜底，确认上一笔状态后再决定是否补偿或重试。

#### 2 分钟回答

我会先区分“模型决策”和“业务执行”。模型最多生成汇款意图和参数，真正执行必须由后端工具服务控制。  

对跨境汇款这种资金操作，执行前必须有用户确认和权限校验；执行时带全局唯一 idempotency_key；如果工具调用超时，不能让 Agent 直接再次发起同样请求，而是先查询交易状态。  

如果状态是成功，就返回成功并停止；如果状态是处理中，就等待或转人工；如果明确失败，才根据业务规则决定是否允许重试。全流程要记录 request_id、user_id、tool_call、参数摘要、交易状态和审计日志。

#### 项目化表达

我会把这种操作从普通 Tool 里单独标记为 high_risk_write_tool，必须经过 human_confirm 节点。LangGraph 里会有 pending_action、approved、idempotency_key、transaction_status 这些状态字段，超时后进入 check_status 节点，而不是回到模型自由决策。

### 1.2 多 Agent 怎么编排

#### 30 秒回答

多 Agent 编排一般会用 supervisor/router 控制，每个 Agent 负责单一职责，比如检索、工具执行、审核、总结。关键不是 Agent 越多越好，而是要定义共享状态、输入输出 schema、终止条件和冲突处理。

#### 2 分钟回答

我会先判断是否真的需要多 Agent。如果固定流程能解决，优先用工作流。需要多 Agent 时，一般采用 supervisor 模式：supervisor 根据任务状态决定调用 Researcher、Tool Executor、Reviewer、Writer 等子 Agent。  

每个 Agent 的输出要结构化，比如 `{"status": "...", "evidence": [], "next_action": "..."}`。状态由统一编排层维护，而不是让 Agent 之间随意传长文本。还要设置最大轮数、超时、成本预算和 fallback，避免多 Agent 互相讨论但不收敛。

#### 项目化表达

客服场景里我不会把所有能力都拆成自由对话 Agent，而是让 router 先判断意图。RAG、订单查询、工单创建是节点或工具，只有复杂投诉处理才可能拆成规则检索、处理建议、审核三个子 Agent。

### 1.3 RAG 知识库如何热更新

#### 30 秒回答

热更新要基于 doc_id 和 version 做增量索引。新版本先解析、切分、embedding 并写入向量库，切换 active_version 后再异步删除旧版本，避免更新过程中查询为空。

#### 2 分钟回答

我会把文档更新做成异步 pipeline。文档源变更后触发任务，解析并生成新 chunk，每个 chunk 带 doc_id、version、chunk_id 和权限元数据。  

更新策略上，不建议先删旧版本再写新版本，因为中间失败会导致知识缺失。更稳的是先写新版本，校验 chunk 数和索引状态，再切换 active_version。在线检索只查 active_version，旧版本异步清理。  

如果文档更新频繁，还要做任务队列、去重、失败重试和版本回滚。

## 2. 阿里/阿里云专项

### 2.1 Agent 工具如何注册和发现

#### 30 秒回答

工具注册需要统一的 tool registry，保存工具名、描述、参数 schema、返回 schema、风险等级、权限要求、超时和版本。Agent 执行前从 registry 获取可用工具列表，并根据用户权限和场景过滤。

#### 2 分钟回答

我会把工具接入做成平台能力，而不是在 Prompt 里手写工具列表。每个工具注册时需要定义 name、description、args_schema、return_schema、risk_level、owner、timeout、permission_scope 和 version。  

运行时，Agent 根据用户、租户、业务场景和工具风险等级获取工具白名单。模型只看到当前可用工具的 schema，避免无关工具干扰。执行前后端再次做 schema 校验和鉴权。  

如果新增工具，理想情况下只需要注册 schema 和执行器，不需要改 Agent 主流程。复杂工具可以从 OpenAPI 生成初版 schema，再人工优化 description 和风险标记。

#### 项目化表达

如果用 LangGraph，我会有一个 load_tools 节点，根据 state 里的 user_id、tenant_id、intent 加载工具列表。写操作工具会进入 human_review 分支，只读工具可直接执行。

### 2.2 新增一个模型，架构要改多少

#### 30 秒回答

如果架构设计合理，不应该大改业务链路。应该通过模型网关或 adapter 层屏蔽差异，统一 chat、embedding、rerank、stream、tool calling 和 structured output 接口。

#### 2 分钟回答

模型差异主要体现在上下文长度、tool calling 格式、stream 协议、token 计费、structured output 能力和错误码。  

我会设计一个 model gateway，把不同供应商模型适配成统一接口。业务层只依赖内部抽象，比如 `chat()、stream_chat()、embed()、rerank()、tool_call()`。  

新增模型时，只新增 adapter 和配置，包括模型名、上下文窗口、temperature 默认值、超时、限流、价格、是否支持工具调用等。上线时做灰度和 A/B，观察延迟、成本、答案质量和错误率。

### 2.3 SSE 流式输出怎么实现

#### 30 秒回答

后端用 `text/event-stream` 返回 SSE，模型生成 token/chunk 时通过 async generator 持续 yield 给前端。要处理断连、超时、异常、done 事件和日志统计。

#### 2 分钟回答

SSE 适合模型回答这种服务端单向推送场景，实现比 WebSocket 简单。FastAPI 里可以用 `StreamingResponse` 包 async generator。  

关键点是：模型调用要支持 async stream；每个 chunk 按 SSE 格式 `data: ...\n\n` 输出；客户端断连时停止上游模型调用或释放资源；异常时发送 error event；结束时发送 done event。  

线上还要关注代理层缓冲、心跳、超时、token 统计、trace 和敏感信息过滤。

## 3. 百度专项

### 3.1 Agent skill 是什么

#### 30 秒回答

Agent skill 可以理解为 Agent 可调用的一个结构化能力单元，通常包括名称、描述、参数 schema、执行逻辑、返回结果和使用约束。它和 Tool 很接近，但更强调可组合的任务能力。

#### 2 分钟回答

一个 skill 需要让模型知道“什么时候用、怎么用、输入什么、输出什么”。所以 skill 定义里最关键的是 description 和 schema。description 决定模型是否选它，schema 决定参数是否可校验。  

执行层不能信任模型生成的参数，必须做类型校验、权限校验和异常处理。如果多个 skill 组合执行，还需要 planner 或 workflow 来管理顺序、状态和终止条件。

### 3.2 计划模式是什么

#### 30 秒回答

计划模式是先让模型把复杂任务拆成步骤，再按步骤执行工具或子任务。它能提升长任务的可解释性，但需要执行反馈、计划修正和终止条件，不能只生成一次计划就盲目执行。

#### 2 分钟回答

Planner-Executor 是常见实现。Planner 根据用户目标生成步骤，例如检索资料、调用 API、验证结果、生成答案；Executor 逐步执行，每一步根据 observation 更新状态。  

生产中会限制计划长度，检查每一步是否可执行，并在工具失败或上下文变化时重新规划。对于高风险动作，计划里只能生成待确认动作，不能直接执行。

### 3.3 向量匹配指标怎么选

#### 30 秒回答

常见指标有 cosine similarity、dot product 和 Euclidean distance。选择要和 embedding 模型训练方式保持一致。很多归一化向量下 cosine 和 dot product 排序近似等价。

#### 2 分钟回答

如果 embedding 输出做了 L2 归一化，cosine similarity 和 dot product 往往排序一致；如果没有归一化，dot product 会受向量长度影响。Euclidean distance 更关注空间距离。  

实际选型时我会优先看模型文档推荐，并用评测集验证 Recall@K、MRR 和延迟，而不是单纯从数学定义判断。

## 4. 字节专项

### 4.1 你项目最难的点是什么

#### 30 秒回答

最难的是把 RAG/Agent 从 Demo 做到可控。具体包括召回不准、模型幻觉、工具调用风险和线上延迟成本。我主要通过 badcase 评测、hybrid search、rerank、引用校验、工具权限和 trace 来治理。

#### 2 分钟回答

我会按“现象、根因、方案、效果”讲。  

现象是用户问一些制度或业务问题时，系统有时答非所问，或者调用工具参数不稳定。根因不只是模型问题，而是文档切分破坏语义、召回结果有噪声、Prompt 约束不足、工具 schema 不清晰。  

方案上，我先从 trace 里抽 badcase 建评测集，再分别优化 chunk、query rewrite、hybrid search、rerank 和 Prompt。工具调用方面，统一 schema、参数校验、权限和高风险确认。  

效果上，如果没有线上指标，我会如实说做了离线评测和 Demo 验证；如果有指标，就讲 Recall@K、延迟、转人工率、用户反馈等。

### 4.2 如果 QPS 提升 10 倍怎么办

#### 30 秒回答

先用 trace 找瓶颈，再分层优化：入口限流，检索和工具调用异步并行，热点缓存，embedding/rerank 批处理，模型路由和降级，长任务队列化，同时按租户做 quota。

#### 2 分钟回答

QPS 提升 10 倍时，瓶颈可能在模型 API、向量库、rerank、外部工具、数据库和日志系统。  

我会先拆指标：P50/P95 延迟、每步耗时、错误率、队列长度、token 成本、向量库 QPS 和工具调用 QPS。  

优化上，简单问题走缓存或小模型；RAG 热点 query 缓存检索结果；embedding 和 rerank 尽量批处理；多个只读工具可以并行；对慢工具设置超时和降级；入口按用户和租户限流；对长任务走异步队列。  

同时要做压测和容量预估，不能只靠代码层优化。

### 4.3 token 成本怎么优化

#### 30 秒回答

主要从模型路由、上下文压缩、缓存、减少无效召回和工具调用、Prompt 版本优化入手。简单任务用小模型，复杂任务再用大模型。

#### 2 分钟回答

token 成本包括输入上下文和输出答案。输入侧要控制 top_k、合并去重 chunk、摘要压缩历史对话、避免把无关文档塞给模型。输出侧可以限制格式和长度。  

系统侧可以做 query/result cache、embedding cache、Prompt 模板精简、模型分级路由和预算控制。Agent 还要限制最大步数和无效工具调用，因为多步循环很容易把成本放大。

## 5. 美团/京东专项

### 5.1 AI 如何嵌入现有业务流程

#### 30 秒回答

我会把 AI 当成业务流程中的一个决策/生成/检索模块，而不是替代整个系统。查询和推荐可以自动化，高风险写操作要确认，最终状态仍由业务系统落库并审计。

#### 2 分钟回答

业务系统最重要的是稳定性和一致性。AI 可以负责理解用户意图、检索规则、生成建议、填充表单，但订单、工单、退款这些状态变更必须走原有业务服务。  

接入时要考虑鉴权、幂等、事务边界、失败补偿、日志和人工兜底。比如客服 Agent 可以生成退款建议，但真正退款要调用业务服务，执行前确认用户身份和订单权限，执行后记录审计日志。

### 5.2 传统规则系统和大模型怎么配合

#### 30 秒回答

规则系统适合确定性强、合规要求高的判断；大模型适合理解自然语言、总结、生成和处理长尾表达。生产中应该组合使用，而不是让模型替代所有规则。

#### 2 分钟回答

例如退货规则、金额阈值、权限校验、黑名单这些应该由规则或业务代码判断；大模型可以负责从用户描述中抽取订单、原因、诉求，并生成解释话术。  

这样可以把不确定性限制在低风险环节，把强一致和合规判断留给确定性系统。

## 6. 云厂商/平台专项

### 6.1 多租户 AI 平台怎么设计

#### 30 秒回答

核心是 tenant_id 贯穿全链路：文档、向量、工具、Prompt、模型配额、日志和缓存都要租户隔离。再加权限、审计、限流、计费和版本管理。

#### 2 分钟回答

多租户平台要避免数据串租和资源抢占。数据层面，文档和 chunk 元数据必须带 tenant_id，检索时强制过滤；缓存 key 要包含 tenant_id 和权限版本；日志和 trace 也要隔离。  

工具层面，不同租户有不同工具白名单和权限；模型层面要有 quota、限流和成本统计；Prompt、模型、工具和检索策略都要版本化，支持灰度和回滚。

### 6.2 OpenAPI 怎么转 Agent Tool

#### 30 秒回答

OpenAPI 可以解析 path、method、parameters、requestBody 和 response schema 生成工具定义，但不能无脑全暴露。要筛选接口、简化 schema、补充 description、加权限、限流和审计。

#### 2 分钟回答

自动转换只是第一步。OpenAPI 里的接口描述往往是给开发者看的，不一定适合模型选择工具。需要把接口改写成模型容易理解的 tool name 和 description，明确什么时候用、什么时候不用。  

同时要按风险等级筛选，只读接口可以更开放，写接口要人工确认。执行层还要处理鉴权、参数校验、错误码翻译、幂等和日志。

## 7. 初创/AI 产品公司专项

### 7.1 Demo 到生产差什么

#### 30 秒回答

Demo 主要证明链路能跑，生产要解决稳定性、安全、权限、评估、成本、延迟、日志、灰度和回滚。大模型应用最难的不是接 API，而是治理不确定性。

#### 2 分钟回答

Demo 里可能直接把文档塞进向量库、Prompt 里写几个规则、工具直接调用。但生产里要考虑文档更新、租户权限、召回评估、模型幻觉、工具误调用、异常恢复、并发限流和成本。  

所以我会先做最小可用闭环，再逐步补：trace、badcase、评测集、权限、缓存、降级和版本管理。Agent 自主性也要逐步放开，先做受控流程，再放动态决策。

## 8. 公司专项回答的万能结构

如果现场遇到没准备过的公司题，可以按这个结构答：

```text
1. 先界定风险等级：只读查询、低风险生成、高风险写操作。
2. 再拆系统链路：入口、模型、RAG、工具、状态、日志。
3. 然后讲工程约束：权限、幂等、超时、重试、降级、审计。
4. 最后讲评估闭环：指标、trace、badcase、灰度、回滚。
```

一句话收束：

```text
AI 应用在大厂里不能只追求模型效果，还要符合业务系统的稳定性、安全性和可治理性。
```
