# 大厂公司轮次作战手册

> 目标：拿到腾讯、阿里、百度、字节等公司的面试通知后，快速判断这一轮该怎么准备、重点防守什么、哪些文件优先看。  
> 这份文件是 `15-公司风格与高频权重表.md`、`16-模拟面试套卷.md`、`22-公司专项标准回答.md` 的实战编排版。

## 1. 先判断这轮面试的真实目的

大厂面试不只是“问技术”。不同轮次在看不同信号：

| 轮次 | 面试官最想确认 | 你要证明什么 | 最容易翻车 |
|---|---|---|---|
| 一面 | 基础扎不扎实、项目是不是本人做的 | P0 八股能开口，项目细节真实 | 只会名词，不会流程和代码 |
| 二面 | 能否解决复杂工程问题 | 能定位问题、做取舍、讲指标 | 方案只停留在 Demo |
| 交叉面 | 技术通用性和表达稳定性 | 换场景也能讲清楚 | 只熟悉自己项目，不会迁移 |
| 主管面 | 业务理解、 ownership、成长性 | 能从业务目标讲到技术闭环 | 只讲技术细节，不讲价值 |
| HR 面 | 动机、稳定性、沟通风格 | 目标清晰，表达成熟 | 薪资/离职原因/职业规划失控 |

准备顺序：

```text
先看 JD 和公司风格
  -> 判断轮次目标
  -> 准备项目入口
  -> 准备本轮 P0
  -> 准备 2 层追问
  -> 准备反问
```

## 2. 公司风格速记

| 公司/类型 | 更看重 | 面试表达关键词 | 最该防守 |
|---|---|---|---|
| 腾讯 | 业务场景、用户体验、稳定落地 | 真实用户、效果指标、体验优化、线上兜底 | 项目是否真实上线，效果如何验证 |
| 阿里/阿里云 | 平台化、抽象能力、工程体系 | 中台、平台、治理、多租户、可扩展 | 架构是否能规模化，边界是否清楚 |
| 百度 | 搜索/RAG/模型能力、知识增强 | 检索、排序、评测、模型边界 | RAG 原理、召回排序、微调边界 |
| 字节 | 指标、效率、实验、代码能力 | A/B、指标、快速迭代、工程质量 | 数据指标是否扎实，代码是否能写 |
| 美团/京东 | 业务流程、稳定性、成本 | 履约、客服、运营效率、ROI | 能否讲业务闭环和成本收益 |
| 华为/云厂商 | 平台、规范、安全、交付 | 标准化、权限、审计、可靠性 | 企业级治理、云上部署、合规 |
| 初创/AI 产品 | 端到端交付、速度、产品感 | 从 0 到 1、快速验证、成本控制 | 是否能独立落地，而不是只会拆模块 |

## 3. 腾讯作战卡

### 3.1 一面

本轮目标：

- 证明项目真实。
- 证明你能把 AI 能力落到具体业务。
- 证明基础不虚。

候选材料：

- `18-自我介绍与项目包装.md`
- `28-P0标准回答扩展版.md`
- `29-P0标准回答-LangGraph后端版.md`
- `04-RAG与向量数据库.md`

高频追问：

1. 你的项目用户是谁，解决了什么具体问题？
2. RAG 效果怎么评估？
3. 召回失败的 case 怎么定位？
4. Agent 工具调用错了怎么办？
5. 线上响应慢怎么优化？

临场打法：

```text
先业务场景
  -> 再技术链路
  -> 再指标变化
  -> 再线上风险和兜底
```

不要只说“我用了 LangChain”。腾讯风格更吃“这个东西对用户体验有什么改善”。

### 3.2 二面

本轮目标：

- 证明你能处理复杂业务场景。
- 证明你知道上线后的坏 case。
- 证明你有取舍能力。

候选材料：

- `13-大厂连续追问链.md`
- `14-系统设计图与伪代码.md`
- `24-项目答辩讲稿版.md`
- `30-P1标准回答-RAG与Agent进阶版.md`

重点防守：

- RAG 权限过滤。
- 多轮对话上下文污染。
- prompt 注入导致工具误调用。
- 热点问题缓存和更新。
- 人工反馈如何回流。

二面回答模板：

```text
我们一开始遇到的问题是...
定位后发现瓶颈在...
我对比了 A/B/C 三种方案...
最终选择...因为...
上线后用...指标验证，并保留...兜底。
```

### 3.3 主管面

本轮目标：

- 证明你不只是执行，而是能推动结果。
- 证明你理解业务价值和团队协作。

准备问题：

1. 这个项目如果重新做，你会怎么改？
2. 你推动过哪些跨团队协作？
3. 你怎么判断一个 AI 功能值得做？
4. 遇到效果不达预期时如何推进？
5. 未来你想在 AI 应用方向怎么成长？

推荐反问：

- 团队当前 AI 应用主要服务 C 端用户、内部效率，还是企业客户？
- 当前更关注用户体验、准确率、成本，还是业务转化？
- 线上 bad case 是如何回流到评测和迭代流程的？

### 4.1 一面

本轮目标：

- 证明基础能力和工程规范。
- 证明你做的不是零散功能，而是可维护系统。

候选材料：

- `07-Python后端工程.md`
- `08-协议与工具集成-OpenAPI-RPC-MCP.md`
- `29-P0标准回答-LangGraph后端版.md`
- `31-P1标准回答-Prompt协议微调版.md`

高频追问：

1. 你们的接口如何设计？
2. Tool schema 如何版本兼容？
3. 多租户权限怎么做？
4. 模型调用如何限流和降级？
5. 服务可观测性怎么做？

临场打法：

```text
模块边界
  -> 数据流
  -> 异常处理
  -> 扩展性
  -> 治理能力
```

阿里风格里，“能跑”不够，最好讲成“能规模化接入、能治理、能复用”。

### 4.2 二面

本轮目标：

- 证明抽象设计能力。
- 证明你能设计平台而不是单点功能。

候选材料：

- `32-P2系统设计平台加分版.md`
- `09-大厂系统设计与项目表达.md`
- `14-系统设计图与伪代码.md`
- `33-P2代码表达加分版.md`

重点防守：

- 模型网关设计。
- Prompt 版本管理。
- 工具调用平台。
- 评测平台。
- 成本统计和预算控制。

二面设计题模板：

```text
先明确用户和租户
  -> 再拆核心模块
  -> 再讲数据模型
  -> 再讲扩展点
  -> 最后讲治理：权限、审计、限流、灰度、成本
```

### 4.3 主管面

准备问题：

1. 你在项目中做过哪些抽象和沉淀？
2. 如果支持 10 个业务线接入，架构怎么演进？
3. 如何平衡业务交付和平台长期建设？
4. 如何推动业务方使用统一平台？
5. 如何衡量平台价值？

推荐反问：

- 团队更偏业务应用落地，还是大模型基础平台建设？
- 目前平台主要服务内部业务线还是外部客户？
- 对新人更期待业务交付、平台抽象，还是模型能力建设？

## 5. 百度作战卡

### 5.1 一面

本轮目标：

- 证明你理解 RAG、检索、模型边界。
- 证明不是只会调框架。

候选材料：

- `04-RAG与向量数据库.md`
- `30-P1标准回答-RAG与Agent进阶版.md`
- `06-模型微调.md`
- `31-P1标准回答-Prompt协议微调版.md`

高频追问：

1. RAG 和微调怎么选？
2. embedding 模型怎么选？
3. 向量召回和关键词召回怎么融合？
4. reranker 为什么有效？
5. 如何设计 RAG 评测集？

临场打法：

```text
先讲检索链路
  -> 再讲排序和生成
  -> 再讲评测指标
  -> 最后讲模型能力边界
```

百度相关岗位更容易深挖“检索增强”和“模型效果”，不要只停在业务包装。

### 5.2 二面

本轮目标：

- 证明你能优化效果。
- 证明你能做实验和评测。

候选材料：

- `13-大厂连续追问链.md`
- `14-系统设计图与伪代码.md`
- `26-真实面经填充版.md`
- `32-P2系统设计平台加分版.md`

重点防守：

- Hybrid Search。
- query rewrite。
- 多路召回融合。
- rerank 延迟和成本。
- bad case 分析。
- 离线指标与线上指标不一致。

回答模板：

```text
效果问题不能直接改 prompt。
我会先拆成解析、切分、召回、排序、生成、引用几个环节，
用 bad case 和评测集定位瓶颈，
再做单变量实验验证收益。
```

### 5.3 主管面

准备问题：

1. 如何判断一个知识增强方案是否有效？
2. 如何做模型能力和工程系统的边界划分？
3. 你如何看 RAG、Agent、微调的组合？
4. 如果业务方说答案不准，你如何推进？
5. 未来大模型应用工程师的核心壁垒是什么？

推荐反问：

- 团队目前更关注检索增强、Agent 应用，还是模型效果优化？
- 是否有统一的离线评测和 bad case 回流平台？
- 岗位是否会参与 embedding/reranker 或微调相关工作？

## 11. 不同公司同一道题怎么变体回答

### 题目：你如何优化 RAG 效果？

腾讯版：

```text
我会先从用户实际问题和体验出发，区分是找不到答案、答非所问，还是答案没有引用。然后按解析、切分、召回、重排、生成、引用几个环节定位，用线上 bad case 和人工标注集验证。最后不仅看准确率，也看用户是否继续追问、是否采纳答案，以及客服或运营成本是否下降。
```

阿里版：

```text
我会把 RAG 效果优化做成可复用链路：数据接入、切分策略、召回策略、rerank、prompt 生成、评测回归都标准化。不同业务可以配置策略，但统一走评测、权限、版本和审计。这样不是单点调参，而是平台化治理。
```

百度版：

```text
我会先拆检索和生成两个阶段，重点看 query rewrite、hybrid search、embedding 模型、向量索引、reranker 和上下文构造。优化时用召回率、MRR、NDCG、答案准确率、引用覆盖率做离线评估，再结合线上 bad case 做迭代。
```

字节版：

```text
我会先定义指标和 baseline，比如 top-k 命中率、答案准确率、延迟、成本和用户采纳率。然后按单变量实验优化切分、召回、rerank 和 prompt，灰度上线后观察线上指标，同时把失败样本回流到评测集。
```

### 题目：为什么用 LangGraph？

腾讯版：

```text
因为我们的业务任务不是单轮问答，而是多步骤执行，需要状态、工具调用、失败恢复和人工确认。LangGraph 可以把流程显式建模，让用户体验和线上风险更可控。
```

阿里版：

```text
LangGraph 的价值在于把 Agent 流程平台化和可治理。节点、边、状态、checkpoint 都显式后，更容易做复用、审计、恢复、灰度和多业务接入。
```

百度版：

```text
我会把 LangGraph 用在需要多步推理和工具执行的任务上，而不是所有 RAG 都套 Agent。它适合有状态流程，但检索增强本身仍要把召回、排序和评测做好。
```

字节版：

```text
用 LangGraph 主要是为了可观测和可迭代。每个节点的输入输出、耗时、成功率都能统计，方便定位哪一步失败，再做实验优化。
```
