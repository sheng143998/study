# 资料库维护规范与去臃肿指南

> 目标：让这套 AI Agent 面试资料能持续迭代，而不是越补越乱。  
> 这份文件回答：什么时候新增文件、什么时候更新旧文件、如何提权题目、如何删除重复内容。

使用边界：本文件仅给资料维护者使用；普通临面用户不要执行维护检查，直接走 `48/80/74/78`。

维护者在结构性新增、大改或准备分发时，用 `79-资料库总验收与维护看板.md` 做最终一致性检查；个人临面记录不需要走完整检查。

## 1. 维护原则

这套资料不是越多越好，而是要满足：

```text
找得到
  -> 背得动
  -> 能开口
  -> 能面试
  -> 能复盘
```

新增内容必须满足至少一个条件：

- 新题型：现有文件没有覆盖。
- 高频化：多个面经/JD 重复出现。
- 可操作：能变成回答、代码、清单或模板。
- 可复盘：能帮助面后更新。
- 可临战：能帮助某个具体轮次准备。

不要新增：

- 只有概念堆砌，没有面试动作。
- 和现有文件高度重复。
- 单条不可信面经里的孤立题。
- 过时框架 API 细节。
- 无法落到项目表达的泛泛观点。

## 2. 文件分层

文件分层以 `79-资料库总验收与维护看板.md` 为最终口径；本节只做维护入口提示。凡是新增文件、改路线、改上场包数量、改评分闭环，都要回 `79` 做一次一致性校验。

| 层级 | 文件类型 | 作用 | 维护策略 |
|---|---|---|---|
| 入口层 | 以 `79` 第 4 节为准：`00`、`36`、`48`、`55`、`74`、`78`、`80` | 找路线、生成 JD 工单、执行减负路线、最后启动 | 必须保持简洁，临战路径优先指向 `48/80/74/78` |
| JD 上场层 | `55`、`66`、`74`、`75`、`80` | 公司/JD 拆解、上场包、轮次替换槽 | `80` 是 JD 工单和上场包源头，`66` 是验收成品口径 |
| 基础层 | `01`-`08` | 技术专题基础 | 稳定维护，少拆新文件 |
| 表达层 | `12`、`18`、`20`、`24`、`42`、`43` | 开口、项目、主管/HR | 高频更新 |
| 题库层 | `10`、`13`、`16`、`27`-`33`、`44`、`45`、`69` | 刷题、代码题和趋势复测 | 按 P0/P1/P2 提权，弱点复测优先落到 `69` |
| 公司层 | `15`、`22`、`26`、`40`、`46` | 公司风格和面经趋势 | 面经后更新 |
| 复盘闭环层 | `21`、`35`、`41`、`47`、`77`、`79` | 证据、评分、弱点关闭、总验收 | 维护者或愿意沉淀资料时面后更新；普通用户只记录个人弱点和下一轮动作 |

## 3. 新增文件判断

新增文件前先问 5 个问题：

1. 现有文件是否已经能容纳？
2. 这个主题是否会被独立复习？
3. 文件名是否能让人一眼知道用途？
4. 是否能和 `00` 的路线形成关系？
5. 是否有明确的使用场景？

适合新增文件：

- “代码面模拟套卷”这种独立场景。
- “HR 主管面”这种独立轮次。
- “公司轮次题型增量”这种独立维护入口。

不适合新增文件：

- 某一个小概念，如“什么是 HNSW”。
- 单家公司单篇面经。
- 一道普通题的标准答案。

这些应该更新到已有文件。

## 4. 更新旧文件判断

| 内容类型 | 更新到哪里 |
|---|---|
| 新技术概念 | 对应专题 `02`-`08` |
| 新标准回答 | `12`、`28`、`29`、`30`、`31` |
| 新系统设计 | `14`、`32` |
| 新公司风格 | `15`、`22`、`40`、`46` |
| 新真实面经 | `21`、`26`、`46` |
| 新代码题 | `17`、`23`、`44`、`45` |
| 新项目追问 | `24`、`42` |
| 新 HR/主管面问题 | `43` |
| 新 JD/轮次拆解 | `48`、`55`、`74`、`75`、`80` |
| 新上场包成品 | `66`、`80` |
| 新弱点卡/复测闭环 | `77`、`80` 建弱点卡，`69` 补复测题，`41` 统一评分 |
| 新复盘方法 | `35`、`41`、`47`、`77`、`79` |

更新旧文件时先判断“这是知识补充，还是上场闭环补充”：

```text
知识补充
  -> 对应专题 / 题库 / 标准回答

上场闭环补充
  -> `80` 做 JD 工单和上场包
  -> `77` 做弱点卡
  -> `69` 做复测题
  -> `41` 给复测评分
  -> `79` 做最终一致性检查
```

B/C 不能只靠“看过答案”关闭；必须复测到 A，或者连续两次稳定 B+，才算真正关闭。

## 5. 题目提权规则

### 5.1 P0

满足任一条件可提为 P0：

- 多家公司反复出现。
- 一面高频基础。
- 直接来自你的简历项目。
- JD 明确写在必备项。
- 不会就容易挂。

例子：

- RAG 完整链路。
- chunk 怎么切。
- LangGraph 和 LangChain 区别。
- Tool schema 怎么设计。
- Python async / SSE。
- LRU / 限流。

### 5.2 P1

满足任一条件可提为 P1：

- 二面深挖常见。
- 岗位专项相关。
- 会明显加分，但不是每轮必问。

例子：

- HyDE / query rewrite。
- checkpoint 恢复。
- MCP Server 设计。
- Prompt A/B。
- 模型路由。

### 5.3 P2

满足任一条件为 P2：

- 三面/主管面加分。
- 平台型岗位关键。
- 需要系统设计和业务抽象。

例子：

- 模型网关。
- 评测平台。
- 多租户权限。
- 成本治理。
- PromptOps / EvalOps。

### 5.4 降权规则

题目可以降权：

- 只在单条低可信面经出现。
- 已经很久没在 JD/面经出现。
- 和目标岗位不匹配。
- API 细节过时。
- 能被更通用的问题覆盖。

## 6. 面经可信度标注

记录面经时标注：

| 字段 | 写法 |
|---|---|
| 来源 | 牛客 / Boss / 官网 JD / 个人复盘 |
| 时间 | YYYY-MM-DD |
| 公司 | 公司 + 部门或业务线 |
| 岗位 | AI Agent / RAG / 后端 / 平台 |
| 轮次 | 一面 / 二面 / 主管 / HR |
| 可信度 | 高 / 中 / 低 |
| 证据 | 题目、JD 原词、多人重复情况 |
| 处理 | 新增 / 提权 / 合并 / 忽略 |

可信度判断：

```text
多人重复 + JD 匹配 = 高
单条面经 + 岗位匹配 = 中
单条面经 + 无上下文 = 低
```

## 7. 去重规则

同一个问题可能有多种问法：

| 问法 | 归一化题型 |
|---|---|
| RAG 怎么做？ | RAG 完整链路 |
| 知识库问答怎么实现？ | RAG 完整链路 |
| 向量库怎么用？ | RAG 检索与向量数据库 |
| Agent 怎么避免循环？ | Agent 终止条件和失败恢复 |
| Function Calling 怎么保证安全？ | Tool schema、权限和审计 |
| 模型输出 JSON 错怎么办？ | Structured Output 和 JSON Repair |

去重策略：

- 题库里保留归一化题型。
- 标准回答里保留一种主问法。
- 追问链里记录变体问法。
- 面经库里保留原始问法。

## 8. 资料臃肿预警

出现下面情况说明需要整理：

- 同一问题在 5 个以上文件重复出现，且没有不同用途。
- `00` 索引越来越长，但路线不清楚。
- 新文件只有概念，没有模板/清单/回答。
- P0/P1/P2 不再准确。
- 面试后找不到应该更新哪里。

处理方式：

```text
先合并重复
  -> 再更新索引
  -> 再调整 P0/P1/P2
  -> 最后删除或降级低价值内容
```

## 9. 每次迭代检查清单

新增或修改后检查：

- [ ] 是否更新 `00-阅读索引.md`。
- [ ] 是否更新使用路线。
- [ ] 是否和已有文件重复。
- [ ] 是否有明确使用场景。
- [ ] 是否能落到面试回答或行动。
- [ ] 是否需要更新 `34-最终冲刺勾选清单.md`。
- [ ] 是否需要更新 `36-总目录导航图与学习地图.md`。
- [ ] 是否需要更新 `46-公司轮次题型增量库.md`。
- [ ] 是否涉及 `48 -> 80 -> 74 -> 78` 的临战路径。
- [ ] 是否需要同步 `66-面试上场包与成品验收清单.md` 的 8/13/19 分层验收。
- [ ] 是否新增了 B/C 弱点；如果有，是否进入 `77/80`，并在 `69` 有复测题。
- [ ] 是否用 `41` 的 `raw_score / grade / display / close_level` 口径评分。
- [ ] 是否最后用 `79-资料库总验收与维护看板.md` 做总验收。

## 10. 维护者：每次面试后资料沉淀流程

普通用户只需记录 3 个答不顺问题和下一轮复习动作；下面流程用于维护资料库。

```text
面试结束 10 分钟内
  -> 用 `35` 记录原题
  -> 用 `41` 给回答打分
  -> 用 `21` 存证据
  -> 用 `26` 更新真实面经
  -> 用 `46` 更新公司轮次题型
  -> 用 `80` 更新 JD 工单 / 上场包差距
  -> B/C 进入 `77/80` 弱点卡
  -> 用 `69` 生成复测题
  -> 用 `41` 做复测评分
  -> A 或连续两次稳定 B+ 后才关闭
  -> 必要时更新 `12/13/24/42/44/45/55/66/74/75/78`
  -> 最后用 `79` 做一致性检查
```

## 11. 每周整理流程

每周做一次轻整理：

1. 看 `21` 和 `35` 是否有未处理错题。
2. 把重复题合并到归一化题型。
3. 把连续出现 3 次的问题提权。
4. 把低价值孤立问题降权。
5. 更新 `34` 的临面清单。
6. 更新 `00` 的后续优化建议。

## 12. 文件命名规范

格式：

```text
编号-主题.md
```

原则：

- 编号连续。
- 标题说用途，不只说概念。
- 尽量让文件名包含使用场景。

好例子：

```text
42-项目深挖追问防守库.md
45-代码面模拟套卷与讲解词.md
46-公司轮次题型增量库.md
```

弱例子：

```text
Agent补充.md
RAG高级.md
更多题.md
```

## 14. 最后速记

```text
资料库维护的目标不是变厚，而是变准：

题型准
  -> 优先级准
  -> 文件入口准
  -> 回答模板准
  -> 复盘动作准
```

一句话：

```text
能被复习路线使用、能被模拟面验证、能被面后复盘更新的内容，才值得留下。
```
